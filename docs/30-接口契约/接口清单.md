> V1.22 **不新增端点**（仍 57 条）：只改 §2 末尾「页面合并」说明里对 `/login` 的旧描述
>（R9–R22 是"进页自动开窗"，**R23 起改为默认不开窗**，`?open=1` 才开），并回填 V1.19–V1.21 三条缺失的修订行。
> V1.21 **不新增端点**（仍 57 条），只给 `GET /documents` 增加查询参数 `match_ready`：
> `match_ready=1` 时只返回「至少有一条已复核资格条件（eligibility / restriction）」的文件，
> 供资格匹配页的政策下拉使用。判据放在后端而不是前端，避免同一语义出现两份实现、
> 也保证 `total` 与过滤后的集合一致。取值范围 `1/0/true/false`，其它值 `1001`。
> 既有 57 条**签名、出参、错误码全部未动**。
> V1.20 **新增一条接口**（56 → 57，#57），是 R20「资格匹配条件覆盖」：
> `PATCH /documents/{id}/rule-applicability`（管理员标记这份政策是否参与资格匹配，
> 标记「不适用」必填理由）。**零新业务态码**：理由缺失/已有已复核条件时用 `1003`，
> 非管理员 `3002`。既有 56 条**签名、出参、错误码全部未动**，仅 `GET /documents*`
> 出参**增** `rule_summary` 字段（向后兼容的加字段，前端据此一次拿到全部文件的状态）。
> V1.19 **新增四条接口**（52 → 56，#53–#56），是 R17「常用政策收藏」：\n> `POST /favorites`（学生收藏，覆盖式幂等）、`GET /favorites`（我的收藏列表，类型筛选 + 关键词搜索 + 分页）、\n> `GET /favorites/ids`（当前用户已收藏的目标标识集合，供收藏按钮渲染状态）、\n> `DELETE /favorites/{target_type}/{target_id}`（取消收藏，幂等）。\n> **零新增业务态码、零改既有表**：新建 `favorites` 关联表（user + target 唯一），\n> 目标不存在复用 `2002`/`2011`/`2009`/`2004`，越权复用 `3002`。\n> 既有 52 条**签名、出参、错误码全部未动**。\n> V1.18 **新增四条接口**（48 → 52，#49–#52），是 R16「办事评价与纠错反馈」：\n> `POST /feedback/corrections`（学生提交纠错，写 `correction_feedback`，覆盖式幂等）、\n> `GET /admin/feedback`（管理员反馈管理，两类合并视图，筛选/排序/分页）、\n> `GET /admin/feedback/stats`（六项统计）、`PATCH /admin/feedback/{kind}/{id}`（状态 + 说明）。\n> **不新增业务态码**（反馈不存在新增 `2012`，其余复用 `1001`/`3001`/`3002`）。\n> 既有 48 条**签名、出参、错误码全部未动**；`GET /messages*` 出参**增** `feedback.comment` 字段\n> （向后兼容的加字段）。\n> V1.17 **新增四条接口**（44 → 48，#45–#48），是 R15「政策更新提醒」：
> `GET /documents/version-candidates`（上传预检，强弱两档候选，只读）、
> `GET /documents/{id}/versions`（历史版本家族：主题组 ∪ 双向 supersedes 链，只读）、
> `POST /documents/{id}/version-link`（**唯一**能把文件标「现行有效」的写入口，管理员显式确认）、
> `GET /policies/updates`（工作台更新区，只读）。零新表零迁移：版本关系复用
> `documents.supersedes_id`（M3 建列，本版首次接通）。**不新增业务态码**：
> 自关联/成环复用 `1001`，旧版本不存在复用 `2002`，越权复用 `3002`。
> 既有 44 条**签名、出参、错误码全部未动**；`GET /documents*` 出参**增** `supersedes_id` 字段
>（向后兼容的加字段），`POST /matches` 与 `GET /matches/{id}` 出参**增** `version_note`
>（多版本时非 null，单版本为 null）。
> V1.16 **新增五条接口**（39 → 44，#40–#44），是 R14「我的校园日历」的写入面：
> `GET /calendar`、`GET /calendar/agenda` 是只读聚合，`POST/PATCH/DELETE /calendar/events` 是
> **学生个人日程**的增改删。前两者**没有新表**（读 `tasks` + `policy_rules` + `calendar_events`），
> 后三者只写 `calendar_events`（第 14 张表，数据模型 V1.5 §3.14）。
> 五条的共同前提：**日历不持有任务的副本**——改期走既有的 `PATCH /tasks/{id}`、
> 标完成走既有的 `POST /tasks/{id}/status`，所以"同步到任务中心"不是一条需要实现的逻辑。
> 不新增业务态码：日程不存在复用 `2004`（资源不存在），越权改他人日程复用 `3002`，
> 日期非法（`2026-02-30`、`25:00`）是 `1001`。
> 既有 39 条**签名、出参、错误码全部未动**。
> V1.15 **新增一条只读接口**（38 → 39，#39）：`GET /recommendations`。
> 它比 R12 的三条更纯粹：响应里没有任何一份数据是它自己的——画像来自 `match_sessions` 最近一次提交、
> 条件来自 `policy_rules`（只认 `approved`）、原文来自 `document_chunks`、版本来自 `guides._pick_document()`。
> 因此**没有新表、没有迁移、没有写入路径**，`tools/init_db.py` 的输出与 V1.14 逐字相同（仍是 13 张表）。
> 唯一新增的业务语义是**三态的聚合口径**（`not_met > unknown > met`）与**排序依据回传**（`sort_basis`）：
> 前者复用 `matching.evaluate()`、不在推荐层重写，后者是为了让「为什么它排第一」可核对。
> 不新增业务态码：无画像不是错误（回 `no_profile` 提示 + 全部 `unknown`），
> 缺文件只是少一张卡（进 `excluded` 并写原因）。
> 既有 38 条**签名、出参、错误码全部未动**（与 V1.13、V1.14 同一条自我约束）。
> V1.14 **新增三条只读接口**（35 → 38，#36–#38）：`GET /guides`、`GET /guides/items`、
> `GET /guides/items/{key}`，另新增业务态码 `2011 GUIDE_NOT_FOUND`。
> 三条接口共同的特点是**不写任何表**：响应全部由 `documents` / `document_chunks` / `policy_rules`
> 三张表现算，服务端不持有指南内容的副本。这也是"不重复建政策库"这条约束在契约上的落地方式——
> 没有写入路径，就没有第二份真值可以写歪。
> 既有 35 条**签名、出参、错误码全部未动**（与 V1.13 同一条自我约束）。
> V1.13 **四轮修复以来第一次真正新增端点**（31 → 35，#32–#35）：注册链路两条（`GET /auth/captcha`、
> `POST /auth/register`）+ 管理员数据看板两条（`GET /admin/analytics/portraits`、`GET /admin/analytics/qa`），
> 另新增两个业务态码 `1006 CAPTCHA_INVALID` 与 `2010 USER_DUPLICATED`。新增的四个端点全部只出不进地
> **不改任何既有端点的签名**——这一点是刻意守住的：R1–R8 八轮里本文档一直写着"一条没加"，如果这一轮
> 为了做新界面顺手去改老接口，前八轮那句自我约束就白写了。
> V1.12 只改一处：§7.3 补偏差 #15——R8 起前端不再渲染正文里的 `[n]` 与匹配条目的 `rule_code`，
> 但**接口出参一个字段都没动**。这属于展示层裁剪，不是契约变更；登记它，是为了让"字段有、界面没有"
> 这件事有据可查，而不是等后来的人翻响应体时以为字段被删了。
> 上一版 V1.11 只改两处：§2.1 `/health` 新增 `llm_config`（降级诊断）、§7.3 补偏差 #14。
> 对应里程碑：M1（冻结）→ M2 起逐条实现
> 配套规范：`接口契约统一规范.md`（外壳、错误码、分页、幂等）
> **计数口径**：本表共 **57** 条，按方法分布 GET 30 / POST 17 / PATCH 7 / DELETE 3。该数字由本表逐行统计得出，**代码落地后必须以 `app.url_map` 导出结果复核**，不得沿用本文数字。
>
> **实现进度（V1.21）**：已实现 **57 / 57**（清单内外全部落地，无剩余项）。该数字由脚本导出，非手填：
> `.venv\Scripts\python.exe tools\dump_routes.py` → `合计 57 条（前缀 /api/v1）  按方法：DELETE 3 / GET 30 / PATCH 7 / POST 17`
>
> **九处清单外新增**：#31 `PATCH /documents/{id}`（M6）、#32–#35（R9）、#36–#38（R12）、#39（R13）、#40–#44（R14）、#45–#48（R15）、#49–#52（R16）、#53–#56（R17）、#57（R20）。
> R18/R19 两轮零接口改动（R18 纯前端、R19 只给现有响应加字段）。
> #31 是 M6 做 T-12 时发现的唯一硬缺口——版本元数据只能在上传那一刻写，
> 而"删了重传"会换 `document_id`，挂在上面的已复核规则全部作废。见 §9 与 §8.8（本文档第 9 节是本版新增）。
> #32–#35 是 R9 的新界面逼出来的：登录小窗要"注册填学号 + 数字验证码"，管理端要有
> "画像记录与提问统计"。**没有一个是"顺手加的"**，每条都对应界面上一块看得见的控件。
> #36–#38 是 R12 的「校园事务指南」逼出来的，但**它们不是写入接口**——指南没有自己的表，
> 三条接口都是"按编目现取"，因此不存在"指南数据写坏了"这种故障类型。见 §11。
>
> #39 `GET /recommendations`（R13）是第四个只读业务接口，比前三个更彻底：**它连编目都不落库**，
> 7 条政策编目是 `app/recommend.py` 里的常量（`_SUBJECTS`），画像取 `match_sessions.profile_json`、
> 条件取已复核的 `policy_rules`、原文取 `document_chunks`，三者现算。契约细节见 §2.12。
>
> **M7 没有新增 `/api/v1` 接口，但改变了根路径的语义**：`/` 从"返回 JSON 说明页"变成
> "托管前端构建产物"，并新增 `/<path:filename>` 这条**静态资源 / SPA 兜底路由**。
> 它不在 `/api/v1` 前缀下、不计入 39 条，但它是契约的一部分（前端深链依赖它），记在 §10。
> R9 又加了 `/welcome` 这个前端路由——纯前端 history 路由，不产生任何后端端点，
> 但它同样依赖 SPA 兜底把 `/welcome` 回落成 `index.html`，所以连同 §10 一起看。
> R12 的 `/guides` 与 `/guides/:key` 同理：两条前端路由，靠 SPA 兜底，不新增后端端点
> （后端的是 `/api/v1/guides*`，是另一回事）。
>

### 2.3 `POST /documents`

| 入参（form-data） | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| file | file | 是 | ≤20MB；扩展名 pdf/docx/txt/md；魔数校验 |
| title | string | 否 | 缺省取文件名去扩展名 |
| department | string | 否 | ≤100 |
| published_at | date | 否 | `YYYY-MM-DD` |
| academic_year | string | 否 | 形如 `2026-2027` |
| effective_status | string | 否 | 缺省 `unknown` |

出参 `data`：`{ "id", "title", "parse_status", "chunk_count", "parse_error", "parse_hint", ... }`

**M3 实现说明（与 V1.0 的偏差，见 §6.1）**：解析在请求内**同步完成**，返回时 `parse_status` 已是终态
（`indexed` / `empty` / `failed`），前端不需要轮询。

- 失败 → `parse_status="failed"`，原因在 `parse_error`；
- 空文本 / 扫描件 → `parse_status="empty"`，可读提示在 `parse_hint`（**同一数据列，按状态选语义化字段名**，前端不必判空两次）；
- 成功 → 两者均为 `null`。

M3 实测四种情形：

| 输入 | HTTP | code | parse_status | 关键字段 |
| --- | --- | --- | --- | --- |
| 正常 PDF（4 页，含章节） | 201 | 0 | `indexed` | `chunk_count=4` |
| 正常 DOCX | 201 | 0 | `indexed` | — |
| 扫描件 PDF（无文本层） | 201 | 0 | `empty` | `parse_hint`="共 1 页，仅提取到 0 个字符（平均每页 0.0 字），疑似扫描件。本系统不含 OCR，请上传带文本层的 PDF 或手工录入。" |
| 空文本 TXT | 201 | 0 | `empty` | `parse_hint`="仅提取到 0 个字符，低于有效阈值 50。" |
| 扩展名 .pdf 但内容是 MZ 头 | 415 | 1005 | —（不落盘） | 魔数校验在写盘前拦截 |

2. 拒答时 `citations` 必须为空数组，`answer.direct_answer` 含"未找到足够依据"；
3. 降级时 `mode != "llm"`，前端必须显示降级标识。

> **M4 实现现状（V1.2 修订）**：上表是 V1.0 冻结的设计。实际实现的入参把
> `document_ids` 改名为 `scope_document_ids`（避免与 `GET /documents/{id}` 的路径参数混淆），
> `top_k` 上限放宽到 20，`include_trace` 未实现（工作流轨迹属 M6）。
> 出参是**扁平结构**，不是 `answer.direct_answer` 嵌套。逐项理由见 §7.3。
>
> 三条硬约束的实现情况：
> | 约束 | 实现 | 验证 |
> | --- | --- | --- |
> | ① 引用必须属于本次检索结果 | 模型只拿到 `[1]..[N]` 顺序编号，越界即剔除；剔除后无有效引用 → 4003 | `test_all_citations_out_of_range_raises_4003`、`test_partially_out_of_range_keeps_valid_and_warns` |
> | ② 拒答时引用为空 | 拒答响应 `data.citations` 不存在，改为返回候选片段供用户自查 | `test_low_coverage_is_refused_without_calling_model` |
> | ③ 降级时 `mode != "llm"` | `mode` 与 `retrieval_mode` 两个字段分开：前者 `llm`/`degraded`，后者 `bm25_only`/`vector` | `test_degraded_mode_returns_raw_candidates` |

### 2.5 `POST /documents/{id}/rules/extract`

V1.0 只写了"触发规则抽取"。实际实现如下（`app/rules.py:extract`）：

| 入参 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| chunk_ids | array[string] | 否 | 只抽指定片段；缺省抽全文 |
| max_rules_per_chunk | int | 否 | 1–20，缺省 8。**按片段限量，不是全篇限量** |

出参：

```json
{
  "document_id": "01J...", "mode": "llm", "model": "deepseek-flash",
  "chunks": 4, "extracted": 20, "stored": 20,
  "dropped": [ { "rule_code": "R-9", "reason": "original_quote 不是该片段的子串" } ],
  "rules": [ { "id", "rule_code", "rule_type", "field_key", "operator",
               "expected_value", "original_quote", "quote_verified": true,
               "extraction_status": "suggested", "review_status": "needs_review",
               "confidence": 0.86 } ]
}
```

**四个契约闸门**（逐条校验，不合法**只丢单条**，不整批失败）：

| 闸门 | 不合法时 | 为什么是丢弃而不是报错 |
| --- | --- | --- |
| `original_quote` 必须是所在片段原文子串 | `dropped` 里记 `original_quote 不是该片段的子串` | 一条引用造假不该让另外 19 条正确规则一起作废 |
| `operator` 必须在 8 算子 + `manual_review` 白名单 | 记 `未知算子` | 同上 |
| `field_key` 必须在 `PROFILE_FIELDS` 九字段白名单 | 记 `field_key 不在画像白名单` | 画像没有的字段无法求值，留着只会让匹配静默跳过 |
| `chunk_index` 不得越界 | 记 `片段序号越界` | 越界说明模型在编片段 |

抽取结果**一律** `review_status="needs_review"`、`extraction_status="suggested"`，**不参与匹配**。
降级模式（无 Key）→ `4006`，`data.note` 明说"规则抽取必须调模型"。

### 2.6 `GET /documents/{id}/rules` 与 `PATCH /rules/{id}`

`GET` 支持 `review_status`（`needs_review` / `approved` / `rejected`）、`rule_type` 过滤，分页 `Paged<Rule>`。

`PATCH` 可改：`description`、`field_key`、`operator`、`expected_value`、`rule_type`、`target_group`、`review_status`。

**复核为 `approved` 时的强校验**（`1003`）：

```text
条件类规则（eligibility / threshold / ...）必须补齐 operator

```

### 2.9 `GET /plans`、`PATCH /plans/{id}`、`GET|POST /tasks`、`PATCH /tasks/{id}`、`POST /tasks/{id}/status`

`GET /plans`：`Paged<Plan>`，支持 `status` 过滤；每项带 `task_count` 与 `progress`（`done / total`）。

`PATCH /plans/{id}`：可改 `title`、`status`（仅 `archived`）。**不允许经此接口把状态改成 `confirmed`**，
确认只能走 `/plans/{id}/confirm`——否则"确认"这个动作就没有唯一入口，审计链断掉。非法转移 → `2005`。

`GET /tasks`：支持 `status`、`plan_id`、`priority` 过滤；`Paged<Task>`。

`POST /tasks`：手工新增待办。**必须有 `plan_id` 且该计划属于自己**（`2004`），
理由：任务中心的任务必须能挂到一个计划上，否则"这个待办是从哪来的"无从回答。

`PATCH /tasks/{id}`：改 `title`/`description`/`priority`/`due_at`/`status`（后者走状态机校验）。

`POST /tasks/{id}/status`：

| 入参 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| status | string | 是 | todo/doing/done/deferred/cancelled |

转移白名单（`shared/enums.py:TASK_TRANSITIONS`）：

| 当前 | 允许转移到 |
| --- | --- |
| `todo` | doing / done / deferred / cancelled |
| `doing` | done / deferred / cancelled |
| `done` | **仅 todo**（撤销完成） |
| `deferred` | todo / doing / cancelled |
| `cancelled` | **仅 todo**（重新启用） |

`done → doing` 被**刻意禁止**：允许它会让 `completed_at` 变得无法解释
（先是 `done` 写了完成时间，再回 `doing` 时这个时间算什么？）。要重做就回 `todo`，语义干净。

非法转移 → 409 / `2005`，`message` 形如：`当前状态 done 不允许转移到 doing（允许：todo）`。
同状态重复提交 → 幂等成功（200，不重复写 `completed_at`）。

这一小节是**唯一一次整块新增**，前九个小节都是 M2–M6 的既有契约。四条分两组：

#### #32 `GET /auth/captcha` —— 公开

无入参。出参 `data`：

```json
{
  "captcha_id": "9Xk2mQ…",          // token_urlsafe(16)，服务端唯一凭据
  "image": "data:image/svg+xml;base64,PHN2Zy…",
  "expires_in": 180,
  "length": 4
}
```

三条硬约束，都是"能被绕过就不算防护"逼出来的：

1. **不回明文**。明文只存在服务端进程内的字典里。这不是洁癖：验证码的唯一价值是
   "人能看、机器难认"，一旦明文随响应下发，`curl` 一次就白拿了。
2. **一码一用，错了也销毁**。`verify()` 第一句就是 `_STORE.pop()`，成功失败都移除。
   留着重试等于把 4 位数字（1 万种）的穷举成本从 1 次降到 N 次。
3. **图片是真文字**。SVG 里的数字是 `<text>` 而不是路径曲线——拿文本编辑器就能读出答案。
   这是**已知限制 C-14**，明确登记，不假装做到了抗 OCR（那要换扭曲位图，是另一个量级）。

#### #33 `POST /auth/register` —— 公开

| 入参 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| display_name | string | 是 | 2–20，去空白后不得为空 |
| student_no | string | 是 | 4–20，仅数字字母 |
| password | string \| null | 否 | 6–72；留空则用「学号后 6 位」 |
| captcha_id | string | 是 | 8–64（来自 #32） |
| captcha_code | string | 是 | 恰好 4 位数字 |

出参 `data`：`{ "token", "expires_in", "user": { "id", "username", "display_name", "role" } , "password_source", "initial_password" }`

- `password_source` 只有两个值：`custom`（用户自己填了）/ `student_no_suffix`（用了默认口令）。
- `initial_password` 在 `custom` 时为 `null`，否则**原样回显身份证件意义上的那个口令**。
  这不是泄露——它就是学号后 6 位，用户本来就有；藏着不说才会让他第二次登录不进去。

**为什么学号即 `username`**：`users` 表没有 `student_no` 列，而本项目用 `create_all()` 建表，
老库不会被自动改结构。加一列就要写迁移、就要考虑"已经注册的人这一列是什么"，
为一个字段引入一整套迁移机制不划算。学号在业务上本来就唯一，直接当 `username`。

**为什么先验验证码再查库**：顺序反过来的话，`"该学号已注册"` 这个响应就变成了
一个**不用过验证码的学号枚举接口**——攻击者能免费问"某某学号在不在"。
现在的顺序是：限流 → 校验参数 → 验验证码（失败即 1006，码作废）→ 查重 → 落库。

**频率限制**：按月限流的一半、最低 3 次/分钟（复用 `LOGIN_RATE_LIMIT_PER_MINUTE`）。
这是全仓第二个公开 POST，不设闸的话注册页就是个现成的请求放大器。

#### #34 `GET /admin/analytics/portraits` —— 仅 A

无入参。数据源是 `match_sessions`（学生在资格匹配页点「开始匹配」时落库的那一行，
`profile_json` 是当时的完整画像快照）——**不另建画像表**。

`data.summary` 关键字段：

| 字段 | 口径 |
| --- | --- |
| `session_count` / `student_count` / `document_count` | 去重计数 |
| `recent_7d` | 近 7 天画像条数 |
| `met` / `not_met` / `unknown` / `judged` | 三态计数，`judged` = 三者之和 |
| `met_rate` | `met / judged`，**`judged = 0` 时为 `null`，不是 0** |
| `avg_completeness` | 已填字段数 ÷ 9（9 个画像字段）后取均值 |
| `by_student_type` | 归并成 专科 / 本科 / 研究生 / 其他 四类 |
| `raw_student_types` | 归并前的原始写法，供核对 |

- **`met_rate` 空库返回 `null` 而不是 0**：0 是"评估了，一条都不符合"，`null` 是"还没人评估"。

- **`by_student_type` 必须归并，`raw_student_types` 必须保留**：库里历史写法至少有

  会得到一张八瓣饼图——每瓣 1 个人。归并到四类图才读得懂，但归并规则是**有损**的，

#### #35 `GET /admin/analytics/qa` —— 仅 A

无入参。数据源是 `messages` 里 `role='user'` 的正文，配 `conversations` 找归属人。

`data` 结构：

| 字段 | 说明 |
| --- | --- |
| `summary.question_count` / `asker_count` / `conversation_count` | 条数 / 去重人数 / 会话数 |
| `summary.keyword_count` | 词云实际词数（`count >= 2` 过滤后） |
| `summary.peak_hour` | 24 小时里最忙的那个钟点；无数据为 `null` |
| `keywords[]` | `{ "word", "count" }`，供 SVG 词云 |
| `topics[]` | `{ "key", "label", "count", "share", "examples" }`，主题偏好图 |
| `hours[]` | 定长 24 项 `{ "hour", "count" }`，**已补零** |
| `weekdays[]` | 7 项 `{ "label", "count" }` |
| `top_askers[]` | 最多 6 项 `{ "name", "count" }` |

四处设计决定，每一处都有"换一种做法就出错"的具体理由：

1. **时区先 +8 再分桶**。库里的 `created_at` 是 naive UTC（`utcnow()` 写的）。
   直接按 UTC 分桶，21 点问的问题会落到 13 点——"晚上问得多"被系统性误判成"下午问得多"。
   面向国内高校，偏移量写死 UTC+8；真要多时区得从用户资料取，那是另一件事。
2. **关键词只留 `count >= 2`**。出现一次的词字号小到看不清，悬停只能回"出现 1 次"，
   纯噪声。这条阈值顺带挡掉 jieba 切出来的半截词（`对绩`、`几本`）——那些几乎都只出现一次。
3. **主题分类用规则不用模型**。看板要的是"同一批数据每次刷新给同样的图"，
   模型分类做不到这点。`TOPIC_RULES` 是 6 组关键词 + 一个"其他事务"兜底；
   多主题命中时取**命中词总长度最长**的那一组，避免"奖学金申请要什么材料"被"申请"拽去别的类。
   代价是 17 条问题落进"其他"，这个数字如实出现在图上，不硬凑。
4. **`hours` 定长 24 且补零**。让前端画图不用自己补空档，也避免"没有提问的时段"
   被压缩成一条直线——那会让深夜看起来和傍晚一样热闹。

#### #37 `GET /guides/items` —— 登录

| `q` | 关键词，在标题 / 简介 / 分类名 / `keywords` / 文件名上做 `lower()` 子串匹配 |
| `page` / `page_size` | 标准分页 |

`data` 除分页外壳外多给三样：`category`（回显分类元数据，供前端显示标题与图标）、
`query`（回显关键词）、`coverage: { total, available }`（当前筛选下有多少条真有政策依据）。

事项卡片字段：`key / category / category_label / title / summary / keywords / recommended /
availability / availability_label / document / conditions_preview / materials_preview /
steps_preview / match_available / plan_available`。

三行摘要的长度分别是 **90 / 72 / 72 字**——对应学生的三个真实问题：
"我够不够格 / 我要带什么 / 我要跑几趟"。截断在**后端**做，前端不切字符串：
切在渲染层会让同一条数据在两个页面显示成两种长度。

#### #38 `GET /guides/items/{key}` —— 登录

无入参（`key` 在路径里）。`data` 是 #37 的卡片字段（去掉三个 `*_preview`）+ 下列字段：

| 字段 | 说明 |
| --- | --- |
| `audience` | `{ text, source }` 或 `null`。**只从原文"适用/面向"句取**，取不到就 `null`，**不从文件标题猜** |
| `blocks[]` | 分区正文：`{ field, label, section, page, article, text }`，`field` ∈ `conditions/materials/steps` |
| `faq[]` | 常见问题字符串数组（**丢弃首行导语**——"这几类问题占了咨询量的一半…"不是问题） |
| `duplicate_fields[]` | 因与前面的分区同源而未重复展示的字段（前端给一句解释，不重复渲染） |
| `actions` | `{ ask: {question, document_id}, match: {available, document_id, reason}, plan: {...} }` |
| `coverage` | `{ sections_found, sections_expected }`——**不假装齐全** |
| `related[]` | 同分类最多 3 条（卡片形态） |
| `source_note` | 固定说明：哪些字段是原文摘录、哪个字段是编辑摘要 |

四条设计理由：

1. **动作可用性在服务端算**（`actions.match.available` / `actions.plan.available`）。
   判据是"该文件有没有**已复核**的 `eligibility`/`restriction` 规则"与
   "有没有 `material`/`deadline`/`process` 规则"。不预判的话，用户点过去必吃
   `2008 RULES_NOT_READY` 或拿到一张空草稿——**两次点击换来一个"这条路不通"**。
2. **`audience` 宁可 `null` 也不猜**。「宿舍管理规定」管不管研究生，从标题猜错
   比留空糟糕得多：留空时界面写"原文未单列适用对象"，读者知道该去问；猜错时读者以为已经知道。
3. **`duplicate_fields` 而不是把重复内容删掉**。缓考、勤工助学等事项的"条件"与"步骤"
   写在同一章，两个字段会命中同一个 chunk。删掉会让"为什么没有办理步骤"变成谜；
   保留一份 + 说一句"原文同属一章"，读者能自己回原文核对。
4. **`2011` 不复用 `2002`**。详见 §11。

1. **`excluded` 与 `coverage` 都不是装饰**。前者回答"为什么没推给我"（否则用户会以为系统漏了

2. **`plan.available` 比 `match.available` 多一个条件**。前者除"本奖项有已复核条件规则"外，

4. **不新增业务态码**。无画像不是错误——回 200 + `notices[no_profile]` + 全部 `unknown`；

### 2.13 R14 新增五条（校园日历：2 条只读 + 个人日程增改删）

#### 2.13.1 `GET /calendar`

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `from` | 否 | `YYYY-MM-DD`，缺省为本月 1 日 |
| `to` | 否 | `YYYY-MM-DD`，缺省为本月最后一天；`from > to` 或跨度 > 366 天 → `1001` |

`data` 结构：

| 字段 | 说明 |
| --- | --- |
| `range` | `{ from, to, days }`，回显解析后的范围 |
| `today` | **服务器本地日期**。前端用它标"今天"，不用浏览器时区另算一个 |
| `items[]` | 范围内有日期的条目，按 `(date, time, priority, title)` 排序；见下 |
| `undated[]` | 没有日期的未完成任务 + 只给月日的政策节点，按 `year_missing` / `no_date_in_policy` / `not_set` 排序 |
| `counts` | `{ total, done, overdue, undated, by_day, by_category, undated_by_category }` |
| `categories[]` | 七类图例 `{ key, label, count }`，**缺的补 0**（列数时多时少会像数据在跳） |
| `notice` | 一句说明：原文只给月日的不会自动补年份 |
| `generated_at` | ISO 8601 UTC |

条目（`items[]` / `undated[]` 同形）：

| 字段 | 说明 |
| --- | --- |
| `id` / `ref_id` / `kind` | `id` 带前缀（`task:` / `event:` / `rule:`）；`kind` ∈ `task` / `event` / `policy` |
| `title` / `description` / `required_materials` / `note` | 前三个来自任务；`note` 是"为什么没有日期"的那句话 |
| `date` / `time` / `due_at` | `date` 为 `YYYY-MM-DD`；**`time` 只在不是 00:00 时才有值** |
| `status` / `done` / `cancelled` / `overdue` | `overdue` = 有日期且早于当前时刻且未完成未取消 |
| `priority` | 任务有，日程/政策节点为 `null` |
| `date_source` / `date_source_label` | `policy`（政策原文）/ `confirmed`（你补全年份）/ `manual`（手动填写）；无日期时为 `null` |
| `category` / `category_label` | 七类之一；由 `rule_type + 文档标题` 实时推断，**不落库** |
| `plan_id` / `plan_title` / `document_id` / `document_title` | 溯源与跳转用；个人日程全为 `null` |
| `raw_text` | 原文里的月日原样（如「9 月 10 日」），只对待确认条目有值 |
| `undated_reason` / `undated_reason_label` | 三种缺法；有日期时为 `null` |
| `editable` / `deletable` | 任务可改期、个人日程可改可删、政策节点都不可 |

四条设计理由：

1. **`date` 为 `null` 不是"没查到"，是结论**。政策只写「当年 9 月 10 日」时，任何具体日期都是编的；
   接口回 `date: null` + `undated_reason: year_missing` + `raw_text: "9 月 10 日"`，
   前端据此把它放进「待确认」而不是格子。**这一条是需求五在契约上的落点。**
2. **`kind='policy'` 与 `kind='task'` 必须分开**。前者是"政策里写了时间、还没生成我的待办"，
   不可勾选；后者是"我的待办"。混在一起，用户会去勾一条不是自己任务的记录。
3. **`date_source` 三态**，不是两态。既有 `tasks.due_source` 只有 `rule` / `manual`，
   而"原文给月日、学生补年份"是第三种，标成 `manual` 会让"这个日期有政策依据吗"无从判断。
4. **`by_category` 与 `undated_by_category` 分开计数**。日历上 0 条、待确认里 20 条是常态
   （真实库里 27 条任务全部无日期）；合并成一个数会让图例显示"材料提交 20"但格子是空的。

#### 2.13.2 `GET /calendar/agenda`

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `days` | 否 | 1–60，默认 7。窗口与 `/tasks/stats` 的 `due_soon` 同一口径 |

`data`：`{ today, window_days, overdue[], soon[], undated[], counts{overdue, soon, undated, undated_year_missing} }`。

- `overdue` 只含**未完成未取消**；已完成的不算逾期（与 `/tasks/stats` 口径一致）；
- `undated` **只放 `year_missing`**，最多 5 条——另外两类在工作台没有可操作性；
  `counts.undated` 仍是全量，用来显示「共 N 条无日期」。

#### 2.13.3 个人日程的增改删

`POST /calendar/events` 请求体：

```json
{"title": "去图书馆还书", "date": "2026-11-21", "time": "15:30",
 "note": "两本", "category": "library"}
```

- `date` 只收 `YYYY-MM-DD`（**不收 ISO 时刻**）：日程的语义是"哪一天"，
  收时刻会逼调用方编一个时区，而日历格子只认日期；
- `time` 可空，格式 `HH:MM`；
- `category` 七类之一，默认 `personal`；
- 成功回 `201` + 完整行。

`PATCH /calendar/events/{id}`：字段全可选。**`time` 传空串表示取消具体时间**，
不传表示不动——两者必须能区分，否则"把时间去掉"与"别碰时间"会变成同一件事。

`DELETE /calendar/events/{id}`：物理删除，回 `{ id, deleted: true }`。
个人日程是用户自己建的，不做软删——软删会在"新建同一天同一条"时留下看不见的重复。

三类错误：`1001`（日期/时间/类型非法，含 `2026-02-30` 这种看起来合法的假日期）、
`2004`（日程不存在）、`3002`（改他人的日程；别人的日程连"存在"都不确认）。

#### 2.14.4 `GET /policies/updates?days=30`

| 参数 | 说明 |
| --- | --- |
| `days` | 1–90，默认 30。越界或非数字 → `1001` |

`data`：`{ window_days, today, items[], counts{total, new_file, meta_updated, plan_related}, notice }`。

条目字段是**封闭集合**（15 个）：`document_id`/`title`/`department`/`published_at`/`academic_year`/
`version_label`/`effective_status`/`created_at`/`updated_at`/`change_kind`/`change_summary`/
`version_count`/`has_newer`/`newer_document_id`/`related_plans`/`may_affect_plans`。

四条设计理由：

1. **没有 `diff`/`changes` 字段是刻意的**（需求红线"不得编造具体变化内容"）。
   系统不做条款对齐——编出来的差异比没有更害人。`change_summary` 只有两句固定话：
   「新文件入库（可能是新版本）」/「文件信息有更新（如有效状态调整）」。
2. **两类更新分开标注**：`new_file`（窗口内新入库）与 `meta_updated`（窗口内元数据变化）。

3. **计划关联按版本家族扩一圈**：旧版被替代后，挂在旧版上的计划同样受新版本影响。
   文案说"可能影响"——条款差异不比对，影响与否只有人读了原文才知道。
4. `notice` 固定声明"系统只提示版本与状态变化，不比对条款内容"，前端原样展示。

下发，不另建接口。纠错反馈是新表 `correction_feedback`——`qa_feedback.message_id` 是
NOT NULL 外键，而"这份政策的发布日期写错了"不指向任何 AI 消息。

#### 2.15.1 `POST /feedback/corrections`

```json
{"target_type": "document", "target_id": "01HX…", "document_id": "01HX…",
 "reason_code": "outdated_policy", "comment": "发布日期写错了"}
```

- `target_type` ∈ document / guide / match；`comment` 必填（纠错不同于一键评价，
  不写清"哪里错"管理员无从核对）；`reason_code` 可选（复用 FEEDBACK_REASONS 六码）；
- **覆盖式幂等**：同一个人对同一对象重复提交只留一条（`updated=true`），不刷排；
- **不写任何正式政策数据**：本接口只插 `correction_feedback` 一行，没有写 documents /
  policy_rules 的路径——"学生反馈不能直接修改政策内容"由此成立；
- 校验失败 `1001`（含 `target_type` 非法、`comment` 缺失）、未登录 `3001`。

#### 2.15.2 `GET /admin/feedback`

| 参数 | 说明 |
| --- | --- |
| `kind` | all / qa / correction，默认 all |
| `status` | pending / processing / resolved |
| `reason_code` | FEEDBACK_REASONS 六码之一 |
| `sort` | `-created_at`（默认，新在前）/ `created_at` |

`data` 为分页结构，条目是**两类合并视图**：公共字段 `kind / id / user / helpful /
reason_code / comment / status / admin_note / created_at / resolved_at` 同形，差异在
`context`——`qa` 带 `question + answer + model + citations`（关联问题、AI 回答、引用片段），
`correction` 带 `target_type + target_id + document`（纠错对象 + 政策文件）。

学生调用 → `3002`；`kind`/`status`/`sort` 非法 → `1001`。

#### 2.15.3 `GET /admin/feedback/stats`

`data`：`{ total, qa{total, helpful, unhelpful, helpful_rate, unhelpful_rate},
correction_count, policy_error_count, reason_distribution[], status{pending,
processing, resolved} }`。

四条口径（`app/feedback.py` 模块注释逐条写明）：

1. **有帮助比例只在答案评价内部算**——纠错反馈没有 helpful 维度，混进去分母就错；
2. **政策错误 = reason ∈ {wrong_fact, outdated_policy} 的答案评价 + 全部纠错反馈**；
3. **reason_distribution 按码计数**（六码），前端映射中文标签；
4. **status 是三类计数**（待处理/处理中/已解决）。

#### 2.15.4 `PATCH /admin/feedback/{kind}/{id}`

```json
{"status": "resolved", "admin_note": "已更正元数据"}
```

`kind` 定位到表（qa / correction）。`status` 与 `admin_note` 至少传一个；`status=resolved`
记 `resolved_at`（correction 另记 `resolved_by`），离开 resolved 清掉 `resolved_at`。
写 `feedback.resolve` 审计。反馈不存在 `2012`、非管理员 `3002`、状态非法 `1001`。

### 2.16 R17 新增四条（常用政策收藏）

```http
POST   /api/v1/favorites                          # 学生收藏（覆盖式幂等）
GET    /api/v1/favorites                          # 我的收藏列表（类型筛选 + 搜索 + 分页）
GET    /api/v1/favorites/ids                      # 已收藏的目标标识集合（按钮渲染状态）
DELETE /api/v1/favorites/{target_type}/{target_id} # 取消收藏（幂等）
```

收藏是一张 `favorites` 关联表（`user_id + target_type + target_id` 唯一），**不改动任何
既有表**。四类目标 `target_type ∈ document / guide / qa / plan`，`target_id` 分别指向
`documents.id` / 指南编目 key / `messages.id` / `action_plans.id`。

#### 2.16.1 `POST /favorites`

```json
{"target_type": "document", "target_id": "01HX…"}
```

- **只收 target_type + target_id**：名称快照与关联政策由后端解析，前端不传 title，
  避免前端随手传一个名称与后端真值不一致；
- **覆盖式幂等**：同 user + target 已存在则刷新快照并返回 `updated=true`，不刷排；
- **目标不存在**：document `2002` / guide `2011` / qa `2009` / plan `2004`；
  **越权**（收藏别人的问答、别人的计划）`3002`；
- **收藏问答只认助手回答且认本人会话**：收藏不泄露他人的问答。

#### 2.16.2 `GET /favorites`

| 参数 | 说明 |
| --- | --- |
| `type` | document / guide / qa / plan，缺省全量 |
| `q` | 关键词，搜「名称快照 + 问答问题 + 问答正文」（内存过滤，因正文不在快照列） |
| `page` / `page_size` | 分页 |

`data` 为分页结构，条目统一形状：`id / target_type / target_type_label / target_id /
title / created_at / document / effective_status`，另按类型带 `question / answer /
citations / answered_at / conversation_id`（qa）或 `plan_status`（plan）。

**两条实时线**（`app/favorites.py` 模块注释）：
1. `document`（关联政策文件）与 `effective_status`（有效状态）**展示时实时 JOIN 目标对象**——
   政策更新或失效后收藏列表同步显示最新状态；目标被下架则 `document=null`，仅剩名称快照；
2. 收藏的问答实时回 `messages.content` 与 `citations_json`——保留原始回答与来源，不随政策更新丢失上下文。

#### 2.16.3 `GET /favorites/ids`

`data`：`{ ids: ["document:01HX…", "qa:01HX…"], count: 2 }`。给各页面的收藏按钮渲染
「已收藏 / 未收藏」状态用，前端挂载时拉一次建内存镜像。

#### 2.16.4 `DELETE /favorites/{target_type}/{target_id}`

物理删除该收藏，回 `{ target_type, target_id, removed: bool }`。幂等：不存在也返回 200、
`removed=false`（取消一个没收藏的东西不算错误）。写 `favorite.remove` 审计。

### 2.17 R20 新增一条（资格匹配条件覆盖）

```http
PATCH  /api/v1/documents/{id}/rule-applicability   # 管理员：标记是否参与资格匹配
```

R20 之前，「这份政策能不能用来做资格匹配」这件事在系统里**没有表达方式**：
`documents` 只记文档元数据，`policy_rules` 只记条件。于是食堂服务指南也只能挤进
匹配下拉，学生选中后拿到一句通用的 `2008`。

这条接口补的就是那个表达方式，但它**只表达人的判定**：`applicable` / `not_applicable`，
后者必填理由。至于"能不能匹配"仍由已复核规则决定（`GET /documents` 出参里的
`rule_summary.state` 是推导值，见数据模型 §4.8）——

> **为什么不让一个标记直接决定"能匹配"**：如果 `applicable` 就代表可用，那么管理员
> 标了适用却没有复核规则时，学生点进来还是空的。状态必须由数据推导，标记只表达意图。

#### 2.17.1 请求与响应

```json
{"applicability": "not_applicable",
 "note": "全文为供餐时间与收费标准，不含申请资格条件"}
```

```json
{"code": 0, "data": {
  "document_id": "01HX…",
  "summary": {"state": "not_applicable", "approved_conditions": 0, "total_rules": 0, "...": "…"},
  "hint": null
}}
```

- `applicability` ∈ unclassified / applicable / not_applicable（枚举外 `1001`）；
- **标 `not_applicable` 时 `note` 必填**，空则 `1003`——理由要留给下一个看这份文件的人；
- **已有已复核的资格条件时禁止标 `not_applicable`**，`1003` 并说明"请先驳回这些规则"：
  匹配接口只按规则查，标了不适用也照样会跑，这种自相矛盾必须在写入时拦住；
- 标 `applicable` 但没有已复核条件时允许，但响应 `hint` 会说明"学生此时仍无法匹配"；
- 文档不存在 `2001`、非管理员 `3002`、未登录 `3001`；
- 每次判定写一条 `document.rule-applicability` 审计（**必须在同一个事务里提交**，
  R20 第一版把它写在 `commit()` 之后，审计行实际上从未落库，是新增的测试抓到的）。

### 2.18 R21 只加查询参数（无新增端点）

```http
GET /api/v1/documents?page=1&page_size=50&parse_status=indexed&match_ready=1
```

`match_ready` 的语义：**这份文件是否至少有一条已复核的资格条件**。

| 取值 | 行为 |
| --- | --- |
| `1` / `true` | 只返回有已复核 eligibility / restriction 规则的文件 |
| `0` / `false` / 不传 | 不过滤（知识库列表用的就是这个） |
| 其它 | `1001` |

实现是一条 `EXISTS` 子查询（`policy_rules.document_id = documents.id AND review_status='approved'
AND rule_type IN ('eligibility','restriction')`），不是"先查 id 再 in_"——后者要为每个 id
拼参数，文件多了会撞 SQLite 参数上限，两次往返之间还有窗口期。

**"已启用"在本系统里等于"已复核通过"**：`policy_rules` 没有独立 enabled 列，
`update_rule` 在 `review_status=approved` 时强制要求算子与预期值（否则这条规则判不了）。
本轮不引入第三种状态——"通过但暂停使用"是另一个功能。

**为什么不做成新端点**：`GET /documents` 本来就存在，加参数比开 `/match/documents` 更小；
而且前端两个页面（知识库 / 匹配）用同一份数据结构，"能不能匹配"只是它的一个视图。

## 6. M3 实现偏差登记

契约一旦冻结就应尽量不改。实现时若必须偏离，**在这里登记，而不是回头偷改 V1.0 的措辞**。

### 6.1 异步解析改为同步解析

| 项 | 契约 V1.0 | M3 实现 | 为什么 |
| --- | --- | --- | --- |
| `POST /documents` 返回时机 | 立即返回 `parse_status=uploaded`，后台解析，前端轮询 | 请求内完成解析，返回终态 | 单机 + 单 worker 部署下，异步只会**增加**状态种类而不减少等待；轮询还得前端配合，M5 才有界面。同步实现让 M3 的 7 条边界用例可以在一行断言里验完 |
| 影响面 | 前端轮询逻辑 | 前端无需轮询 | 若 M7 压测暴露出大文件阻塞（>20 MB / >200 页），再改回异步；届时同步保留为 `?sync=true` 兼容 |

**代价如实记录**：同步解析意味着上传 20 MB PDF 时请求会挂住（实测 4 页 PDF 约 0.3 s，未测大文件）。
`POST /documents` 因此**不适合被前端直连公网**，M6 部署时需在 Nginx 上调大 `proxy_read_timeout`。

### 6.2 `parse_hint` 字段为新增

契约 V1.0 只有 `parse_error`。实现时发现两种语义必须分开：**失败**（文件坏了/加密）与**没有可用文本**（扫描件/空白）
给用户的指引完全不同，混在一个字段里前端只能靠 `parse_status` 猜。故在 `empty` 状态下把提示放到 `parse_hint`。
后端仍存同一列（`documents.parse_error`），只是序列化时按状态换字段名。

### 6.3 `GET /chunks/{id}` 的定位字段

契约 V1.0 只写"单片段 + 上下文 + 定位"，没定字段名。M3 实现如下（`app/documents.py:_chunk_payload`）：

```json
{
  "id", "document_id", "document_title", "chunk_index", "content",
  "char_start", "char_end", "page_number", "section_title", "token_count",
  "document": { "id", "title", "file_name", "effective_status" },
  "context": [ { "chunk_index", "page_number", "section_title", "preview" } ]
}
```

- `char_start` / `char_end` 是片段在**整篇纯文本**中的字符区间，前端可用它做原文高亮——这是引用可追溯的底层能力，M4 直接复用；
- `context` 返回前后各一个片段的**摘要（前 80 字）**，不返回完整正文。理由：完整正文会与 `content` 重复传输三倍数据，而阅读上下文本来就要整篇看，M5 政策详情页会整篇加载。摘要只用于"这条片段前后还有内容"的提示；
- `token_count` 是按中文 1 字 ≈ 1 token 粗估的用量参考，**不是分词器真实计数**，只用于估算上下文预算。

### 6.4 检索接口未随 M3 交付

`POST /retrieval/search`（#11）仍是 M4。M3 的检索能力只通过 `tools/rebuild_index.py --probe` 暴露——
不给前端开口子的原因很直接：**没有覆盖率的检索接口会诱导用户把"召回了 3 条"误读成"答案有依据"**，
而这正是 M4 要解决的事。宁可晚一个里程碑，也不先放一个会误导的口子。

### 6.5 M3 顺带补的两处契约外行为

| 行为 | 说明 | 是否会影响前端 |
| --- | --- | --- |
| SHA-256 去重 | 同一文件重复上传返回 **409 / 2001**，`message` 里带上已存在文档的**标题**。去重只看未删除的文档，软删除后重新上传同一文件是允许的（等价于"恢复"） | 会。前端需提示"该文件已在库中" |
| 软删除后重建索引 | `DELETE` 后立即从内存索引移除该文档的全部片段 | 不会，纯后端一致性 |

> **已知不便利**：409 的响应体里**没有**已存在文档的 `id`——统一外壳在错误分支固定 `data: null`，
> M3 没有为此改动外壳（改外壳的影响面远大于收益）。M5 做上传页时，前端只能按标题去列表里找。
> 若届时体验不可接受，再单独评估"错误分支允许携带 `data`"，而不是现在顺手改契约。

## 7. M4 实现偏差登记

M4 交付 #11–#14 四条接口。与 V1.0 冻结契约有 5 处偏差，逐条给出理由与影响面。

### 7.1 业务态码开始携带 `data`（外壳的一次能力扩展）

**契约原文**：`接口契约统一规范.md §3.3` 只规定"4001/4003/4006 返回 HTTP 200"，未规定响应体形状；
V1.0 时期 `fail()` 固定输出 `data: null`。

**实际实现**：`ApiError` 增加 `payload` 字段，`fail()` 增加 `data` 参数，业务态码携带结构化数据。

**为什么必须改**：拒答时如果只回一句"证据不足"，用户无法判断是**库里真没有**还是**阈值把自己要的文件滤掉了**。
两者的处置动作完全不同（上传文件 vs 调整提问方式），而用户看到的提示一模一样——这等于把排查成本全推给用户。
现在拒答响应带上 `retrieval`（本次检索统计）、`rejected_candidates`（被覆盖率闸门拦下的片段）、
`suggestions`（可执行的下一步），用户能自己判断。

**影响面**：
- 前端：需要按 `code ∈ {4001,4003,4006}` 渲染"提示卡"而非"错误弹窗"，卡片里可以展示候选片段；
- 非业务态错误（1001/3001/500 等）`data` 仍为 `null`，不受影响；
- §6.5 提到的"409 去重响应没有 `id`"这个问题**现在有解了**，但 M4 没有回头改（见 §7.3 第 5 条）。

### 7.2 `POST /retrieval/search` 从"调试接口"变成"可被前端调用"

M3 时这个接口**故意没有实现**，理由记录在 §6.4："没有覆盖率的检索接口会诱导用户把'召回了 3 条'误读成'答案有依据'"。

M4 补上了覆盖率与拒答判定，这个顾虑消除：响应里 `coverage`、`refused`、`refuse_reason` 都是显式字段，
前端不可能把"3 条候选"直接当成答案展示。因此接口开放，但仍**只返回片段与分数，不生成答案**。

## 8. M5 实现偏差登记

M5 交付 #16–#28 十三条接口。与 V1.0 冻结契约有 6 处偏差，逐条给出理由与影响面。

### 8.1 新增业务态码 `2008 RULES_NOT_READY`

**契约原文**：V1.0 把"文档下没有可用条件规则"归到 `1003 参数非法`。

**实际实现**：新增 `2008`（`RULES_NOT_READY`），加入 `BUSINESS_STATE_CODES`，**返回 HTTP 200**。

**为什么必须改**：这不是用户填错了参数，而是**系统当前没有可用的规则**——
用户什么都没做错，重试同样的请求也没用，正确动作是"先去抽规则/复核规则"。
若按 `1003` 返回 400，前端只能弹"参数错误"，用户会去改画像，越改越偏。

**影响面**：前端需按 `code=2008` 渲染"引导去抽规则"的提示卡。已在 `frontend/src/api/client.ts`
的 `BIZ_CODES = {4001, 4003, 4006, 2008}` 里登记。

### 8.2 匹配接口不认 `target_group`（**已知缺口，未修复**）

**契约现状**：`POST /matches` 只按 `document_id` 取该文档下全部已复核条件规则。

**问题**：同一份文件里常有多类条件（`R-4` 励志 gpa≥3.0 / `R-8` 优秀学生 gpa≥3.5），
两条都参与求值时，gpa 3.2 申请励志的学生会被 `R-8` 判"不符合"——**结果里会出现一条与他无关的不符合项**。

**本轮处置**：复核阶段拒绝无关规则（`tools/review_demo_rules.py` 的 `REJECT` 字典里逐条写明理由，
如"校级优秀学生奖学金的条件（gpa≥3.5），不适用于励志奖学金场景"）。

**这是绕过，不是修复**。正解是给 `POST /matches` 加 `target_group` 过滤参数、并在画像里带上申请目标。
排在 M6，理由：改入参要同步改前端表单与已冻结的契约，M5 已用复核期剔除把演示链路跑通，
贸然在结项前动入参会把稳的东西弄不稳。登记在此，不假装解决。

### 8.3 草稿回传 `note` 与溯源字段（新增，未违反契约）

V1.0 的 `confirm` 入参只有 `temp_id/title/priority/due_at/dependency_ids`。
实际新增四个字段：`source_rule_code`、`due_source`、`note`、`needs_human_confirmation`。

原因：这些信息是 `draft` 阶段算出来的**唯一来源**，`confirm` 若不回传，落库后就永久丢失
（"为什么这条任务的截止日期是空的"没有答案）。契约原本没禁止加字段，但**前端必须回传**，
否则表现为"任务建好了，提示语没了"。

### 8.4 `tasks` 表新增 `note` 列（`source_rule_id` 此前从未写入）

`note` 见 8.3。`source_rule_id` 是"这条任务来自哪条规则"的外键，**v1.0 数据模型里就有这一列**，
但 M5 之前从来没写过值（`confirm` 时一律 `NULL`）——等于溯源链在数据层是空的。
M5 补上了写入逻辑：按草稿回传的 `source_rule_code` 反查 `policy_rules.id` 落库，
回执里同时带人可读的 `source_rule_code`。

**部署注意**：`db.create_all()` **不会给已存在的表加列**。已有 `app.db` 的环境需手工执行
`ALTER TABLE tasks ADD COLUMN note VARCHAR(500);`（只需补这一列），或 `init_db --drop` 重建。

### 8.5 `GET /plans` 无单条详情接口

V1.0 列了 `GET /plans` 与 `PATCH /plans/{id}`，但没列 `GET /plans/{id}`。
实际实现也没加：前端计划列表已带 `task_count` 与 `progress`，任务通过 `GET /tasks?plan_id=` 取，
不需要"再取一次计划本身"。**这是有意不加**，不是漏了——加一条只返回 6 个字段的接口没有使用者。

### 8.6 `POST /tasks` 必须带 `plan_id`

V1.0 写的是"手工新增任务"，未规定归属。实际实现强制要求 `plan_id` 且必须是自己的计划（否则 `2004`）。

原因：任务中心里每一条任务都要能回答"属于哪个计划"。允许孤立任务，
就等于允许一堆无法解释来源的待办混进列表，进度条也会算不准。

### 8.8 依赖成环的 HTTP 状态：设计 422 → 实现 409

设计说明书 §11.2 的 T-17 写"依赖成环 → **422**，指出环"。
实现里 `DEPENDENCY_CYCLE(2006)` 映射到 **409**（`shared/codes.py:CODE_HTTP`）。

理由：成环时**资源当前状态冲突**（同一批任务互相依赖，无法确定顺序），语义上是 409 Conflict；
而 422 在本项目已分配给 `SCHEMA_INVALID(1003)`（请求体结构不合法），
若两者都用 422，前端无法区分"字段写错了"与"依赖关系本身不成立"。

**代价**：与冻结设计不一致。已在本表 §8.7 的 T-17 行标注偏差，是否回改留 M6 决定
（回改要同步改前端与 6 处断言，收益只是"与文档一致"）。

## 9. R9 新增业务态码登记

R1–R8 九轮修复里只加过业务态码（`2008`/`2009`），**从没加过新的错误码**。
R9 因为把"注册"搬到了公开互联网上，必须加两个——它们各自承担一件别的码做不了的事。

### 9.1 `1006 CAPTCHA_INVALID`（HTTP 400）

| 项 | 内容 |
| --- | --- |
| 触发 | `captcha_id` 不存在 / 已过期（>180s）/ 已被消费 / 4 位数字不匹配 |
| 为什么不用 `1001 INVALID_PARAM` | 前端**必须据此换一张新图**。参数格式错只需在字段下画红字；验证码错必须重新拉图，因为服务端一码一用、失败即销毁。混成一个码，前端只能猜"这条 1001 是格式错还是码错" |
| 前端契约 | `AuthPanel.vue` 在收到 `1006` 时自动 `GET /auth/captcha` 刷新 `<img>`，并清空输入框 |

### 9.2 `2010 USER_DUPLICATED`（HTTP 409）

| 项 | 内容 |
| --- | --- |
| 触发 | `student_no` 已被注册 |
| 为什么不用 `2001 DOCUMENT_DUPLICATED` | 语义不同、且前端动作不同：文档重复是"换个文件"，学号重复是"**去登录**"。`AuthPanel` 据此把提示的那行字变成可点击的"去登录" |
| 额外含义 | 学号存在与否属于**隐私**。这条消息只在验证码通过之后才可能返回（见 §2.10 #33 的校验顺序），所以它不构成学号枚举通道 |

### 9.3 顺带说明：为什么注册**不做**用户名唯一性校验的独立接口

有人会想"先给个 `GET /auth/exists?student_no=xxx` 让前端实时提示"。
**明确不做**：那个接口本身就是枚举器，一个 GET 就能批量试探学号。
现在的做法是"填完表单、过验证码、提交，错了再说"——体验上多一次失败，安全性上少一个口子。

## 10. 根路径语义与 SPA 兜底（M7；本节长期被头部引用却未落笔，V1.14 补上）

§1 不计入 39 条的两条路由，是前端深链能否打开的前提：

| 路由 | 行为 |
| --- | --- |
| `GET /` | 有 `frontend/dist` 时返回 `index.html`；无 dist 时退化为 JSON 说明页 |
| `GET /<path:filename>` | 静态资源；路径不是文件时回落 `index.html`（history 路由） |

三条约束：

1. **`/api/*` 的 404 必须仍是 JSON**，不得被 SPA 兜底吞成 `index.html`——
   否则前端拿到一坨 HTML 去 `JSON.parse`，报错信息会指向"解析失败"而不是"接口不存在"。
2. **前端路由不产生后端端点**：`/welcome`（R9）、`/guides` 与 `/guides/:key`（R12）
   都是纯前端 history 路由，靠这条兜底生效。所以它们不出现在 §1 的 39 条里。
3. **两种根路径形态都要有测试锁住**：`test_health.py` 覆盖"有 dist / 无 dist"两态
   与 `/api/*` 的 404 保持 JSON。

## 11. R12 新增业务态码登记

### 11.1 `2011 GUIDE_NOT_FOUND`（HTTP 404）

| 项 | 内容 |
| --- | --- |
| 触发 | `GET /guides/items/{key}` 的 `key` 不在 `GUIDE_ITEMS` 编目里 |
| 为什么不用 `2002 DOCUMENT_NOT_FOUND` | **两者的处理动作完全不同**。文档不存在 → 用户该去知识库确认"文件传了没有"；事项不存在 → 文件可能好好的，只是**这条编目没有**（写错 key、或该事项已下线）。报"文档不存在"会把用户引去知识库翻一份其实存在的政策，然后在那里更加困惑 |
| 为什么不用 `1001 INVALID_PARAM` | `key` 是路径段不是参数，且它是一个**枚举值集合**（编目里的 32 个 key）。参数格式错是"这段填错了"，事项不存在是"这个条目没有" |
| 前端契约 | `GuideDetailView` 收到 `2011` 显示"该事项可能已下线"，并给一个回 `/guides` 的按钮——**不弹 toast**，因为这是一次导航失败，不是一个可以忽略的提示 |

### 11.2 为什么三条接口都不需要新的业务态码

`GET /guides` 与 `GET /guides/items` 的失败面只有两种：未登录 `3001`、
分类参数不认识 `1001`。两者都是既有码。

`availability` 的三种取值（`ok` / `missing_policy` / `no_text`）**刻意做成 `data` 里的字段
而不是错误码**：它们不是"请求失败"，是"这一条确实没有依据"——
用错误码表达会让"知识库还没收录"看起来像"系统出错了"，而这恰恰是 R12 最想避免的观感。
