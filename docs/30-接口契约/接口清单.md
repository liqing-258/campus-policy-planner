## 2. 关键接口入参 / 出参

### 2.1 `GET /health`

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "status": "ok",
    "version": "0.3.0",
    "env": "dev",
    "db": "ok",
    "llm_mode": "degraded",
    "llm_model": null,
    "embedding_mode": "disabled",
    "document_count": 4,
    "chunk_count": 10
  },
  "request_id": "01M6X47D9YJ61T025SAE4YCDA1",
  "timestamp": "2026-11-08T08:26:01Z"
}
```

> 上面是 M3 实测响应（2026-11-08），非示意。相比 V1.0 多了 `env`、`document_count` 两项——M3 需要一眼看出知识库里有多少文件和片段。
>
> `llm_mode ∈ {llm, degraded}`；`embedding_mode ∈ {vector, bm25_only, disabled}`。评审一条命令即可看到系统真实能力状态。

### 2.2 `POST /auth/login`

| 入参 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| username | string | 是 | 1–64 |
| password | string | 是 | 1–72 |

出参 `data`：`{ "token": "...", "expires_in": 43200, "user": { "id", "username", "display_name", "role" } }`

### 2.3 `POST /documents`

| 入参（form-data） | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| file | file | 是 | ≤20MB；扩展名 pdf/docx/txt/md；魔数校验 |
| title | string | 否 | 缺省取文件名去扩展名 |
| department | string | 否 | ≤100 |
| published_at | date | 否 | `YYYY-MM-DD` |
| academic_year | string | 否 | 形如 `2026-2027` |
| effective_status | string | 否 | 缺省 `unknown` |

出参 `data`：`{ "id", "title", "parse_status", "chunk_count", "parse_error", "parse_hint", ... }`

**M3 实现说明（与 V1.0 的偏差，见 §6.1）**：解析在请求内**同步完成**，返回时 `parse_status` 已是终态
（`indexed` / `empty` / `failed`），前端不需要轮询。

- 失败 → `parse_status="failed"`，原因在 `parse_error`；
- 空文本 / 扫描件 → `parse_status="empty"`，可读提示在 `parse_hint`（**同一数据列，按状态选语义化字段名**，前端不必判空两次）；
- 成功 → 两者均为 `null`。

M3 实测四种情形：

| 输入 | HTTP | code | parse_status | 关键字段 |
| --- | --- | --- | --- | --- |
| 正常 PDF（4 页，含章节） | 201 | 0 | `indexed` | `chunk_count=4` |
| 正常 DOCX | 201 | 0 | `indexed` | — |
| 扫描件 PDF（无文本层） | 201 | 0 | `empty` | `parse_hint`="共 1 页，仅提取到 0 个字符（平均每页 0.0 字），疑似扫描件。本系统不含 OCR，请上传带文本层的 PDF 或手工录入。" |
| 空文本 TXT | 201 | 0 | `empty` | `parse_hint`="仅提取到 0 个字符，低于有效阈值 50。" |
| 扩展名 .pdf 但内容是 MZ 头 | 415 | 1005 | —（不落盘） | 魔数校验在写盘前拦截 |

### 2.4 `POST /qa/ask`

| 入参 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| question | string | 是 | 2–500 字 |
| conversation_id | string \| null | 否 | 传则续接会话 |
| document_ids | array[string] | 否 | 限定检索范围 |
| top_k | int | 否 | 1–12，缺省 6 |
| include_trace | bool | 否 | 缺省 true |

出参见设计说明书 §6.3（含 `answer`、`citations`、`workflow`、`mode`、`suggestions`）。

**三条硬约束**（写入测试用例）：

1. `citations[].chunk_id` 必须属于本次检索结果，否则该条被剔除并记 `4003`；
2. 拒答时 `citations` 必须为空数组，`answer.direct_answer` 含"未找到足够依据"；
3. 降级时 `mode != "llm"`，前端必须显示降级标识。

### 2.5 `POST /matches`

| 入参 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| document_id | string | 是 | |
| profile | object | 是 | 键必须在 `field_key` 白名单内；`extra='forbid'` |

出参 `data`：`{ "session_id", "summary": {met,not_met,unknown,total}, "items": [...], "disclaimer" }`

`items[]` 字段：`rule_id`、`rule_code`、`description`、`status`、`unknown_reason`、`user_value`、`expected_value`、`rationale`、`evidence{chunk_id,page,quote}`。

### 2.6 `POST /plans/draft` → `POST /plans/{id}/confirm`

`draft` 入参：`{ "match_session_id": "...", "document_id": "..." }`，出参返回**未落库**的草稿（含临时 ID `T1..Tn`）。

`confirm` 入参：

```json
{
  "action_plan_id": "01JCV...P1",
  "tasks": [
    { "temp_id": "T1", "title": "下载并填写申请表", "priority": "P0", "due_at": null, "dependency_ids": [] },
    { "temp_id": "T2", "title": "到教务办开具成绩单", "priority": "P1", "due_at": "2026-09-25T09:00:00Z", "dependency_ids": ["T1"] }
  ]
}
```

校验：`tasks` 非空且 ≤50；`title` 1–100；`due_at` 若存在须晚于当前时间；`dependency_ids` 均存在于本次 `temp_id` 集合；依赖无环；`priority ∈ {P0,P1,P2,P3}`。

### 2.7 `POST /tasks/{id}/status`

| 入参 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| status | string | 是 | todo/doing/done/deferred/cancelled |

非法转移 → `2005`，`message` 形如：`当前状态 done 不允许转移到 doing（允许：todo）`。

## 6. M3 实现偏差登记

契约一旦冻结就应尽量不改。实现时若必须偏离，**在这里登记，而不是回头偷改 V1.0 的措辞**。

### 6.1 异步解析改为同步解析

| 项 | 契约 V1.0 | M3 实现 | 为什么 |
| --- | --- | --- | --- |
| `POST /documents` 返回时机 | 立即返回 `parse_status=uploaded`，后台解析，前端轮询 | 请求内完成解析，返回终态 | 单机 + 单 worker 部署下，异步只会**增加**状态种类而不减少等待；轮询还得前端配合，M5 才有界面。同步实现让 M3 的 7 条边界用例可以在一行断言里验完 |
| 影响面 | 前端轮询逻辑 | 前端无需轮询 | 若 M7 压测暴露出大文件阻塞（>20 MB / >200 页），再改回异步；届时同步保留为 `?sync=true` 兼容 |

**代价如实记录**：同步解析意味着上传 20 MB PDF 时请求会挂住（实测 4 页 PDF 约 0.3 s，未测大文件）。
`POST /documents` 因此**不适合被前端直连公网**，M6 部署时需在 Nginx 上调大 `proxy_read_timeout`。

### 6.2 `parse_hint` 字段为新增

契约 V1.0 只有 `parse_error`。实现时发现两种语义必须分开：**失败**（文件坏了/加密）与**没有可用文本**（扫描件/空白）
给用户的指引完全不同，混在一个字段里前端只能靠 `parse_status` 猜。故在 `empty` 状态下把提示放到 `parse_hint`。
后端仍存同一列（`documents.parse_error`），只是序列化时按状态换字段名。

### 6.3 `GET /chunks/{id}` 的定位字段

契约 V1.0 只写"单片段 + 上下文 + 定位"，没定字段名。M3 实现如下（`app/documents.py:_chunk_payload`）：

```json
{
  "id", "document_id", "document_title", "chunk_index", "content",
  "char_start", "char_end", "page_number", "section_title", "token_count",
  "document": { "id", "title", "file_name", "effective_status" },
  "context": [ { "chunk_index", "page_number", "section_title", "preview" } ]
}
```

- `char_start` / `char_end` 是片段在**整篇纯文本**中的字符区间，前端可用它做原文高亮——这是引用可追溯的底层能力，M4 直接复用；
- `context` 返回前后各一个片段的**摘要（前 80 字）**，不返回完整正文。理由：完整正文会与 `content` 重复传输三倍数据，而阅读上下文本来就要整篇看，M5 政策详情页会整篇加载。摘要只用于"这条片段前后还有内容"的提示；
- `token_count` 是按中文 1 字 ≈ 1 token 粗估的用量参考，**不是分词器真实计数**，只用于估算上下文预算。

### 6.4 检索接口未随 M3 交付

`POST /retrieval/search`（#11）仍是 M4。M3 的检索能力只通过 `tools/rebuild_index.py --probe` 暴露——
不给前端开口子的原因很直接：**没有覆盖率的检索接口会诱导用户把"召回了 3 条"误读成"答案有依据"**，
而这正是 M4 要解决的事。宁可晚一个里程碑，也不先放一个会误导的口子。

### 6.5 M3 顺带补的两处契约外行为

| 行为 | 说明 | 是否会影响前端 |
| --- | --- | --- |
| SHA-256 去重 | 同一文件重复上传返回 **409 / 2001**，`message` 里带上已存在文档的**标题**。去重只看未删除的文档，软删除后重新上传同一文件是允许的（等价于"恢复"） | 会。前端需提示"该文件已在库中" |
| 软删除后重建索引 | `DELETE` 后立即从内存索引移除该文档的全部片段 | 不会，纯后端一致性 |

> **已知不便利**：409 的响应体里**没有**已存在文档的 `id`——统一外壳在错误分支固定 `data: null`，
> M3 没有为此改动外壳（改外壳的影响面远大于收益）。M5 做上传页时，前端只能按标题去列表里找。
> 若届时体验不可接受，再单独评估"错误分支允许携带 `data`"，而不是现在顺手改契约。
