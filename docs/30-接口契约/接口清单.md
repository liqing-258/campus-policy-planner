## 2. 关键接口入参 / 出参

### 2.1 `GET /health`

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "status": "ok",
    "version": "0.3.0",
    "env": "dev",
    "db": "ok",
    "llm_mode": "degraded",
    "llm_model": null,
    "embedding_mode": "disabled",
    "document_count": 4,
    "chunk_count": 10
  },
  "request_id": "01M6X47D9YJ61T025SAE4YCDA1",
  "timestamp": "2026-11-08T08:26:01Z"
}
```

> 上面是 M3 实测响应（2026-11-08），非示意。相比 V1.0 多了 `env`、`document_count` 两项——M3 需要一眼看出知识库里有多少文件和片段。
>
> `llm_mode ∈ {llm, degraded}`；`embedding_mode ∈ {vector, bm25_only, disabled}`。评审一条命令即可看到系统真实能力状态。
>
> **R1 现状（2026-11-12）**：`version="0.7.0"`、`llm_mode="llm"`、`llm_model="deepseek-flash"`、
> `embedding_mode="bm25_only"`、`document_count=18`、`chunk_count=74`。
> （M6 时为 5 / 14；修复轮 R1 把知识库扩到 18 份文档，接口字段与语义未变，
> 只是这两个计数按真实库返回。）
> **R2 现状（2026-11-12）**：同一接口、同一字段，计数变为 `document_count=18`、`chunk_count=122`
> （15 份 PDF 各追加 2–3 章，见 `docs/90-AI协作留痕/11-知识库可见性与内容补齐.md` §O.5.5）。
> 接口签名**一条没动**——本轮改的是页面挂载逻辑与演示语料。
> M5 那一版记的是 `deepseek-v4.1-flash`——**这个名字在服务端不存在**，是任务书给的；
> 实际可用的是 `deepseek-flash` / `deepseek-v4-pro`。文档照抄任务书是错的，照抄 `/health` 才对。
> 上面那份 M3 响应保留原样，是为了让"字段随里程碑增长"这件事本身可追溯。
> **规则数不在 health 里**（`GET /health` 只统计文档与片段），要看规则数用 `GET /documents/{id}/rules`。
> **R6 新增 `llm_config`（2026-11-14）**：降级时最需要回答的不是"降级了"，而是"缺什么、找过哪里"。
> 实测响应（把 exe 放在 `dist/`、密钥在项目根时）：
>
> ```json
> "llm_config": {
>   "configured": true,
>   "api_key": "set",
>   "model": "deepseek-flash",
>   "base_url": "set",
>   "missing": [],
>   "env_files": [
>     {"path": "D:////私人////学习////传智杯////dist////.env", "found": false},
>     {"path": "D:////私人////学习////传智杯////.env", "found": true},
>     {"path": "C:////Users////...////_MEI00000d942////.env", "found": false}
>   ]
> }
> ```
>
> 三条硬规则：①**永不回传密钥值**，`api_key` 只有 `set`/`missing`，连长度都不给（长度能用于验证猜测）；
> ②`missing` 列出具体变量名，让"没配"与"配了没读到"能分开；③`env_files` 是**找过的位置**而不是"应该放的位置"——
> 用户看到项目根那行是 `found: true` 却仍降级，才该去查变量名拼写，而不是继续怀疑路径。
> 该字段只增不改，旧前端忽略它不影响任何既有行为。

### 2.2 `POST /auth/login`

| 入参 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| username | string | 是 | 1–64 |
| password | string | 是 | 1–72 |

出参 `data`：`{ "token": "...", "expires_in": 43200, "user": { "id", "username", "display_name", "role" } }`

### 2.3 `POST /documents`

| 入参（form-data） | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| file | file | 是 | ≤20MB；扩展名 pdf/docx/txt/md；魔数校验 |
| title | string | 否 | 缺省取文件名去扩展名 |
| department | string | 否 | ≤100 |
| published_at | date | 否 | `YYYY-MM-DD` |
| academic_year | string | 否 | 形如 `2026-2027` |
| effective_status | string | 否 | 缺省 `unknown` |

出参 `data`：`{ "id", "title", "parse_status", "chunk_count", "parse_error", "parse_hint", ... }`

**M3 实现说明（与 V1.0 的偏差，见 §6.1）**：解析在请求内**同步完成**，返回时 `parse_status` 已是终态
（`indexed` / `empty` / `failed`），前端不需要轮询。

- 失败 → `parse_status="failed"`，原因在 `parse_error`；
- 空文本 / 扫描件 → `parse_status="empty"`，可读提示在 `parse_hint`（**同一数据列，按状态选语义化字段名**，前端不必判空两次）；
- 成功 → 两者均为 `null`。

M3 实测四种情形：

| 输入 | HTTP | code | parse_status | 关键字段 |
| --- | --- | --- | --- | --- |
| 正常 PDF（4 页，含章节） | 201 | 0 | `indexed` | `chunk_count=4` |
| 正常 DOCX | 201 | 0 | `indexed` | — |
| 扫描件 PDF（无文本层） | 201 | 0 | `empty` | `parse_hint`="共 1 页，仅提取到 0 个字符（平均每页 0.0 字），疑似扫描件。本系统不含 OCR，请上传带文本层的 PDF 或手工录入。" |
| 空文本 TXT | 201 | 0 | `empty` | `parse_hint`="仅提取到 0 个字符，低于有效阈值 50。" |
| 扩展名 .pdf 但内容是 MZ 头 | 415 | 1005 | —（不落盘） | 魔数校验在写盘前拦截 |

### 2.5 `POST /documents/{id}/rules/extract`

V1.0 只写了"触发规则抽取"。实际实现如下（`app/rules.py:extract`）：

| 入参 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| chunk_ids | array[string] | 否 | 只抽指定片段；缺省抽全文 |
| max_rules_per_chunk | int | 否 | 1–20，缺省 8。**按片段限量，不是全篇限量** |

出参：

```json
{
  "document_id": "01J...", "mode": "llm", "model": "deepseek-flash",
  "chunks": 4, "extracted": 20, "stored": 20,
  "dropped": [ { "rule_code": "R-9", "reason": "original_quote 不是该片段的子串" } ],
  "rules": [ { "id", "rule_code", "rule_type", "field_key", "operator",
               "expected_value", "original_quote", "quote_verified": true,
               "extraction_status": "suggested", "review_status": "needs_review",
               "confidence": 0.86 } ]
}
```

**四个契约闸门**（逐条校验，不合法**只丢单条**，不整批失败）：

| 闸门 | 不合法时 | 为什么是丢弃而不是报错 |
| --- | --- | --- |
| `original_quote` 必须是所在片段原文子串 | `dropped` 里记 `original_quote 不是该片段的子串` | 一条引用造假不该让另外 19 条正确规则一起作废 |
| `operator` 必须在 8 算子 + `manual_review` 白名单 | 记 `未知算子` | 同上 |
| `field_key` 必须在 `PROFILE_FIELDS` 九字段白名单 | 记 `field_key 不在画像白名单` | 画像没有的字段无法求值，留着只会让匹配静默跳过 |
| `chunk_index` 不得越界 | 记 `片段序号越界` | 越界说明模型在编片段 |

抽取结果**一律** `review_status="needs_review"`、`extraction_status="suggested"`，**不参与匹配**。
降级模式（无 Key）→ `4006`，`data.note` 明说"规则抽取必须调模型"。

### 2.6 `GET /documents/{id}/rules` 与 `PATCH /rules/{id}`

`GET` 支持 `review_status`（`needs_review` / `approved` / `rejected`）、`rule_type` 过滤，分页 `Paged<Rule>`。

`PATCH` 可改：`description`、`field_key`、`operator`、`expected_value`、`rule_type`、`target_group`、`review_status`。

**复核为 `approved` 时的强校验**（`1003`）：

```text
条件类规则（eligibility / threshold / ...）必须补齐 operator
除 manual_review 外，operator 必须配 expected_value
```

理由：没有算子的条件规则**无法参与匹配**，若允许"通过"，用户会以为这条规则生效了，
而实际上它在匹配时被静默跳过——这比拒绝通过更糟。

### 2.9 `GET /plans`、`PATCH /plans/{id}`、`GET|POST /tasks`、`PATCH /tasks/{id}`、`POST /tasks/{id}/status`

`GET /plans`：`Paged<Plan>`，支持 `status` 过滤；每项带 `task_count` 与 `progress`（`done / total`）。

`PATCH /plans/{id}`：可改 `title`、`status`（仅 `archived`）。**不允许经此接口把状态改成 `confirmed`**，
确认只能走 `/plans/{id}/confirm`——否则"确认"这个动作就没有唯一入口，审计链断掉。非法转移 → `2005`。

`GET /tasks`：支持 `status`、`plan_id`、`priority` 过滤；`Paged<Task>`。

`POST /tasks`：手工新增待办。**必须有 `plan_id` 且该计划属于自己**（`2004`），
理由：任务中心的任务必须能挂到一个计划上，否则"这个待办是从哪来的"无从回答。

`PATCH /tasks/{id}`：改 `title`/`description`/`priority`/`due_at`/`status`（后者走状态机校验）。

`POST /tasks/{id}/status`：

| 入参 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| status | string | 是 | todo/doing/done/deferred/cancelled |

转移白名单（`shared/enums.py:TASK_TRANSITIONS`）：

| 当前 | 允许转移到 |
| --- | --- |
| `todo` | doing / done / deferred / cancelled |
| `doing` | done / deferred / cancelled |
| `done` | **仅 todo**（撤销完成） |
| `deferred` | todo / doing / cancelled |
| `cancelled` | **仅 todo**（重新启用） |

`done → doing` 被**刻意禁止**：允许它会让 `completed_at` 变得无法解释
（先是 `done` 写了完成时间，再回 `doing` 时这个时间算什么？）。要重做就回 `todo`，语义干净。

非法转移 → 409 / `2005`，`message` 形如：`当前状态 done 不允许转移到 doing（允许：todo）`。
同状态重复提交 → 幂等成功（200，不重复写 `completed_at`）。

### 2.10 R9 新增四条（注册链路 + 管理员数据看板）

这一小节是**唯一一次整块新增**，前九个小节都是 M2–M6 的既有契约。四条分两组：
前两条给"登录小窗里的注册页"，后两条给"管理员数据中心"。

#### #32 `GET /auth/captcha` —— 公开

无入参。出参 `data`：

```json
{
  "captcha_id": "9Xk2mQ…",          // token_urlsafe(16)，服务端唯一凭据
  "image": "data:image/svg+xml;base64,PHN2Zy…",
  "expires_in": 180,
  "length": 4
}
```

三条硬约束，都是"能被绕过就不算防护"逼出来的：

1. **不回明文**。明文只存在服务端进程内的字典里。这不是洁癖：验证码的唯一价值是
   "人能看、机器难认"，一旦明文随响应下发，`curl` 一次就白拿了。
2. **一码一用，错了也销毁**。`verify()` 第一句就是 `_STORE.pop()`，成功失败都移除。
   留着重试等于把 4 位数字（1 万种）的穷举成本从 1 次降到 N 次。
3. **图片是真文字**。SVG 里的数字是 `<text>` 而不是路径曲线——拿文本编辑器就能读出答案。
   这是**已知限制 C-14**，明确登记，不假装做到了抗 OCR（那要换扭曲位图，是另一个量级）。

#### #33 `POST /auth/register` —— 公开

| 入参 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| display_name | string | 是 | 2–20，去空白后不得为空 |
| student_no | string | 是 | 4–20，仅数字字母 |
| password | string \| null | 否 | 6–72；留空则用「学号后 6 位」 |
| captcha_id | string | 是 | 8–64（来自 #32） |
| captcha_code | string | 是 | 恰好 4 位数字 |

出参 `data`：`{ "token", "expires_in", "user": { "id", "username", "display_name", "role" } , "password_source", "initial_password" }`

- `password_source` 只有两个值：`custom`（用户自己填了）/ `student_no_suffix`（用了默认口令）。
- `initial_password` 在 `custom` 时为 `null`，否则**原样回显身份证件意义上的那个口令**。
  这不是泄露——它就是学号后 6 位，用户本来就有；藏着不说才会让他第二次登录不进去。

**为什么学号即 `username`**：`users` 表没有 `student_no` 列，而本项目用 `create_all()` 建表，
老库不会被自动改结构。加一列就要写迁移、就要考虑"已经注册的人这一列是什么"，
为一个字段引入一整套迁移机制不划算。学号在业务上本来就唯一，直接当 `username`。

**为什么先验验证码再查库**：顺序反过来的话，`"该学号已注册"` 这个响应就变成了
一个**不用过验证码的学号枚举接口**——攻击者能免费问"某某学号在不在"。
现在的顺序是：限流 → 校验参数 → 验验证码（失败即 1006，码作废）→ 查重 → 落库。

**频率限制**：按月限流的一半、最低 3 次/分钟（复用 `LOGIN_RATE_LIMIT_PER_MINUTE`）。
这是全仓第二个公开 POST，不设闸的话注册页就是个现成的请求放大器。

#### #34 `GET /admin/analytics/portraits` —— 仅 A

无入参。数据源是 `match_sessions`（学生在资格匹配页点「开始匹配」时落库的那一行，
`profile_json` 是当时的完整画像快照）——**不另建画像表**。

`data.summary` 关键字段：

| 字段 | 口径 |
| --- | --- |
| `session_count` / `student_count` / `document_count` | 去重计数 |
| `recent_7d` | 近 7 天画像条数 |
| `met` / `not_met` / `unknown` / `judged` | 三态计数，`judged` = 三者之和 |
| `met_rate` | `met / judged`，**`judged = 0` 时为 `null`，不是 0** |
| `avg_completeness` | 已填字段数 ÷ 9（9 个画像字段）后取均值 |
| `by_student_type` | 归并成 专科 / 本科 / 研究生 / 其他 四类 |
| `raw_student_types` | 归并前的原始写法，供核对 |
| `truncated` | 是否触到 `MAX_ROWS = 2000` |

`data.items[]` 每条 12 个字段，按 `created_at` 倒序，逐条对应学生端的一次匹配。

两处必须解释的口径：

- **`met_rate` 空库返回 `null` 而不是 0**：0 是"评估了，一条都不符合"，`null` 是"还没人评估"。
  两者在页面上要显示成不同的东西（`—` vs `0%`），在 API 层就不能合并。
- **`by_student_type` 必须归并，`raw_student_types` 必须保留**：库里历史写法至少有
  `full_time_undergraduate`、`全日制在校本科生（具有本校正式学籍）` 这种。直接 group by
  会得到一张八瓣饼图——每瓣 1 个人。归并到四类图才读得懂，但归并规则是**有损**的，
  所以原始写法另存一份，出问题时能看到"到底哪几种写法被归到了这里"。

#### #35 `GET /admin/analytics/qa` —— 仅 A

无入参。数据源是 `messages` 里 `role='user'` 的正文，配 `conversations` 找归属人。

`data` 结构：

| 字段 | 说明 |
| --- | --- |
| `summary.question_count` / `asker_count` / `conversation_count` | 条数 / 去重人数 / 会话数 |
| `summary.keyword_count` | 词云实际词数（`count >= 2` 过滤后） |
| `summary.peak_hour` | 24 小时里最忙的那个钟点；无数据为 `null` |
| `keywords[]` | `{ "word", "count" }`，供 SVG 词云 |
| `topics[]` | `{ "key", "label", "count", "share", "examples" }`，主题偏好图 |
| `hours[]` | 定长 24 项 `{ "hour", "count" }`，**已补零** |
| `weekdays[]` | 7 项 `{ "label", "count" }` |
| `top_askers[]` | 最多 6 项 `{ "name", "count" }` |

四处设计决定，每一处都有"换一种做法就出错"的具体理由：

1. **时区先 +8 再分桶**。库里的 `created_at` 是 naive UTC（`utcnow()` 写的）。
   直接按 UTC 分桶，21 点问的问题会落到 13 点——"晚上问得多"被系统性误判成"下午问得多"。
   面向国内高校，偏移量写死 UTC+8；真要多时区得从用户资料取，那是另一件事。
2. **关键词只留 `count >= 2`**。出现一次的词字号小到看不清，悬停只能回"出现 1 次"，
   纯噪声。这条阈值顺带挡掉 jieba 切出来的半截词（`对绩`、`几本`）——那些几乎都只出现一次。
3. **主题分类用规则不用模型**。看板要的是"同一批数据每次刷新给同样的图"，
   模型分类做不到这点。`TOPIC_RULES` 是 6 组关键词 + 一个"其他事务"兜底；
   多主题命中时取**命中词总长度最长**的那一组，避免"奖学金申请要什么材料"被"申请"拽去别的类。
   代价是 17 条问题落进"其他"，这个数字如实出现在图上，不硬凑。
4. **`hours` 定长 24 且补零**。让前端画图不用自己补空档，也避免"没有提问的时段"
   被压缩成一条直线——那会让深夜看起来和傍晚一样热闹。

## 6. M3 实现偏差登记

契约一旦冻结就应尽量不改。实现时若必须偏离，**在这里登记，而不是回头偷改 V1.0 的措辞**。

### 6.1 异步解析改为同步解析

| 项 | 契约 V1.0 | M3 实现 | 为什么 |
| --- | --- | --- | --- |
| `POST /documents` 返回时机 | 立即返回 `parse_status=uploaded`，后台解析，前端轮询 | 请求内完成解析，返回终态 | 单机 + 单 worker 部署下，异步只会**增加**状态种类而不减少等待；轮询还得前端配合，M5 才有界面。同步实现让 M3 的 7 条边界用例可以在一行断言里验完 |
| 影响面 | 前端轮询逻辑 | 前端无需轮询 | 若 M7 压测暴露出大文件阻塞（>20 MB / >200 页），再改回异步；届时同步保留为 `?sync=true` 兼容 |

**代价如实记录**：同步解析意味着上传 20 MB PDF 时请求会挂住（实测 4 页 PDF 约 0.3 s，未测大文件）。
`POST /documents` 因此**不适合被前端直连公网**，M6 部署时需在 Nginx 上调大 `proxy_read_timeout`。

### 6.2 `parse_hint` 字段为新增

契约 V1.0 只有 `parse_error`。实现时发现两种语义必须分开：**失败**（文件坏了/加密）与**没有可用文本**（扫描件/空白）
给用户的指引完全不同，混在一个字段里前端只能靠 `parse_status` 猜。故在 `empty` 状态下把提示放到 `parse_hint`。
后端仍存同一列（`documents.parse_error`），只是序列化时按状态换字段名。

### 6.3 `GET /chunks/{id}` 的定位字段

契约 V1.0 只写"单片段 + 上下文 + 定位"，没定字段名。M3 实现如下（`app/documents.py:_chunk_payload`）：

```json
{
  "id", "document_id", "document_title", "chunk_index", "content",
  "char_start", "char_end", "page_number", "section_title", "token_count",
  "document": { "id", "title", "file_name", "effective_status" },
  "context": [ { "chunk_index", "page_number", "section_title", "preview" } ]
}
```

- `char_start` / `char_end` 是片段在**整篇纯文本**中的字符区间，前端可用它做原文高亮——这是引用可追溯的底层能力，M4 直接复用；
- `context` 返回前后各一个片段的**摘要（前 80 字）**，不返回完整正文。理由：完整正文会与 `content` 重复传输三倍数据，而阅读上下文本来就要整篇看，M5 政策详情页会整篇加载。摘要只用于"这条片段前后还有内容"的提示；
- `token_count` 是按中文 1 字 ≈ 1 token 粗估的用量参考，**不是分词器真实计数**，只用于估算上下文预算。

### 6.4 检索接口未随 M3 交付

`POST /retrieval/search`（#11）仍是 M4。M3 的检索能力只通过 `tools/rebuild_index.py --probe` 暴露——
不给前端开口子的原因很直接：**没有覆盖率的检索接口会诱导用户把"召回了 3 条"误读成"答案有依据"**，
而这正是 M4 要解决的事。宁可晚一个里程碑，也不先放一个会误导的口子。

### 6.5 M3 顺带补的两处契约外行为

| 行为 | 说明 | 是否会影响前端 |
| --- | --- | --- |
| SHA-256 去重 | 同一文件重复上传返回 **409 / 2001**，`message` 里带上已存在文档的**标题**。去重只看未删除的文档，软删除后重新上传同一文件是允许的（等价于"恢复"） | 会。前端需提示"该文件已在库中" |
| 软删除后重建索引 | `DELETE` 后立即从内存索引移除该文档的全部片段 | 不会，纯后端一致性 |

> **已知不便利**：409 的响应体里**没有**已存在文档的 `id`——统一外壳在错误分支固定 `data: null`，
> M3 没有为此改动外壳（改外壳的影响面远大于收益）。M5 做上传页时，前端只能按标题去列表里找。
> 若届时体验不可接受，再单独评估"错误分支允许携带 `data`"，而不是现在顺手改契约。

## 7. M4 实现偏差登记

M4 交付 #11–#14 四条接口。与 V1.0 冻结契约有 5 处偏差，逐条给出理由与影响面。

### 7.1 业务态码开始携带 `data`（外壳的一次能力扩展）

**契约原文**：`接口契约统一规范.md §3.3` 只规定"4001/4003/4006 返回 HTTP 200"，未规定响应体形状；
V1.0 时期 `fail()` 固定输出 `data: null`。

**实际实现**：`ApiError` 增加 `payload` 字段，`fail()` 增加 `data` 参数，业务态码携带结构化数据。

**为什么必须改**：拒答时如果只回一句"证据不足"，用户无法判断是**库里真没有**还是**阈值把自己要的文件滤掉了**。
两者的处置动作完全不同（上传文件 vs 调整提问方式），而用户看到的提示一模一样——这等于把排查成本全推给用户。
现在拒答响应带上 `retrieval`（本次检索统计）、`rejected_candidates`（被覆盖率闸门拦下的片段）、
`suggestions`（可执行的下一步），用户能自己判断。

**影响面**：
- 前端：需要按 `code ∈ {4001,4003,4006}` 渲染"提示卡"而非"错误弹窗"，卡片里可以展示候选片段；
- 非业务态错误（1001/3001/500 等）`data` 仍为 `null`，不受影响；
- §6.5 提到的"409 去重响应没有 `id`"这个问题**现在有解了**，但 M4 没有回头改（见 §7.3 第 5 条）。

### 7.2 `POST /retrieval/search` 从"调试接口"变成"可被前端调用"

M3 时这个接口**故意没有实现**，理由记录在 §6.4："没有覆盖率的检索接口会诱导用户把'召回了 3 条'误读成'答案有依据'"。

M4 补上了覆盖率与拒答判定，这个顾虑消除：响应里 `coverage`、`refused`、`refuse_reason` 都是显式字段，
前端不可能把"3 条候选"直接当成答案展示。因此接口开放，但仍**只返回片段与分数，不生成答案**。

### 7.3 逐项偏差清单

| --- | --- | --- | --- | --- |

## 8. M5 实现偏差登记

M5 交付 #16–#28 十三条接口。与 V1.0 冻结契约有 6 处偏差，逐条给出理由与影响面。

### 8.1 新增业务态码 `2008 RULES_NOT_READY`

**契约原文**：V1.0 把"文档下没有可用条件规则"归到 `1003 参数非法`。

**实际实现**：新增 `2008`（`RULES_NOT_READY`），加入 `BUSINESS_STATE_CODES`，**返回 HTTP 200**。

**为什么必须改**：这不是用户填错了参数，而是**系统当前没有可用的规则**——
用户什么都没做错，重试同样的请求也没用，正确动作是"先去抽规则/复核规则"。
若按 `1003` 返回 400，前端只能弹"参数错误"，用户会去改画像，越改越偏。

**影响面**：前端需按 `code=2008` 渲染"引导去抽规则"的提示卡。已在 `frontend/src/api/client.ts`
的 `BIZ_CODES = {4001, 4003, 4006, 2008}` 里登记。

### 8.2 匹配接口不认 `target_group`（**已知缺口，未修复**）

**契约现状**：`POST /matches` 只按 `document_id` 取该文档下全部已复核条件规则。

**问题**：同一份文件里常有多类条件（`R-4` 励志 gpa≥3.0 / `R-8` 优秀学生 gpa≥3.5），
两条都参与求值时，gpa 3.2 申请励志的学生会被 `R-8` 判"不符合"——**结果里会出现一条与他无关的不符合项**。

**本轮处置**：复核阶段拒绝无关规则（`tools/review_demo_rules.py` 的 `REJECT` 字典里逐条写明理由，
如"校级优秀学生奖学金的条件（gpa≥3.5），不适用于励志奖学金场景"）。

**这是绕过，不是修复**。正解是给 `POST /matches` 加 `target_group` 过滤参数、并在画像里带上申请目标。
排在 M6，理由：改入参要同步改前端表单与已冻结的契约，M5 已用复核期剔除把演示链路跑通，
贸然在结项前动入参会把稳的东西弄不稳。登记在此，不假装解决。

### 8.3 草稿回传 `note` 与溯源字段（新增，未违反契约）

V1.0 的 `confirm` 入参只有 `temp_id/title/priority/due_at/dependency_ids`。
实际新增四个字段：`source_rule_code`、`due_source`、`note`、`needs_human_confirmation`。

原因：这些信息是 `draft` 阶段算出来的**唯一来源**，`confirm` 若不回传，落库后就永久丢失
（"为什么这条任务的截止日期是空的"没有答案）。契约原本没禁止加字段，但**前端必须回传**，
否则表现为"任务建好了，提示语没了"。

### 8.4 `tasks` 表新增 `note` 列（`source_rule_id` 此前从未写入）

`note` 见 8.3。`source_rule_id` 是"这条任务来自哪条规则"的外键，**v1.0 数据模型里就有这一列**，
但 M5 之前从来没写过值（`confirm` 时一律 `NULL`）——等于溯源链在数据层是空的。
M5 补上了写入逻辑：按草稿回传的 `source_rule_code` 反查 `policy_rules.id` 落库，
回执里同时带人可读的 `source_rule_code`。

**部署注意**：`db.create_all()` **不会给已存在的表加列**。已有 `app.db` 的环境需手工执行
`ALTER TABLE tasks ADD COLUMN note VARCHAR(500);`（只需补这一列），或 `init_db --drop` 重建。

### 8.5 `GET /plans` 无单条详情接口

V1.0 列了 `GET /plans` 与 `PATCH /plans/{id}`，但没列 `GET /plans/{id}`。
实际实现也没加：前端计划列表已带 `task_count` 与 `progress`，任务通过 `GET /tasks?plan_id=` 取，
不需要"再取一次计划本身"。**这是有意不加**，不是漏了——加一条只返回 6 个字段的接口没有使用者。

### 8.6 `POST /tasks` 必须带 `plan_id`

V1.0 写的是"手工新增任务"，未规定归属。实际实现强制要求 `plan_id` 且必须是自己的计划（否则 `2004`）。

原因：任务中心里每一条任务都要能回答"属于哪个计划"。允许孤立任务，
就等于允许一堆无法解释来源的待办混进列表，进度条也会算不准。

### 8.8 依赖成环的 HTTP 状态：设计 422 → 实现 409

设计说明书 §11.2 的 T-17 写"依赖成环 → **422**，指出环"。
实现里 `DEPENDENCY_CYCLE(2006)` 映射到 **409**（`shared/codes.py:CODE_HTTP`）。

理由：成环时**资源当前状态冲突**（同一批任务互相依赖，无法确定顺序），语义上是 409 Conflict；
而 422 在本项目已分配给 `SCHEMA_INVALID(1003)`（请求体结构不合法），
若两者都用 422，前端无法区分"字段写错了"与"依赖关系本身不成立"。

**代价**：与冻结设计不一致。已在本表 §8.7 的 T-17 行标注偏差，是否回改留 M6 决定
（回改要同步改前端与 6 处断言，收益只是"与文档一致"）。

复跑命令：`.venv\Scripts\python.exe -m pytest tests/test_rules.py tests/test_matching.py tests/test_plans.py -q`（54 项）

## 9. R9 新增业务态码登记

R1–R8 九轮修复里只加过业务态码（`2008`/`2009`），**从没加过新的错误码**。
R9 因为把"注册"搬到了公开互联网上，必须加两个——它们各自承担一件别的码做不了的事。

### 9.1 `1006 CAPTCHA_INVALID`（HTTP 400）

| 项 | 内容 |
| --- | --- |
| 触发 | `captcha_id` 不存在 / 已过期（>180s）/ 已被消费 / 4 位数字不匹配 |
| 为什么不用 `1001 INVALID_PARAM` | 前端**必须据此换一张新图**。参数格式错只需在字段下画红字；验证码错必须重新拉图，因为服务端一码一用、失败即销毁。混成一个码，前端只能猜"这条 1001 是格式错还是码错" |
| 前端契约 | `AuthPanel.vue` 在收到 `1006` 时自动 `GET /auth/captcha` 刷新 `<img>`，并清空输入框 |

### 9.2 `2010 USER_DUPLICATED`（HTTP 409）

| 项 | 内容 |
| --- | --- |
| 触发 | `student_no` 已被注册 |
| 为什么不用 `2001 DOCUMENT_DUPLICATED` | 语义不同、且前端动作不同：文档重复是"换个文件"，学号重复是"**去登录**"。`AuthPanel` 据此把提示的那行字变成可点击的"去登录" |
| 额外含义 | 学号存在与否属于**隐私**。这条消息只在验证码通过之后才可能返回（见 §2.10 #33 的校验顺序），所以它不构成学号枚举通道 |

### 9.3 顺带说明：为什么注册**不做**用户名唯一性校验的独立接口

有人会想"先给个 `GET /auth/exists?student_no=xxx` 让前端实时提示"。
**明确不做**：那个接口本身就是枚举器，一个 GET 就能批量试探学号。
现在的做法是"填完表单、过验证码、提交，错了再说"——体验上多一次失败，安全性上少一个口子。
