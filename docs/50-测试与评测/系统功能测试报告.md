### 2.2 数据保护措施（实际执行）

1. **物理备份**：用 `sqlite3.Connection.backup()` 生成带时间戳备份，与直接 `cp` 不同，能保证 WAL 中未 checkpoint 的事务一并落盘。
2. **测试数据隔离**：所有写操作使用 `[R19测试]` 前缀标记；每轮脚本用 `before/after` 快照差集清理自己创建的数据，不做跨范围删除。
3. **规则类写操作双保险**：修改 `policy_rules`（R-4）时记录原值，`try/finally` 无条件恢复并回读核对。实测恢复成功：`expected_value='3.0'`、`review_status='approved'`。
4. **不碰历史业务数据**：库中 M6/R13 遗留的「准备材料 / 注意截止时间」等任务属既有数据，**未删除**（只在清理时按 `plan_id` 精确删除本轮创建的计划）。
5. **测试后基线复核**：12 张表的记录数与测试前完全一致（见第九部分回归结果）。

### 10.2 结论

1. **系统整体可交付且已修复到全绿**：7 个模块、4 条跨模块流程、全部权限与异常场景均按设计工作；

2. **核心链路是真实的，不是演示**：上传→解析→索引→检索→生成→引用全链路真实跑通（新上传政策的独有内容
   能被检索、被引用、原文可回溯到 `chunk_id`）。匹配的三态判定严格区分「不符合」与「信息不足」，
   边界值含等号，规则改动可逆地影响判定结果。
3. **AI 回答的引用可核对**：抽查的每条引用都能回库对上原文、页码、章节与文档标题，未发现编造引用。
4. **P1-01 是本轮最有价值的发现，且已修好**：系统的知识库侧明知「哪份现行有效」
   （匹配页、政策更新、日历、收藏都在用这个事实），但**问答检索侧没有消费它**，
   导致回答把 3.0 与 2.8 并列并称"无法判断"。修复后同一问题明确回答「不低于 3.0」，
   并一句话说明旧版已被替代。
   这条缺陷的特点是**所有接口都是"成功"的**——只跑 `code==0`、引用非空、工作流有节点，永远发现不了。
5. **两条"缺陷"经复核不成立（P2-02、P3-03），已撤回**。撤回原因如实写在第六部分：
   一条是只测了 API、没看前端实际下拉来源；一条是我自己的测试脚本绕过 API 直接改库，
   把"索引不同步"归咎于系统。**宁可把缺陷数从 6 改回 4，也不留假阳性。**
6. **三项观察项已在第八部分登记**（短追问易被闸门拒答、演示库无部门数据、version_label 仅 1 份），
   都不作为缺陷：前者的闸门是防幻觉核心机制，后两者的字段系统支持、是演示数据没填。
7. **降级路径已真机验证**：模型不可用与数据库异常两项，原先标"未执行"，后来用**独立端口 +
   环境变量覆盖**起临时实例补测（不动主服务），9 项页面断言全过。
   结论是**降能力不降可用性**：没有模型就给原文片段并说明原因（4006 + 9 条候选），
   没有库就明确报错（9001 + 登录窗内可读文案），都不白屏、不裸栈、不丢数据。

**本轮的方法论**（比结论本身更值得留下）：数据类断言全部从 SQLite 独立重算，不用接口自证；
引用逐条回库核对；写操作带标记 + 快照差集清理 + 规则 `try/finally` 恢复；
自己的用例写错就改判、不充数。
