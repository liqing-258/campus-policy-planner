# 链 AD · 常用政策收藏（R17）

> 功能轮 R17（2026-11-15）。新增「常用政策收藏」：政策文件 / 校园事务指南 / 重要问答 /
> 常用办理事项四类收藏 + 取消 + 类型筛选 + 关键词搜索 + 「我的收藏」页。

## AD.1 目标

| 表面上看 | 实际牵连 |
| --- | --- |
| 给政策/指南/问答加收藏按钮 | 收藏是「谁收藏了」的多对多关系，塞进目标表说不清归属——**必须独立关联表** |
| 「我的收藏」页 | 四类目标的展示字段不统一：政策有有效状态、问答有原文+来源、计划有状态 |
| 政策更新后收藏显示最新状态 | 收藏不能存状态快照，否则政策一变收藏就过期——**状态必须实时 JOIN** |
| 收藏问答保留原始回答 | 收藏只存 message_id，回答与来源实时从 messages 取，天然不丢上下文 |
| 不同账号隔离 | 收藏按 user_id 过滤；收藏问答/计划只能认本人（越权 3002） |

## AD.2 用户 Prompt 与理解

用户原话（R17 完整需求，六节 + 十二条约束 + 收尾）。我的理解落在三条硬线：

1. **「尽量采用简单的收藏关联表实现，不要改变原有政策文件和问答的数据结构」** ——
   直接决定方案：一张 `favorites` 表，`user_id + target_type + target_id` 指向既有实体，
   不改动 documents / guides / messages / action_plans 任何一张表的结构。
2. **「收藏政策后，如果原政策更新或失效，应同步显示最新有效状态」** —— 收藏表只存
   `title`（名称）与 `document_id`（关联政策）快照，`effective_status` 一律展示时实时
   JOIN 目标对象现算。快照存的是**指向**，不是**状态**。
3. **「收藏的问答应保留原始回答和来源信息」** —— 收藏 `qa` 只存 `message_id`，列表实时
   回 `messages.content` + `citations_json`，天然保留原始回答与来源，不随政策更新丢上下文。

「常用办理事项」映射到既有实体是本次唯一需要决策的歧义点：四类收藏对象里 document / guide /
qa 都有明确实体，第四类「常用办理事项」在系统里最贴近的是**事务计划**（`action_plans`，
页面标题「计划与任务」），故 `target_type=plan` 指向 `action_plans.id`，收藏入口放在计划卡片。

## AD.3 方案取舍

| 取舍点 | 选了什么 | 为什么 |
| --- | --- | --- |
| 收藏放哪张表 | 新建 `favorites` 关联表 | 收藏横跨四类实体，给四张表各加「收藏」列要改 4 张表结构；一张 `user+target` 关联表最直白 |
| 目标怎么定位 | `target_type`（四类）+ `target_id` | 指向既有实体，不复制任何目标数据 |
| 名称/关联政策 | `title` + `document_id` 快照 | 目标删除后收藏列表仍能显示名称、仍知道关联哪份政策 |
| 有效状态 | 展示时实时 JOIN，不落库 | 政策更新/失效后收藏列表同步最新状态（需求五.3） |
| 收藏问答 | 只存 `message_id`，原文+来源实时查 | 保留原始回答与来源（需求五.4） |
| 幂等 | 覆盖（同 user+target 唯一约束） | 与 qa_feedback 一致，重复收藏不刷排 |
| 取消收藏 | 幂等（不存在也返回成功） | 取消一个没收藏的东西不算错误 |
| 关键词搜索 | 拉全量后内存过滤 title/question/answer | 问答正文不在快照列，SQL 只按 title 过滤会把命中正文的收藏排掉 |
| 「常用办理事项」 | `plan`（action_plans） | 系统里「办理事项」的最贴切实体是事务计划 |

## AD.4 现场记录（本轮踩到的）

1. **关键词搜索第一次写在 SQL 层**：`Favorite.title.contains(keyword)` 把「回答正文命中关键词、
   标题快照不含」的 qa 收藏提前排掉（qa 的 title 快照是问题文本，答案里的词搜不到）。
   收藏量级小，改为拉全量（MAX_ROWS 500）后统一在内存按 title / question / answer 过滤。
2. **测试夹具里第二个学生的密码 hash 用假值**：`password_hash="pbkdf2:...$x"` 导致登录
   `verify_password` 失败、且 `Conversation.user_id` 引用未 commit 的 User 触发
   `FOREIGN KEY constraint failed`。改用 `app.auth.hash_password()` 生成真 hash，并把
   User / Conversation / Message 分步 commit（无 relationship 的父子表 flush 顺序不可假设，
   数据模型 §6.3 早已登记，又踩一次）。
3. **`db.func.current_timestamp()` 不能赋值给 `DateTime` 列**：软删除测试里给
   `deleted_at` 赋 SQL 函数对象报类型错，改用 `utcnow()`。
4. **收藏按钮初始状态**：`FavoriteButton` 挂载时若 `favorites` store 镜像没拉过就拉一次；
   多个按钮同时挂载会并发请求 ids——store 里加模块级 `inflight` promise 防重。
5. **历史回答无法收藏（与 C-25 同根因）**：收藏按钮与评价按钮挂在同一处（当前轮的
   `answer.message_id`），历史轮走 `QAMessage` 没有 `message_id`。登记为 C-26。

## AD.7 已知不做 / 限制

- **C-26**：历史回答（store 缓存的 `QAMessage`）没有收藏入口——与 C-25 同根因（缺
  `message_id`），当前轮回答的收藏已覆盖需求主路径。
- 收藏列表单次最多返回 500 条（`MAX_ROWS`，与 analytics 同源防接口转圈）；个人收藏量级
  远小于此，不设分页上限更细的告警。
- 「查看详情」跳回目标所在页靠深链（`?doc=` / `?plan=` / `?conversation_id=` / `/guides/{key}`），
  目标若已删除则落在空状态——收藏列表里 `title` 快照仍可显示，但无法回看已删除的原文。

## AD.9 结论

这一轮最硬的判断是**「收藏不能变成过期快照」用「快照存指向、状态实时算」来守**：`title` 与
`document_id` 落库（目标删除后仍能显示名称），`effective_status` 与问答原文一律展示时实时
JOIN——于是「政策更新后同步最新有效状态」与「收藏问答保留原始回答来源」都成立，且收藏表
本身**不改动任何既有表结构**，满足约束 6「尽量采用简单的收藏关联表实现」。其次是账号隔离
落到数据约束而非前端隐藏：收藏问答只认本人会话、收藏计划只认本人计划（越权 3002），
`GET /favorites/ids` 只回当前用户的收藏标识，测试 `test_isolation_between_students` 直接
断言学生 B 看不到学生 A 的收藏。
