## AI.2 判断：先把"留白"拆成两个独立原因

拿到这条需求的第一件事不是改 CSS，而是**量清楚空白到底是多少、由什么造成**。
旧版词云在 1440 视口下的实测值是：

| 量测项 | 旧版 |
| --- | --- |
| 卡片宽 | 1186px |
| 词云画布（`.cloud-box` 实际渲染尺寸） | 1152 × **676** px |
| 词（`getBoundingClientRect` 合成包围盒） | 540 × 365 px |
| **词占卡片宽度的比例** | **45.6%** |
| SVG 内部坐标 | `viewBox="0 0 640 360"` |

两个原因，互相独立，只修一个都不行：

1. **坐标被缩放了两次**。布局是在 640×360 的坐标系里算的，再用 `width:100%` 拉到 1152px 宽
   （放大 1.8 倍）、`height:auto` 连带放大到 676px 高。放大是**把已经排好的坐标当图放大**：
   词与词之间的缝隙、画布四周的留白一起被放大。而且高度是被 width 决定的，1152 宽必然配 676 高，
   一条词云占掉了接近两屏的高度。
2. **词团是"方"的，画布是 3:1 的扁的**。螺旋排布出来的形状各向同性（斜着看是个圆），
   塞进宽扁画布后，左右两侧必然各留一条。

所以本轮的做法是：**布局直接在容器的实测 CSS 像素里做（坐标 1:1，不再缩放），排完再做一次
各向异性松弛把词团摊到画布的宽高比上。**

## AI.3 实现：五块版式 + 词云的三个测点

**版式**（顺序即用户要求的第一～第四部分，另加既有的用户反馈管理块）：

```
① 四张指标卡（等宽 grid-4）        ② 学生画像 │ 提问主题（双栏等高）
③ 词云（通栏，高度 = 宽度 × 0.30）  ④ 一日内时段 │ 提问活跃度（双栏）
⑤ 画像逐条记录表                   ⑥ 用户反馈管理（R16 既有，仅跟随新版式）
```

指标卡从"左右各一条色条"改成"标签 + 右上角线性图标 / 大数字 / 一行口径说明"：
**数字统一用主色**（`--c-primary`），语义色只留在图标底色上。四张卡是同一层的四个侧面，
用四种颜色会被读成四种状态（红=故障、黄=警告）。

**词云三个测点**（都在 `packCloud` 里）：

1. **量**：`ResizeObserver` 读容器实测宽高，`viewBox` 直接等于它 → 坐标即 CSS 像素；
2. **定字号**：按"目标覆盖率"反解统一缩放系数
   `s = sqrt(AREA · W · H / Σ(units · rel² · 1.32))`，再逐档向上试探，
   **同时受"放得下"与"不过密"两个硬闸约束**；
3. **摊开**：排完做各向异性松弛——每个词沿远离中心的方向每次挪 2.6px，不越界、不撞别的词就留下，
   走 30 轮。不增字、不缩字号、只把词团的横向间距拉到与画布同比例。

`AREA` 与松弛是两种不同的手段：前者决定"这个画布最多能放多大的字"，后者决定"同样的字怎么铺开"。

## AI.4 出错现场（三次，全部有实测数字）

### 一、字号被"能不能放下"顶到 67px，密度 44.4%，14 处压字

第一版把试探写成"只要 `forced === 0` 就继续放大"。结果是字号一路顶到 **67.6px**，
估计覆盖率 **44.4%**，`getBBox` 实测 **14 处压字**，最糟糕的一对是「奖学金 × 借阅」。

标定探针（`.build/cloud_calibrate.py`）把估算盒与真实墨迹盒并排列出来，一眼看出问题在哪：

```
词      字号   真实宽   估算宽   真实高   估算高
奖学金  67.6   203.2    221     90      82.4
本科生  56.8   170.4  186.6     75      69.9
...
重叠对 14 组：
  奖学金 × 借阅: 横向 99px  纵向 3.8px
  本科生 × 逾期费: 横向 28.3px 纵向 0.5px
```

**每一处都是纵向 0.3~4.3px、横向却有 27~137px 的余量**——宽估得够、**高估小了**。
真实墨迹高 / 字号稳定落在 1.31~1.33（中文字的全角框比字体 em 盒还高一点），
而我写的是 1.16。两处一起改：

- 高度系数 1.16 → **1.32**（量出来的，不是估的）；
- 加一道密度硬闸 `CLOUD_MAX_COVER`：覆盖率超了就停，哪怕还放得下。

**记下的一条经验：判断"估算够不够"不能看总重叠数，要看重叠的方向与量级。**
全部集中在同一个方向、且只有几像素，那是系数标定问题；如果两个方向都大，才是布局真放不下。

### 二、"让小词从外圈起步"完全无效（测量结果逐位相同）

第二版的想法是：小词（后放的）从螺旋 34% 的位置起步，就能把外围填满。改完重测，
`bboxW` **807.7 → 807.7**，一个像素都没变（先怀疑构建没生效，逐个核对产物哈希才确认是新代码）。

原因：螺旋本来就是从内往外走的，起步点往前挪只是**跳过了那些已经被占用、反正会被拒绝的点**。
只要"第一个可用空位"在外圈，从哪儿起步都落在同一处。**唯一会变的场景是内圈还有空洞**。

结论：起点偏移解决不了各向异性，删掉，换成排完之后的松弛（见 AI.3 第 3 点）。
这也解释了为什么"看起来合理的启发式"必须用测量证伪——它读代码时毫无破绽。

### 三、像素探针越界：Edge 截图按窗口尺寸缩放

写像素级探针（`.build/visual_probe.py`，验证"这块还有没有一块死白"）时报
`IndexError: index out of range`。原因是 1440×1000 的视口，`captureScreenshot` 输出的是
**1080×750**（比例 0.75），拿 CSS 坐标当像素坐标必然越界。改成
`sx = img_w / innerWidth` 换算后正常。

这一条是**已知坑的第二次踩**（R11 记过"取色要乘 `img_w / innerWidth`"），
记在这里是因为"写新探针时不会想起旧文档"。

### 附带修掉的既有腐化：`tools/browser_check.py` 两条过期断言

跑全站巡检证明"没波及别的页面"，结果脚本自己先崩了两次，**都与本轮改动无关**：

1. `getComputedStyle(document.querySelector('.login-page'))` 抛
   `parameter 1 is not of type 'Element'`——登录页在 R11 之后已改成 `WelcomeView`（根节点 `.welcome`），
   脚本还在找 `.login-page` 与"两个 `.role-chip`"。改成断言"`.welcome` 在 + 用户名/密码两个输入框在"。
2. 深色主题探针断言"页面底色必须暗（`bodyLum ≤ 0.6`）"——站点在 R10 就换成了浅底青碧，
   于是 5 个页面恒定报"与深色主题不符"。这条噪声把真正的失败盖住了。判据反转为
   "底色 ≥ 0.75 且文字明显比卡片深（差 ≥ 0.35）"。

修完 7 页一次通过：工作台 / 智能问答 / 资格匹配 / 计划与任务 / 政策知识库 / 规则管理 +
登录页（知识库 18 份、列表 10 行）。

验收脚本的**两条测试自身缺陷**值得记：

1. 第一版断言 `cloud["W"] == cloud["boxW"]` 用的是 `svg.clientWidth` 与 `box.clientWidth`，
   两者本来就相等（`width:100%`），**这条断言永远成立**，等于没验。真正的判据是
   `viewBox` 的三个数与实测尺寸一致——`vb === "0 0 W H"`，它才能抓出"画布与坐标不一致"。
2. 覆盖率阈值最初凭感觉写 `0.72`，第一轮就卡在 0.708 不动。这个数字后来是**量出来的**
   （旧版 0.469 → 新版 0.845），阈值写 0.72 是"介于两者之间"，而不是"看起来差不多"。
