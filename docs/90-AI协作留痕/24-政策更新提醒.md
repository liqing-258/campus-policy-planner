> 所属项目：知校（campus-policy-planner）
> 时间：2026-11-15 ｜ 对应代码：`v0.7.0` + R15 ｜ 提交批次：见 §AB.8
> 定位：功能轮（新增模块，**零新表**）。用户 Prompt 见 §AB.2，全过程记录到"被纠正的缺陷"一级。

---

## AB.1 这一轮要解决什么

需求一句话：**政策换了版本，学生与管理员要能及时发现，且不能编造"改了什么"**。

| 表面看 | 实际牵连 |
| --- | --- |
| 知识库加个"版本"字段 | `documents` 里 `academic_year`/`version_label`/`effective_status`/`supersedes_id` 四列 **M3 就建好了**，但 `supersedes_id` 从未被序列化、也无任何接口能写它——有数据结构没通路 |
| 上传时提示"是不是新版" | 现有上传只做**同 hash 去重**（2001），同标题不同内容照收不误——提示点就该长在这里，但不能拦上传（政策本来就该有新旧版） |
| 旧版本显示个提醒 | "已被替代"是**管理员确认的事实**，"不是最新"是**日期推断**——两句话不能混，混了就会出现"标了已被替代却看不到横幅" |
| 工作台加个更新区 | 红线：**不得编造条款差异**。系统不做条款 diff，卡片只许有事实字段与两句固定话 |
| 问答/匹配提醒 | 问答已有 T-12 版本冲突面板（检索层），匹配页完全没有 |

## AB.2 用户 Prompt 原文（节选，六节）

> 一、功能定位：帮助学生和管理员及时发现政策文件的版本变化、有效状态变化以及可能影响个人事务办理的政策更新。
> 二、知识库优化：突出政策名称/发布部门/发布日期/适用学年/文件版本/当前有效状态/上传时间/关联历史版本；政策状态明确区分：现行有效、已被替代、已失效、暂未确认；增加政策详情页面（基本信息、政策摘要、历史版本和相关文件）。
> 三、版本变化提醒：上传与已有标题相同或高度相关的新文件时提示管理员检查是否属于政策更新；管理员确认新旧版本关系后建立版本关联；旧版本标记「已被替代」；学生查看旧版本时显示醒目的版本提示；问答和资格匹配页面提醒核对版本。
> 四、学生端提醒：工作台「政策更新」区；与已有计划相关的更新要提示"哪份政策发生了变化、新版本发布日期、当前有效状态、是否可能影响已有事务计划、查看新版本"。**注意：如果系统无法准确判断新旧政策的具体条款差异，只提示版本发生变化，不得编造具体变化内容。**
> 五、历史版本查看：同一政策的历史版本列表，点击后能够打开对应文件及原文。
> 六、开发要求：**优先复用** `documents` 的 `academic_year`、`version_label`、`effective_status`、`supersedes_id` 与已有版本冲突检测机制；**不要重复建设一套政策版本数据库**，也不要自动将未经管理员确认的文件标记为现行有效。

### 我对 Prompt 的理解（先于动手写下的三条）

1. "不要重复建设版本数据库" 的意思是：**版本关系只有一份真值**——`supersedes_id`（人工链）+ 标题归并（`versions.normalize_title`）。任何"版本表"都会立刻和 `documents` 分叉。
2. "不得编造具体变化内容" 是**接口层的约束**，不只是前端话术：`GET /policies/updates` 的响应里就不该存在 `diff`/`changes` 这类字段——测试直接断言字段集合。
3. "不要自动标记现行有效" 需要一个**唯一出口**：全仓只有一个动作能把文件标成 active（管理员显式调 `version-link`），上传与预检都不改状态。

## AB.3 方案取舍

| 备选 | 结论 | 一句话理由 |
| --- | --- | --- |
| 建 `policy_versions` 表 | ❌ | 需求明令禁止；且 `supersedes_id` 本来就是干这个的 |
| 上传时弹窗拦截"疑似新版本" | ❌ | 政策有新版本是常态，拦上传是把正常流程当异常 |
| 上传响应 + 预检接口给候选，管理员一键关联 | ✅ | 提示但不拦；确认是显式动作（一个单选 + 一个按钮），审计有记录 |
| 自动把新版标 active、旧版标 superseded | ❌ | 违反"不得自动标记现行有效"——改为 version-link 里管理员显式传 `new_status`（默认 active 但可改 unknown） |
| 用向量相似度找"高度相关" | ❌ | T-12 的老判断：相似度误报会让提示被忽略。只用两条保守规则：规范化标题相同（强）/ 字符二元组 Jaccard ≥ 0.55 或包含（弱），且**只用于提示** |
| 更新卡写"第 X 条由 A 改为 B" | ❌ | 条款对齐做不准，编出来的 diff 比没有更害人。卡片只有事实字段 + 两句固定话 |
| 政策详情新开路由 `/documents/:id` | ❌（取舍） | 知识库行内展开已经是详情（片段原文在），按"不为增加页面数量做演示"的约束就地增强；`?doc=` 深链两处复用 |

## AB.4 现场：被纠正的缺陷（含"测试全绿仍然错"）

### AB.4.1 `supersedes_id` 有字段没通路（开工即发现）

`Document.supersedes_id` 是 M3 建的列，但 `_serialize` 不带它、`PATCH` 不能写它、任何界面都看不到它。**这一轮所有功能都建立在"把它接通"上**：序列化补字段、`version-link` 一条接口负责"建联 + 旧版标 superseded + 新版标状态"三件事（一个动作三步，拆开会漏）。

### AB.4.2 横幅文案「已被《X》替代」被自己的断言抓包

第一版横幅写的是"该文件已被《2026年版》替代"，验收断言查连续子串「已被替代」——**书名号插在中间，断言永远为假**。这不算产品缺陷（文案本身没错），但它逼出了产品侧的修正：改成"该文件已被替代，请勿按本文条款办理；最新版本是《X》。"——**重要信息（已被替代）必须是能被 grep 到的连续词**，插在句子中间的专名会把"已被替代"拆碎。

### AB.4.3 「已被替代」的横幅被日期排序短路（真缺陷，验收抓到）

链路：管理员把 2026 版标「已被替代」→ 打开 2026 版详情 → **横幅没出来**。原因：横幅逻辑先判"是不是最新版"（日期推断），而家族里有一份无发布日期、年份 2099 的验收文件，日期排序把它排到 2026 版前面——于是"当前就是最新版"，横幅短路。**人工确认过的事实被日期猜测否决了**。修复：

- 后端 `versions.replacer_of()`：**人工 supersedes 链优先**——有人明确替代了这一版，那份才是"新版本"，日期只在没人说话时作数；
- 前端 `versionBanner()`：先判 `effective_status === 'superseded'`（事实），再判"不是最新"（推断），两分支不共享前置条件。

回归测试 `test_replacer_wins_over_date_guess` 用"2099 年版无日期"这个刁钻数据钉住。

### AB.4.4 上传预检测试撞了 hash 去重（测试自己的错）

验收脚本第一版复制演示 docx 改名上传——**内容 hash 与库里的《学生事务办理指南》相同**，被 2001 拦下，"上传提示"面板根本没机会出现，连环挂了 4 条断言。改用带唯一内容的 txt（标题仍来自文件名）。教训：**测"同标题不同内容"的场景时，内容也必须是新的**——去重在标题之前。

### AB.4.5 版本列表断言读在"加载中"（竞态，脚本自己的错）

详情展开后版本家族是并行请求，断言跑在落定之前读到 0 条——同一屏里横幅（后一拍）却已经有了。修法是显式等 `.version-block` 不含「加载中」再断言。这类竞态在本地快得看不见，CI 慢的机器上必然偶发。

### AB.4.6 无发布日期的文件排序：年份比日期"大"

`sort_key = (published_at or "", year, id)`：无日期的文件排序键是空串，**在按日期排序时永远垫底**——但当它的年份是 2099 时语义上"很新"。这不是本轮要修的（年份大的无日期文件该排哪是政策语义问题），如实登记：`replacer_of` 绕开了它（人工链优先），纯日期组仍按现规则。

### AB.4.7 两处断言是脚本自己的错

① 查"不比对条款内容"时取了第一个 `.tiny`——那是标题行"近 30 天 18 项"；② 断言"已被替代"连续子串（见 AB.4.2）。**断言先于产品改动失败时，先怀疑断言自己的取值路径**。

## AB.7 已知不做

1. **条款级 diff**：需求明令"无法判断就不编造"，且条款对齐做不准——更新卡永远只有"版本发生变化"。
2. **弱相似阈值是拍的**（0.55）：只影响"要不要提示管理员看一眼"，不自动建联，误报成本是一次点击。
3. **收藏政策**：系统没有收藏功能，"与收藏相关"降级为"与我的计划相关"（有真实数据的那一半）。
4. **无发布日期文件的排序语义**（AB.4.6）：登记为数据问题，不在本轮修。

## AB.9 结论

这一轮没有新表、没有迁移、没有模型调用——**全部是把 M3 就建好的 `supersedes_id` 接通，
再用 T-12 的标题归并把"版本家族"算出来**。最值钱的一条判断是 AB.4.3：
**人工确认过的事实（已被替代）必须排在日期推断（谁最新）前面**——
排序是启发式，标注是决定，启发式永远不能否决决定。
第二条是"不得编造条款差异"的落法：不靠前端自觉，靠接口**根本没有 diff 字段**。
