## AF.1 目标

用户要的不是"跑一遍测试然后报告全绿"，而是**真实地找出问题**。原话里有几条硬约束：

- 「不能只根据回答是否通顺判断功能是否通过」
- 「将接口返回成功当成业务结果正确」在禁止清单里
- 「通过率只能按照实际执行结果计算，不得把未执行、阻塞或无法验证的用例算作通过」
- 「如果某个测试因为缺少真实政策文件、模型服务或账号权限而无法完成，请明确标记为阻塞或未执行，并说明原因」

所以本轮的判定标准只有一条：**结论必须能回指到一个可复核的证据**——数据库里的一行、接口返回的一个字段、页面上的一个 DOM 值。

## AF.2 用户 Prompt 与理解

七阶段结构：环境检查 → 模块测试（7 个）→ 跨模块流程（4 条）→ 权限异常（12 项）→ 自动化 → 问题清单 → 修复与回归（待确认）。

两处张力需要先解决，否则会做错：

1. **第六阶段说"先不要改代码，等我确认"**，而结尾说"完成任务后更新文档、更新 GitHub"。→ 解法：**出报告 + 更新文档 + 推送，但不碰业务代码**。缺陷留"是否已修复：否"，修复方案写清楚等确认。这样两边都不违背。
2. **"不允许删除或修改现有正式数据"**，但测试必然要写（上传文件、建计划、改规则）。→ 解法：所有写操作带 `[R19测试]` 前缀 + `before/after` 快照差集清理 + 规则改动 `try/finally` 恢复；测试后逐表核对基线。

## AF.3 方案取舍

### 取舍一：数据一致性用"回库重算"，不用"接口自证"

工作台的待办数、7 天到期、逾期、完成率、管理员三态统计，全部从 SQLite 用独立 SQL 重算一遍，再与接口返回值比。**没有一条用例是"接口 code==0 即通过"。**

这条做法直接抓出了两个"看着对其实要澄清"的点：

- `/tasks/stats` 的 `completion_rate` 分母排除 `cancelled` —— 若不读实现注释，会误判"取消任务后完成率变高"是 bug；
- 管理员的 `document_count` 是"参与过匹配的政策数"（当前 1），不是知识库总数（18）—— 若不查实现，会误判接口少算了 17 份。

后者最终降级为 P3 文案歧义（数字本身对，label 容易被误读），而不是数据错误。

### 取舍二：引用真实性逐条回库，不抽样

每条 citation 都拿 `chunk_id` 查 `document_chunks`，四项一起核：chunk 存在、`document_title` 与库一致、`page_number` 一致、`section_title` 一致、`snippet` 是 chunk 正文的子串。

实测两条引用全部通过。**这一步是"AI 有没有编造"唯一能落地的判据**——追问模型"你是否编造"没有意义。

### 取舍三：AI 回答正确性用"关键词 + 人工对照原文"，不判文风

`answer` 是否通顺不参与判定。判定的是：回答里的数字能不能在原文里找到（3.0 / 30% / 23:30），以及引用指向的原文是否支持这个数字。

由此抓出 **P1-01**：回答并列了 3.0（2026 版）与 2.8（2025 版）并说"无法判断"。数字都在原文里，引用也都是真的——**问题不在生成，在检索**。

### 取舍四：两条"用例预期错误"必须改判，不能算缺陷

首轮 T2.9（无关问题）、T2.10（食堂几点开门）、T6.6（政策文件数）判 FAIL，逐个查证后确认是**测试脚本写错了**：

| 用例 | 我的错误预期 | 系统正确行为 |
| --- | --- | --- |
| T2.9 | 断言 `code==0` 且返回一段话 | 返回 `4001 refused=true` + 明确理由（覆盖率 0.11 < 阈值 0.35），且不落库 |
| T2.10 | 预设"知识库没有食堂政策" | 库里有《食堂与后勤生活服务指南》，答 6:30 有据可依 |
| T6.6 | 把 `document_count` 当知识库总数 | 它是"参与匹配的政策数"（distinct document_id） |

**如果把这三条算成系统缺陷，报告就会变成"6 个缺陷"** —— 数字更"充实"，但全是假的。改判并在报告里写明"这是用例问题、非系统缺陷"，比凑数重要。

## AF.4 现场记录（本轮踩到的）

### 1. `pytest` 汇总行再次被临时目录清理拦掉

跑全量 456 项，进度点 100% 是 `.`，但没有任何 `passed` 汇总行，尾部是
`safe-delete SAFE_DELETE_BULK_CONFIRM_REQUIRED count=231`。这是项目已知环境坑的**第五次**复现。
判据固定为：`--collect-only` 按文件加总（456）+ 进度点无 `F`/`E`。

### 2. 检索接口的返回字段不是 `hits` 而是 `candidates`

T5.6/T5.15 首轮判 FAIL（"命中 0 条"），实际是我读错了字段名：
`{mode, min_coverage, candidates, total_hits, index_size, refused, ...}`。
**"命中 0 条"和"我读错字段"在断言里长得一模一样** —— 这类假失败只能靠打印完整响应识破。

### 3. `page_size=200` 被拒后脚本崩了，但那是正确行为

`/tasks?page_size=200` 返回 `1002 page_size 必须在 1–100 之间`。
我的 `urlopen` 包了 `HTTPError` → `data=None` → 下一行 `data["items"]` 崩。
系统没错，脚本脆。改成 100 并分页。

### 4. `users` 表没有 `updated_at` 列

为了测"跨账号隔离"造临时学生，按习惯写了 `updated_at`，直接
`table users has no column named updated_at`。
**造测试数据也要按 schema 来，不能凭印象。**

### 5. 脚本中途崩溃会留下孤儿草稿计划

`/plans/draft` 是**会落库的**（`status=draft`，`tasks_persisted=false`）。
脚本在 T4.4 崩溃后，那个 draft 计划留在库里；第二次运行又建一个，于是我在库里看到
两个同名 plan，一度怀疑"confirm 会不会另建一个正式计划"。

做了一次受控实验才排除：`draft → X`，`confirm X` 后 **X 自己**变 confirmed，没有新 plan。
**孤儿是脚本崩溃留下的，不是 confirm 的缺陷。** 结论：这类"写接口"的测试脚本必须 `try/finally` 清理。

### 6. 浏览器脚本被路由守卫"正确行为"卡住

学生访问 `/admin` → 守卫重定向到 `/` → `b.goto()` 等不到 `/admin` 直接 `TimeoutError`。
这和 R11 那次"带 token 访问 `/welcome` 被跳走"是同一类。改法：`goto` 包 `try/except`，之后读
`location.pathname` 断言"被弹回"。

## AF.9 结论

这一轮最值得记的不是"195 项通过"，而是**一个只有同时读设计文档和读代码才能发现的缺陷**：

> 设计说明书 §5 写得很清楚——`effective_status = superseded` 的片段降权 50%，且必须在答案里提示"该文件已被更新版本替代"。
> 而 `app/retrieval.py` / `app/qa.py` 里**一行 `effective_status` 都没有**。
> 同一份字段在匹配页（`version_note`）、政策更新、日历、收藏里都被正确使用，唯独检索层不消费它。

现象是 AI 说"3.0 或 2.8，无法判断"。**看起来像模型能力不足，实际是检索少了一步过滤。**
如果只跑接口断言（`code==0`、`citations 非空`、`trace 有节点`），这条永远发现不了——所有接口都是"成功"的。

第二件事：三条 FAIL 里没有一条是系统缺陷，全是我自己的用例写错了。
把它们改判、并在报告里写明"这是用例问题"，会让通过率从 96.97% 变成 98.48%——
但更重要的是，**报告里的每一个 FAIL 都真的指向一个要修的东西**。这比数字好看有用。
