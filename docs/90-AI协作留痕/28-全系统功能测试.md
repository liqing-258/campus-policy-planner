## AF.1 目标

用户要的不是"跑一遍测试然后报告全绿"，而是**真实地找出问题**。原话里有几条硬约束：

- 「不能只根据回答是否通顺判断功能是否通过」
- 「将接口返回成功当成业务结果正确」在禁止清单里
- 「通过率只能按照实际执行结果计算，不得把未执行、阻塞或无法验证的用例算作通过」
- 「如果某个测试因为缺少真实政策文件、模型服务或账号权限而无法完成，请明确标记为阻塞或未执行，并说明原因」

所以本轮的判定标准只有一条：**结论必须能回指到一个可复核的证据**——数据库里的一行、接口返回的一个字段、页面上的一个 DOM 值。

## AF.2 用户 Prompt 与理解

七阶段结构：环境检查 → 模块测试（7 个）→ 跨模块流程（4 条）→ 权限异常（12 项）→ 自动化 → 问题清单 → 修复与回归（待确认）。

两处张力需要先解决，否则会做错：

1. **第六阶段说"先不要改代码，等我确认"**，而结尾说"完成任务后更新文档、更新 GitHub"。→ 解法：**出报告 + 更新文档 + 推送，但不碰业务代码**。缺陷留"是否已修复：否"，修复方案写清楚等确认。这样两边都不违背。
2. **"不允许删除或修改现有正式数据"**，但测试必然要写（上传文件、建计划、改规则）。→ 解法：所有写操作带 `[R19测试]` 前缀 + `before/after` 快照差集清理 + 规则改动 `try/finally` 恢复；测试后逐表核对基线。

## AF.3 方案取舍

### 取舍一：数据一致性用"回库重算"，不用"接口自证"

工作台的待办数、7 天到期、逾期、完成率、管理员三态统计，全部从 SQLite 用独立 SQL 重算一遍，再与接口返回值比。**没有一条用例是"接口 code==0 即通过"。**

这条做法直接抓出了两个"看着对其实要澄清"的点：

- `/tasks/stats` 的 `completion_rate` 分母排除 `cancelled` —— 若不读实现注释，会误判"取消任务后完成率变高"是 bug；
- 管理员的 `document_count` 是"参与过匹配的政策数"（当前 1），不是知识库总数（18）—— 若不查实现，会误判接口少算了 17 份。

后者最终降级为 P3 文案歧义（数字本身对，label 容易被误读），而不是数据错误。

### 取舍二：引用真实性逐条回库，不抽样

每条 citation 都拿 `chunk_id` 查 `document_chunks`，四项一起核：chunk 存在、`document_title` 与库一致、`page_number` 一致、`section_title` 一致、`snippet` 是 chunk 正文的子串。

实测两条引用全部通过。**这一步是"AI 有没有编造"唯一能落地的判据**——追问模型"你是否编造"没有意义。

### 取舍三：AI 回答正确性用"关键词 + 人工对照原文"，不判文风

`answer` 是否通顺不参与判定。判定的是：回答里的数字能不能在原文里找到（3.0 / 30% / 23:30），以及引用指向的原文是否支持这个数字。

由此抓出 **P1-01**：回答并列了 3.0（2026 版）与 2.8（2025 版）并说"无法判断"。数字都在原文里，引用也都是真的——**问题不在生成，在检索**。

### 取舍四：两条"用例预期错误"必须改判，不能算缺陷

首轮 T2.9（无关问题）、T2.10（食堂几点开门）、T6.6（政策文件数）判 FAIL，逐个查证后确认是**测试脚本写错了**：

| 用例 | 我的错误预期 | 系统正确行为 |
| --- | --- | --- |
| T2.9 | 断言 `code==0` 且返回一段话 | 返回 `4001 refused=true` + 明确理由（覆盖率 0.11 < 阈值 0.35），且不落库 |
| T2.10 | 预设"知识库没有食堂政策" | 库里有《食堂与后勤生活服务指南》，答 6:30 有据可依 |
| T6.6 | 把 `document_count` 当知识库总数 | 它是"参与匹配的政策数"（distinct document_id） |

**如果把这三条算成系统缺陷，报告就会变成"6 个缺陷"** —— 数字更"充实"，但全是假的。改判并在报告里写明"这是用例问题、非系统缺陷"，比凑数重要。

## AF.4 现场记录（本轮踩到的）

### 1. `pytest` 汇总行再次被临时目录清理拦掉

跑全量 456 项，进度点 100% 是 `.`，但没有任何 `passed` 汇总行，尾部是
`safe-delete SAFE_DELETE_BULK_CONFIRM_REQUIRED count=231`。这是项目已知环境坑的**第五次**复现。
判据固定为：`--collect-only` 按文件加总（456）+ 进度点无 `F`/`E`。

### 2. 检索接口的返回字段不是 `hits` 而是 `candidates`

T5.6/T5.15 首轮判 FAIL（"命中 0 条"），实际是我读错了字段名：
`{mode, min_coverage, candidates, total_hits, index_size, refused, ...}`。
**"命中 0 条"和"我读错字段"在断言里长得一模一样** —— 这类假失败只能靠打印完整响应识破。

### 3. `page_size=200` 被拒后脚本崩了，但那是正确行为

`/tasks?page_size=200` 返回 `1002 page_size 必须在 1–100 之间`。
我的 `urlopen` 包了 `HTTPError` → `data=None` → 下一行 `data["items"]` 崩。
系统没错，脚本脆。改成 100 并分页。

### 4. `users` 表没有 `updated_at` 列

为了测"跨账号隔离"造临时学生，按习惯写了 `updated_at`，直接
`table users has no column named updated_at`。
**造测试数据也要按 schema 来，不能凭印象。**

### 5. 脚本中途崩溃会留下孤儿草稿计划

`/plans/draft` 是**会落库的**（`status=draft`，`tasks_persisted=false`）。
脚本在 T4.4 崩溃后，那个 draft 计划留在库里；第二次运行又建一个，于是我在库里看到
两个同名 plan，一度怀疑"confirm 会不会另建一个正式计划"。

做了一次受控实验才排除：`draft → X`，`confirm X` 后 **X 自己**变 confirmed，没有新 plan。
**孤儿是脚本崩溃留下的，不是 confirm 的缺陷。** 结论：这类"写接口"的测试脚本必须 `try/finally` 清理。

### 6. 浏览器脚本被路由守卫"正确行为"卡住

学生访问 `/admin` → 守卫重定向到 `/` → `b.goto()` 等不到 `/admin` 直接 `TimeoutError`。
这和 R11 那次"带 token 访问 `/welcome` 被跳走"是同一类。改法：`goto` 包 `try/except`，之后读
`location.pathname` 断言"被弹回"。

## AF.9 结论

这一轮最值得记的不是"195 项通过"，而是**一个只有同时读设计文档和读代码才能发现的缺陷**：

> 设计说明书 §5 写得很清楚——`effective_status = superseded` 的片段降权 50%，且必须在答案里提示"该文件已被更新版本替代"。
> 而 `app/retrieval.py` / `app/qa.py` 里**一行 `effective_status` 都没有**。
> 同一份字段在匹配页（`version_note`）、政策更新、日历、收藏里都被正确使用，唯独检索层不消费它。

现象是 AI 说"3.0 或 2.8，无法判断"。**看起来像模型能力不足，实际是检索少了一步过滤。**
如果只跑接口断言（`code==0`、`citations 非空`、`trace 有节点`），这条永远发现不了——所有接口都是"成功"的。

第二件事：三条 FAIL 里没有一条是系统缺陷，全是我自己的用例写错了。
把它们改判、并在报告里写明"这是用例问题"，会让通过率从 96.97% 变成 98.48%——
但更重要的是，**报告里的每一个 FAIL 都真的指向一个要修的东西**。这比数字好看有用。

## AF.10 修复与回归（用户确认后）

用户回复「继续」即视为确认按建议顺序修复。实际只修**复核确认成立的 4 项**，另 **2 项撤回**。

### 撤回的两项，比修好的四项更值得记

| 编号 | 首轮我怎么判的 | 复核为什么站不住 |
| --- | --- | --- |
| P2-02 | 「匹配页申请项目下拉列出了没有已复核规则的项目」 | `MatchView.vue:238` 的请求本就带 `?review_status=approved`，下拉只从已复核规则生成。我的 T3.20 是**手动**给 `/matches` 传了个前端不会给的值——测的是后端容错，不是前端有坑 |
| P3-03 | 「检索索引累积已删文档，index_size 163 > 库中 134」 | `documents.py:497` 的 `delete_document` 本来就调 `rebuild_index()`。163 是**我的测试脚本直接 SQL 删文件**（绕过 API）造成的。重启后 131 = 未下架片段数，严丝合缝 |

共同点：**两条都是"我构造出的输入"被当成"用户能触发的路径"**。
一条没读前端代码，一条没走 API 删除。把缺陷数从 6 改回 4 不会让报告更好看，
但能让"每个 FAIL 都真的指向要修的东西"这句话成立。

### 修的四项

**P1-01（唯一 P1）** —— 三处落点，两个设计取舍：

1. `versions.status_map()`：批量取「有效状态 + 替代者标题」。放在 versions.py 而不是 retrieval.py，
   因为 `新版.supersedes_id = 旧版.id` 这个方向只该在一个地方解释。
2. `retrieval.retrieve()`：被替代片段 `score × 0.5`，状态随 `Candidate` 带走。
   **降 score 不降 coverage**——coverage 是相关性闸门，版本新旧不改变"这段文字与问题有多相关"；
   降 coverage 会把证据推进拒答分支，那是用"答不出"掩盖"答错版本"。
3. `qa.build_evidence()` + `SYSTEM_PROMPT` 第 7 条：证据块里写【版本效力】，并要求"有现行版就按现行版答，
   不要说无法判断"。**状态必须写进证据文字**——模型看不到 API 里的 `conflicts`。

复测：回答从「3.0 或 2.8，无法判断」变成「不低于 3.0…2025 年版已被替代，不再作为当前标准」；
检索侧 score 13.5 vs 6.75，精确 2 倍。

**P2-01** 知识库补「部门」列 + `version_label`；**P3-01** 数据中心文案「N 份政策被匹配」；
**P3-02** `GET /plans` 加 `task_counts`（一次 GROUP BY，顺带干掉前端 N+1），计划卡片显示进度。

### AF.11 补测：不再用"要停服务"当借口

首轮把「模型不可用」「数据库异常」标成未执行，理由是停服会影响正在服务的进程。这个理由**只对了一半**——
真正的问题是我没想到可以用**独立端口 + 环境变量覆盖**做：

```bash
# 读 config.py 确认 load_dotenv(override=False)：进程环境变量优先于 .env
LLM_API_KEY= PORT=5011 python server.py --no-browser --port 5011
DATABASE_URL="sqlite:///./data/__r19_missing__/x.db" PORT=5012 python server.py --no-browser --port 5012
```

主服务全程在 5000 端口正常跑，三个 `health` 同时可查：

| 实例 | status | db | llm_mode |
| --- | --- | --- | --- |
| 5000 主 | ok | ok | llm |
| 5011 无密钥 | ok | ok | **degraded** |
| 5012 库不可用 | **degraded** | **unavailable** | llm |

**实测结论：降能力不降可用性。**

- 无模型：登录照常（鉴权不依赖模型）；提问返回 `4006`「当前为降级模式：未接入模型，仅返回原文片段」，
  answer 为空但**候选片段 9 条照给**，页面横幅写明"缺 LLM_API_KEY；已查找 .env（已读到）"。
- 无库：服务起得来，`health` 报 `db=unavailable`；登录返回 500 + `9001`，
  登录窗内渲染 `<p class="err">服务器内部错误，请联系管理员</p>`——用户知道发生了什么，页面无 `Traceback`/`sqlite` 字样。

页面层 9 项断言全过（D0–D8）。

**两条 FAIL 又是脚本问题**：D6 我在登录失败后先 `goto("/")` 才读页面，读到的是落地页；
D8 把浏览器对 500 的 `Failed to load resource` 日志当成前端 JS 异常。
**判据要贴着"被测行为"写，而不是贴着"我想看到什么"写。**

补测后统计：**208 / 208（100%），未执行 0**。

### AF.12 补测二：第 12 项「快速连续点击」——顺带抓出一个竞态

用户任务书的第四阶段列了 12 项异常，首轮我做了 11 项，「快速连续点击按钮」只写了句"做了单用户快速操作"，
没有用例。补上时分成两层，结果第二层抓出一个真缺陷。

**第一层：前端守卫（真实连点）** —— 都挡住了。

- 收藏按钮连点 5 次：`favorites` 只变 1 条（`FavoriteButton` 的 `busy` + `:disabled`）；
- 问答「发送」连点 5 次：只建 1 个会话（`asking` 在首次点击同步置位）。

**第二层：数据层（真并发）** —— 这里出问题。

5 个线程同时 `POST /favorites` 同一文档：1 个返回 `code=0`，**4 个返回 9001（HTTP 500）**。
库里仍然只有 1 条，所以数据没错——错在反馈。

根因是 check-then-act：`select` 查不存在 → `insert`。5 个请求同时查到"不存在"，后 4 个撞
`UNIQUE constraint failed: favorites.user_id, favorites.target_type, favorites.target_id`，
异常冒到全局处理器变成 9001。**幂等接口在竞态下退化成了报错。**

修法：捕获 `IntegrityError` → `rollback` → 按同一三元组重查 → 按幂等命中返回 `updated=true`；
重查仍为空说明不是唯一约束（比如外键失败），照原样抛，不把真错误吞成 200。
复测：返回码 `[0, 9001]` → **`[0]`**。

**一条方法论**：已有的"重复收藏幂等"用例是**串行**的——第二次请求能查到第一次的记录，走 `updated` 分支，
所以永远测不出竞态。**幂等要在并发下验，不是连续两次。**

**又一次自己打自己的脸**：写"唯一约束存在"的断言时，我用 `inspect().get_indexes("favorites")`，
返回的两个索引都不是 unique，差点写下"约束根本不存在"。实际它是 `UniqueConstraint`（表级约束），
要查 `get_unique_constraints()`。**断言写错方向，会把"有防线"读成"没防线"**——这比漏测更危险，
因为你会去"修"一个没坏的东西（我确实先写了一段没有任何用的 IntegrityError 处理，后来才发现方向对了、
理由是错的）。
