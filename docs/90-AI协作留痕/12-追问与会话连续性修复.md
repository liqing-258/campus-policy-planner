## P.1 目标（一句话）

让"继续追问"能答出来，让"切页再回来"还看得见刚才那段对话；
并且**不让这两件事把系统弄坏**——断言的口径是"改写只做加法"。

拆开是三条独立目标，且必须先证明它们互不替代：

1. **追问召回**：点「继续追问」拼出的句子含"这个问题/它"，在 BM25 上是纯噪声，
   覆盖率被稀释到阈值以下，于是拒答；带会话历史时更糟——"那它要多久"字面一个主题词都没有。
2. **同义说法**：原文写"评审办法""申请材料"，学生说"拿奖学金要准备啥"，
   字面不通就零召回。这不是知识库缺内容，是**问法与写法不接轨**。
3. **状态丢失**：`<router-view>` 切走时 AskView 卸载，`answer/refusal/degraded` 三个 ref 一起消失，
   点一下「政策知识库」再回来，刚才那段解答变成欢迎页——而会话在右侧历史栏里明明还列着。

第 3 条与第 1、2 条**没有任何代码重叠**：一条在检索链路，一条在组件生命周期。
写在同一轮里是因为用户同时在界面上看到了它们，不是因为它们同源。

## P.3 AI 输出摘要（做了什么，以及为什么这么做）

### P.3.1 三个缺陷其实只有两个根因

- 缺陷 1、2 是**同一个根因的两种表现**：检索只认字面，而"追问"和"口语"都让字面与原文不接轨。
  所以解法是同一个：**检索前先问一次模型"这句话到底在问什么"**，产出两种东西——
  一句自包含的查询（还原指代）、几个政策同义表述（接轨写法）。
- 缺陷 3 是**状态放错了层**：把"当前这一轮"放在组件 ref 里，而组件的生命周期比用户的浏览行为短。
  解法不是"防抖存一下"，而是**把会话状态提到 Pinia 并把清空权收回到两个显式入口**。

### P.3.2 与需求书 **不一样** 的那一处：覆盖率闸门不用并集

需求书写的是"`standalone` 分词 ∪ `expanded_terms` 当分母，重算覆盖率"。
照做之前先量了一遍（`.workbuddy/measure_coverage2.py`，演示库 18 份 / 122 片段）：

```
Q: 《图书馆借阅与自习空间管理办法》里还有哪些与这个问题相关的规定？
  standalone 15 / 扩展词项 16（语料存在 12）/ 并集全量 20
  文档/章节                                R2     并集全量    去掉OOV
  图书馆借阅与自习空间管理/第一章 开放时间              0.53     0.40     0.47
  图书馆借阅与自习空间管理/第四章 违规处理              0.40     0.30     0.35   ← 掉到阈值以下
```

并集把同义词当成了**追加要求**：一条片段除了覆盖用户原话，还得分担"滞纳金""借阅管理办法"
才不掉分。可扩展词是同义**替代**，不是必须同时满足的条件。而 0.35 是 §7.2.1 用 24 条评测集
5 点扫描定的——**分母一变，阈值就不是原来那个阈值了**，等于偷偷改了定标结果。

所以改成"三视图取最大值"：谁覆盖得好用谁，扩展词只负责把候选捞回来，不负责扣分。
这一处与需求书不同，**理由是可复核的数字，不是偏好**。

### P.3.3 三视图的第三个视图，是被一次反向退化逼出来的

第一版只取 A（standalone）/ E（扩展词）两视图，端到端一跑就露了马脚：

```
问： 《图书馆借阅与自习空间管理办法》里还有哪些与这个问题相关的规定？
  R2 单路: refused=False total=18 passed=6
  R3 双路: refused=False total=19 passed=5     ← 少了 1 条
```

改写把问题变长变具体，A 视图的分母变大，原本够格的片段掉到 0.35 以下——
**加了个体验优化，反而把原本能答的候选挡在门外。**

修法加两处，合成一条可断言的性质「改写只做加法」：

1. 闸门把**用户原话**也算一个视图，取三者最大值（原话那一项与 R2 完全相同，所以 R2 过闸的 R3 必过）；
2. 原话单独占一路召回（O 路），保证 R2 能召回进池的片段，R3 一定还在池里——
   否则改写跑偏时，原话的片段**根本进不了池子**，覆盖率再宽松也救不回来（闸门只筛池子，不捞池子外的）。

排序分数仍按 self-contained 查询算：原话只决定**进不进门**，不决定**排第几**，
否则排序会退回 R2，改写的意义就没了。

### P.3.4 改写放在 retrieval 节点内，不塞进 intent

`app/intent.py` 是刻意的纯规则模块，输出只影响"要不要建议去做资格匹配"，不参与召回。
把一次模型调用塞进去，等于让一个不参与决策的节点开始产生网络延迟；
而且改写失败时 intent 节点会被记成 failed，整条链路按"意图识别失败"处理——属于错判。

放在 retrieval 里，改写失败是**可回退**的：用原话照样检索，`rewrite.reason` 写进轨迹。
降级（无 Key）时连调用都不发。

### P.3.5 前端：清空的权力只留给两个显式入口

| 事件 | 允许做什么 | 为什么 |
| --- | --- | --- |
| `onMounted` | `restore()` → 空则按 `conversation_id` hydrate → 仍空显示欢迎区 | 三步任何一步拿到内容就停 |
| `onBeforeUnmount` | 只**落盘**（`writeNow`） | 卸载时清空正是缺陷本身 |
| 点「新对话」 | `clear()` | 用户明确要重新开始 |
| 登出 / 3001 令牌失效 | `clear()` | 换人登录不能看到上一个人的问答，这是隐私不是体验 |

缓存只存 `role/content/timestamp/kind/精简引用`，正文单条截断 600 字。
不截断的话，一条降级回答是"6 段原文拼接"（3~4 KB），二三十轮后抛 `QuotaExceededError`——
那时**整份缓存一次都写不进去**，退化成"全丢"，比不缓存更糟。

## P.4 人工干预记录（出错、被数据打回、测法错的现场）

这一轮 10 个现场里有 4 个属于同一类：**我的验证手段本身是错的**。
按本项目惯例，测法错也要留档——它比代码错更隐蔽，因为"测试通过"看起来像好消息。

### P.4.1 并集口径把好候选算出闸门（设计被数据打回）

见 §P.3.2 的表：第四章 违规处理 0.40 → 0.30。
**这条是需求书原文的做法，被自己的实测否掉。** 处理方式是改口径 + 把数据写进设计 §7.2.4，
而不是"照做，反正错了也不是我的问题"。

### P.4.2 R3 让过闸数从 6 掉到 5（自己引入的反向退化）

见 §P.3.3 的现场。修完后补了两条用例把它钉死，其中一条先断言"构造有效"：

```python
def test_a_view_alone_would_refuse_the_chunk(index):
    # 先证明构造有效：只看自包含视图，这条片段确实掉到阈值以下
    assert index.score_chunk_with(a_terms, "lib-fee").coverage < 0.35
    assert index.score_chunk_with(tokenize(USER_QUERY), "lib-fee").coverage >= 0.35
```

没有这一步，后面两条可能在"两个口径都能过闸"的构造上跑成永远通过——
看起来一直在守着，其实什么也没守。

### P.4.3 拒答把 `conversation_id` 清成空串（代码造成的会话断裂）

现场（E2E 第二次跑，③ 之后）：

```
--- ③ 纯指代追问 → code=4001
    拒答: 没有检索到任何与问题词项相关的片段
    conversation_id = None          ← 我传了 cid，返回却丢了
```

根因不在前端：`_refusal_payload()` 从来没有 `conversation_id` 这个字段，
前端只能 `refusal.value.conversation_id ?? ''` → 把正在看的会话 id 抹掉 →
下一句追问另起一条新会话，上一轮问题不在历史里，改写再强也无从还原指代词。

**这是"追问答不出来"的第二个成因，而且是代码造成的、与检索质量无关。**
修法：后端回传（没有上文时回 `null`，与"有但丢了"可区分），前端**只在拿到非空 id 时覆盖**。

### P.4.4 改写预算 800 被推理吃光，改写**静默**回退

同一个现场，报错原文：

```
rewrite: applied=False reason=改写失败，已回退原查询：模型只输出了推理内容
         （reasoning_tokens=800），正文为空——max_tokens=2500 被推理耗尽，请调大 LLM_MAX_TOKENS
```

一句话里有两个问题：

1. **预算太小**：`QUERY_REWRITE_MAX_TOKENS=800`，`deepseek-flash` 把 800 全用在推理上，
   正文为空。表现就是"改写没生效"——和"没做这个功能"一模一样，**日志里只有一句失败**。
2. **错误信息在骗人**：它说 `max_tokens=2500`（全局配置），实际这次生效的是 800。
   运维照着调 `LLM_MAX_TOKENS` 永远调不好，因为卡住的是另一个更小的数。

修法：默认预算 800 → **1800**；`llm._to_result()` 增加 `budget` 参数，
报错里的数字改成**本次实际生效的预算**。这条改的是"错误信息必须指向正确的旋钮"，
不是顺手美化文案。

### P.4.5 第一次 E2E 得出结论"改写完全没生效"——其实连的是旧进程

第一次跑端到端，`standalone` / `expanded` / `recall_paths` 全是 `None`，拒答也没有 `conversation_id`。
看起来像"新代码一行都没生效"。查下来的原因：**5000 端口上跑着上一轮留下的服务**，
我新起的进程绑不上端口就退了，请求全打在旧进程上。

教训：改动后要验证"服务到底是不是新代码"。判据不能是"我刚启动过"，而是**取一个新代码才有的字段**
（`recall_paths` 里有 `original` 这个键）。后面所有验证都改到独立端口 5002/5003 并先做这个探针。

### P.4.6 巡检脚本自己"测法错"：把 2 轮判成 1 轮

`tools/ask_flow_check.py` 第 8 步报 `FAIL 切到知识库再回来，对话轮次还在 · 2 → 1 轮`。
一度以为是缓存丢消息。逐步打印后看清是**脚本的等待条件写错了**：

```python
answered_again = c.wait_for("!!document.querySelector('.answer-text')", 150)
```

历史轮次里也有一个 `.answer-text`（R3 起历史会铺出来），所以这句**立刻返回 true**，
脚本紧接着就 `goto /library`——**请求还在飞就把页面切走了**，第二轮自然没落库。

修法：等"第 2 个答案块"（历史 1 个 + 本轮 1 个）。改完 32/32。
顺带发现一个真实的边界行为：请求在飞时切页，那一问会以"无回答的提问"留在缓存里。
于是补了一句提示（"这一问没有等到回答……可以重新问一次"）——不是消灭它，是**如实说出来**。

### P.4.7 我的调试脚本把两个问题拼成了一句

为了定位 P.4.6，写了个打印缓存与 DOM 的临时脚本。第一版这样输入第二问：

```python
c.eval("document.querySelector('textarea').focus()")
c.send("Input.insertText", {"text": "那能续借几次？"})
```

`ask()` 结束后会把问题留在输入框里，`insertText` 是**追加**，于是第二问变成
"图书馆的书逾期了怎么收费那能续借几次？"。缓存里前 8 个字看起来完全正常，
差点又误判成"缓存丢消息"。

修法：插入前先清空并 dispatch `input`（Vue 的 v-model 只认真实输入事件，
`el.value = x` 改得动 DOM 改不动绑定）。

### P.4.8 注释与实现不符（不是功能错，是文档错）

- `app/qa.py` 里写着 `# ---------- ③ analysis（唯一调模型的节点） ----------`，
  R3 之后 retrieval 也调模型了。改成"生成答案的那次模型调用"，并写明 `model_calls` 要按节点各记各的。
- `retrieval._path_uncovered()` 的 docstring 声称"实测 9 条过闸只有 5 条真正命中"。
  那个现象在覆盖率改成三视图最大值之后就**不可能发生**了（融合池里的片段必然命中过某一路）。
  代码保留为防御性断言，docstring 改成说实话，不再拿一个已不存在的数据当理由。

### P.4.9 「登出清缓存」只写了代码，真跑才发现卸载钩子把空壳写了回去

收尾时补验两条**只在代码里写过、没在浏览器里跑过**的路径（它们都在 `App.vue` / `stores/auth.ts`，
影响全站 7 个页面）。第一条一跑就红：

```
① 退出前：path=/ask  token=eyJhbGci…  qa={"conversationId": "01FAKE00…
  ✗ 退出后：路径 /login · 令牌 None · 问答缓存 '{"conversationId":"","messages":[]}'
```

路径对、令牌清了，**但缓存不是 `null`，是一个空壳**。

根因是三个动作的先后顺序：`logout()` 里的 `qa.clear()` 先 `removeItem`，
路由随即跳 `/login`，AskView 卸载，而 `onBeforeUnmount` 里的 `qa.writeNow()` 又把
`{conversationId:'', messages:[]}` 写了回去。**"卸载时只落盘"这条规矩本身没错，错在落盘不判空。**

内容确实是空的（没有泄露上一个用户的问答），所以这不是隐私事故；但它让"清干净了没有"
这件事没法用一条断言回答——**能一条断言回答的隐私保证才是可信的**。
修法：`writeNow()` 里加一条前置判断，空会话直接 `removeItem` 而不写盘。

> 这一条如果只读代码是发现不了的：三条语句分开看都对。

### P.4.11 复现门禁一直在偷偷验证"别人的库"

"改了检索层就重跑评测集"之外，交付里还有一条更硬的声明：**陌生环境 10 分钟复现**。
我原本把它列为"不跑"——理由是"本轮没新增依赖，风险低"。那是一句论证，不是证据。
真跑了，第一次就红：

```
FAIL  2.5s  生成演示计划与任务
httpx.ConnectError: [WinError 10061] 由于目标计算机积极拒绝，无法连接。
```

`tools/seed_demo_flow.py` 按设计**只走真实 HTTP**（它的文档明写"需要服务已启动"），
而 `repro_check.py` 把它当自包含脚本直接调。于是出现两种情形：

| 环境 | 会发生什么 |
| --- | --- |
| 真正干净（评审机器） | 连接被拒 → 整条门禁 FAIL。**评审第一步就卡住** |
| 开发者本机开着 5000 | 它"通过"了——但打的是**那个外部服务的库**，与刚从 `git archive` 解出的干净库无关；还顺手往那个库写了计划与任务 |

也就是说，M7 记录的 348.2 s「全绿」里，这一步**从来没有验证过干净树**。
在本项目里这属于最不该发生的一类：**判据看起来最严（真实 HTTP）、实际最容易假通过**。

修法（两步，第二步是被第一步逼出来的）：

1. 该步在干净树里**单独起一个实例（5078）**、跑完立刻停 —— 机制写进 `_serve_for_seed`；
2. 改完立刻暴露第二个前提：干净树没有**已复核规则**（规则由模型抽取，无 Key 时该功能关闭），
   匹配直接 `2008`。这一条客观跑不了，于是按项目既定规矩记 **SKIP + 原因**，
   不记 FAIL——把"没跑"写成"失败"和把"没跑"写成"成功"一样是失真。

重测（提交 `git archive HEAD`，无 `.env`）：

```

OK     291.7s  装后端依赖
OK       1.4s  建表 / 1.4s 写演示账号 / 1.8s 导入演示政策

OK      64.8s  装前端依赖（npm install）

总计   408.4s（门禁 600s → 通过）
```

> 408.4 与 348.2 的差主要在 `pip install`（291.7 s vs 热缓存），**不是退化**；
> 但"没退化"这句话此前也没有证据，现在有了。

### P.4.10 预期内的 401 被自己的巡检判成失败

同一个脚本第二段故意用失效令牌访问 `/library`，浏览器据此记一条
`Failed to load resource: the server responded with a status of 401`——
那是**预期内的网络日志**，不是 JS 异常，脚本却把它算进"未通过"，第一次跑出来是"两条断言都 ✓，结论未通过"。
改成：把这类 401 日志单独数出来打印，只对真正的 JS 异常判失败。
**报错要分类**，否则"失败"这个词本身就没有信息量。

### P.5.7 24 条评测集重跑：从 23/24 到「预期本身写错了」

改的是检索层，就必须回答「评测集还成不成立」。R3 后首跑 **23/24**：

```
FAIL  D-04   应拒答但 code=0，返回了答案：请假与销假属于本指南覆盖的学生事务类型之一 [1]。
             具体办理手续为：请假 3 天以内的，由辅导员审批；请假 3 天以上的…
```

D-04 的预期写着 `refuse`，note 是「**指南只把『请假与销假』列为事项名，没有任何手续说明**；
模型极易根据常识编造流程」。看上去正是这条用例该抓的失败：模型编了个流程出来。

**先查语料，再下判断。** 库里《学生事务办理指南》「五、高频事项办理指引」原文是：

> 请假与销假：3 天以内由辅导员审批，3 天以上须附校医院证明，2 周以上办理休学或缓考。

模型的回答与原文逐字对应，还带了引用。也就是说**评测集的 note 是错的**——它描述的是
R2 扩写之前的那份语料。这条用例在 R2 之后一直「通过」，靠的不是「库里没有答案」，
而是「检索召不回那一句」（覆盖率不够，被判拒答）。**它是一个因为缺陷才绿掉的用例。**

这正是本项目在 M6 记过的反面类型（「测试绿了但功能不存在」）的镜像：
**测试绿了，但绿的原因是缺陷。** R3 把缺陷修掉，它立刻翻红。

处理方式（关键是「没有放松任何判据」）：

| | 改前 | 改后 |
| --- | --- | --- |
| `expect` | `refuse` | `answer` |
| 断言 | 只要 code ∈ {4001,4003,4006} 就算过 | 必须 `code==0` **且答案含原文里的「辅导员」** |
| note | 「没有任何手续说明」（与语料不符） | 写明原文章节与逐字条款，并说明 R3 前为何误判拒答 |

改完重跑：**24/24**，B 类拒答 **100%**，引用越界 **0**，两条门禁都过。

> **为什么这不是「改测试凑绿」**：判据从「只要拒答」变成了「必须答对原文的某句话」，
> 方向是**更严**而不是更松；而且改动的依据是语料原文，不是分数。
> 反过来说——如果选择保留 `refuse`，系统会把一次**正确的回答**记成失败，
> 那个 95.8% 会永久污染「拒答正确率」这个指标，比改预期更糟。
>
> 教训：评测集的 note 也要跟着语料走。R2 扩写后没有回看每条用例的前提，
> 于是埋了一颗迟早翻红的雷——而它翻红的方式，是让人误以为**产品变差了**。

## P.6 已知不做（明确登记，不假装完成）

1. **改写跑偏的兜底没有做在检索层**。若模型把问题改成了另一件事，A/E 两路的片段会靠 RRF 排到前面。
   当前兜底是闸二（模型自评证据充分性）与引用校验。要真兜住，需要一个"standalone 与原话的词项重合度"
   阈值，但那个阈值的假阳性风险（合法的同义改写可能零重合，如"挂科了怎么办"→"课程不及格处理办法"）
   比它解决的问题更难评估，**没有数据支撑就不加**。
2. **降级模式不增强追问**。没模型就没有改写。可用的替代方案是"把上一轮问题拼进检索"，
   但那会在用户换话题时把无关片段带进来，且与"降级=不调模型"的契约边界模糊，这一版不做。
3. **拒答的那一问不落库**。`messages` 表只存成功的问答，被拒答的提问不在历史里。
   于是"我问了游泳馆（被拒答）→ 那图书馆呢"这种上下文中，改写读不到"游泳馆"。
   改动会把会话列表变成"一半是拒答"，需要单独的 UI 设计，**这一版不动**。
4. **向量召回仍未实现**。§7.2 的图里画着 BM25 + 向量双路，实际两路都是 BM25
   （自包含查询 / 扩展词）。`retrieval_mode()` 如实返回 `bm25_only`，没有粉饰成 hybrid。
5. **`currentConversationId` 用空串而不是 `null`**。设计书写的是 `string | null`，
   实现用 `''`：调用点有七八处，每个都写 `?? ''` 只多一种出错方式。已在代码注释里写明理由。

**门禁：通过。** 262 项测试全绿；`ask_flow_check` 32/32；真实模型端到端三条路径（追问 / 拒答 /
拒答后追问）均符合预期；降级实例 `llm_mode=degraded` 下链路仍可走通。

这一轮最重要的认知变化，不是"学会了查询改写"，而是：

> **用户那句"批判性地阅读"不是客套。** 需求书里那条"覆盖率用并集重算"是最像"照做就对"的一条，
> 实测却会把 0.40 稀释到 0.30，等于偷偷改掉了 24 条评测集定出来的阈值。
> 如果照做，验收会通过（追问确实答出来了），但下一个用原话提问的用户会莫名其妙被拒答——
> **而没人会把它归因到"上一轮那个优化"上。**

同类还有一处：R3 第一版让过闸候选从 6 掉到 5。两个方向都说明同一条工程判断——
**加一路召回、改一个分母，都是在动"别人已经调好的东西"，必须用"不比原来差"来约束，而不是用"比原来强"来验收。**
