## Y.1 目标

用户的原话（节选）：

> 请在现有「知校——校园政策智能理解与事务规划系统」中，新增并完善「校园事务指南」功能模块。
> ……这一模块的目标是把现有政策知识库中的政策文件与知识片段，转化为面向学生的结构化校园事务指南，
> 让学生不必每次都通过 AI 提问，也能主动浏览……
> 优先使用现有 documents、document_chunks、policy_rules，不重复建政策库；
> 每条指南必须能关联到真实存在的政策文件；无政策依据不得编造，可显示「暂未收录相关政策」；
> 缺资料显示友好空状态，不生成虚假指南；指南内容支持后续更新，政策变化能及时反映。

| 需求 | 表面看 | 实际牵连 |
| --- | --- | --- |
| 把知识库变成"指南" | 建一张 `guides` 表，把内容写进去 | 一旦落表就有**第二份真值**：政策换版、条款修订、文件下架，指南不会自己跟着变。用户第 5 条要求的"支持后续更新"会变成"每次都要人改两处" |
| 每条指南必须关联真实文件 | 存个 `document_id` 外键 | 文件被软删/被新版替代时，外键还在、内容已经过期；且 `document_id` 是运行时 UUID，**写死在代码里就意味着换库即全断** |
| 无依据不得编造 | 空数据时显示"暂无" | 空的成因有三种（库里没这文件 / 文件没正文 / 文件被替代），提示一句话会让人分不清"知识库缺资料"和"系统坏了" |
| 五个分区 + 三个动作 | 前端排五个卡片和三个按钮 | 三个动作全都能一键跳到既有页面，但**能不能跳**取决于该文件有没有已复核的规则——不做预判就是让用户跳过去撞 `2008` |

**这一轮的核心判断**：用户要的是"指南"这个**界面**，不是"指南"这张**表**。所以正确做法是
**只建编目（指向），正文每次请求时从 `document_chunks` 现取**——零迁移、零复制、天然随政策更新。

> 这句话不是文字游戏。如果建了表，用户第 1 条约束（优先用现有三张表、不重复建政策库）就只在
> "不复制原文"这一层成立，而在"内容会过期"这一层不成立；而 R12 的需求里同时写着"政策变化能及时反映"，
> 两者在落表方案里必然打架。

## Y.2 我发给 AI 的完整 Prompt

**用户原文**（五节结构，此处按原文照抄，仅去掉重复的空行）：

> 请在现有「知校——校园政策智能理解与事务规划系统」中，新增并完善「校园事务指南」功能模块。
>
> [功能定位]
> 目前系统已经具备政策知识库、政策问答、资格匹配、事务规划、任务管理等功能。本次希望新增一个面向学生的「校园事务指南」模块，把现有政策知识库中的政策文件与知识片段，转化为面向学生的结构化校园事务指南，让学生不必每次都通过 AI 提问，也能主动浏览"我这个事项该看哪份文件、要满足什么条件、要准备什么材料、大概怎么办理"。
>
> [功能设计]
> 1. 在系统左侧导航中增加「校园事务指南」入口，位置与「智能问答」「资格匹配」等保持一致。
> 2. 指南首页采用"分类 + 事项卡片"结构，分类包含但不限于：奖学金与助学金、评奖评优、考试与等级考试、学籍与成绩、宿舍与校园生活、图书馆服务、就业与实习、请假与证明办理。
> 3. 每个分类下展示具体事项卡片。每个事项至少包含：事项名称、简短介绍、适用对象、主要申请条件、需要准备的材料、办理流程、相关政策文件、政策有效状态。

> [页面设计要求]

> [开发要求]

> 2. 不要为了完成任务而更换技术栈（Vue3 + Vite + TypeScript + Flask + SQLite 保持不变）。
> 3. 不要删除、清空、覆盖现有数据。
> 4. 优先复用已有组件、接口、数据模型，新增功能要与现有代码风格一致。
> 5. 不要为了"看起来丰富"而写死假数据、假接口、假页面。所有展示内容必须来自真实数据和真实逻辑。
> 6. AI 功能必须真实调用模型或真实规则，不能只做静态演示界面。
> 7. 不要破坏已实现的核心能力：政策引用溯源、资格匹配三态判断、计划草稿与确认、任务状态管理、工作流执行记录。

### 我对 Prompt 的理解

第 5 条约束（"不要写死假数据"）和第 2 条数据要求（"必须能关联真实文件"）合起来，把
"给 32 个事项各写一段介绍文案"这条最省事的路堵死了：文案一旦写进代码，
它和 `documents` 表里的政策就没有任何约束关系，文件下架了它还在。

第 1 条数据要求（"不重复建政策库"）与第 5 条（"政策变化能及时反映"）合起来，
把"建 guides 表 + 灌一份副本"这条路也堵死了。

所以剩下的形状只有一个：**代码里只存"这 32 件事各自该看哪份文件的哪一章"，
正文在请求时取**。这不是我为了"优雅"选的方案，是四条约束的交集只剩这一个。

## Y.4 我的判断与修改

这一节记**AI（我自己）给出的第一版方案里，哪些是错的**。R12 的失败全部集中在
"从 PDF 文本里切出人话"这一段——`app/guides.py` 的解析函数改了四轮。

### Y.4.1 第一版：按"上一行有没有句号"合并硬换行 → 把三条材料拍成一句

PDF 抽出的正文按**版心宽度**硬换行，一句话会被切成好几行；同时清单项本来就一行一条。
第一版的合并规则是"上一行不以句号/分号结尾就与下一行合并"，判据看起来合理，实测结果：

```
身份证件仅需核验，不留存复印件成绩单须为教务系统导出并带验证码委托他人办理还须附委托书
```

三条原本独立的材料被拍成了一句——学生照着这份清单准备，会以为"三样东西缺一不可、
而且必须一起去办"。

**改法**：换判据。被切断的行一定**排满了版心**，清单项则长短不一。所以先量版心：
取所有 ≤45 字符的行里最长的那条当版心宽度，只有长度 ≥ 版心 − 2 的行才可能是被切断的。

```python
lengths = [len(line) for line in lines]
narrow = [length for length in lengths if length <= 45]
width = max(narrow) if narrow else max(lengths)
threshold = max(width - 2, 30)
```

**改法本身又错了一次**：最初取"所有行里 ≤45 字符的最长行"，示例数据里有一条 70 字的长行
（本身已是两行拼合的结果），把阈值抬到 66，于是一条都合不上，段落变成一行一句的碎片。
所以 `narrow` 必须先过滤掉超长行再取 max。

### Y.4.2 第一版：章节名等值匹配 → 首行标题带着"示例大学"前缀

`_clean()` 要去掉片段正文开头的文件标题行。第一版写的是 `lines[0] == doc_title`，
而实际首行是 `示例大学学生事务办理指南本指南适用于…`（标题行和正文被切在同一个 chunk 里），
等值比较永远不成立，"示例大学学生事务办理指南"被当成正文第一句渲染出来。

**改法**：`lines[0] == doc_title or lines[0].endswith(doc_title)`，顺便把"第二条"这种条文号前缀剥掉。

### Y.4.3 第一版：整章取用 → 同一章写四件事，请假卡片里出现"成绩单"

《学生事务办理指南》的「三、材料要求」和「五、高频事项办理指引」是**一章写四类事务**的写法。
第一版按章节名整章取，结果请假卡片里出现了"在读证明需…""成绩单须…"——学生读到会以为
请假要带成绩单。

**改法**：加 `lines` 字段做行筛选（`{"steps": "请假"}`），只保留含关键词的行；
一行都没命中就退回整章（宁可多给，不可少给——关键词写错是我这边的问题，不该让用户看到空白）。

请假那条还要额外关掉材料：那把材料是**四类事务通用**的，列在请假卡里会被误读成"请假必须带这些"。
所以引入语义 `sections[field] = ""` = **明确不取**（与 `None` 的"没指定，走自动匹配"区分开）：

```python
section = spec["sections"].get(field)
# 空字符串 = 该事项明确不取这一节；None 才是"没指定，走自动匹配"
if section == "":
    continue
```

### Y.4.4 第一版：材料与常见问题自动匹配 → 推免卡片的"材料"变成一串问句

《推免办法》第五章叫「材料清单与常见问题」，材料与问答合在一章。自动匹配 faq 时
把整章抓过来，于是第十二~十四条（材料）被当成问题列进了"常见问题"。

**改法**：`sections={"faq": ""}` 显式关闭，同时 `articles={"materials": "第十一条"}`
把材料精确切到那一条。**这是 `""` 与 `None` 必须区分的直接原因**——同一个字段上，
"不要"和"没指定"是两件事。

### Y.4.5 第一版：条件与步骤同章 → 同一段原文展示两遍

缓考、勤工助学等事项的"申请条件"和"办理步骤"写在同一章里，两个字段都命中同一个 chunk，
页面上出现两块标题不同、内容一字不差的卡片，读者会以为自己读了两节。

**改法**：用 `(section, article)` 签名去重，保留第一次出现，后面记进 `duplicate_fields`，
前端给一句解释（"办理步骤与申请条件在原文中同属一章，已合并展示"）而不是重复渲染。

### Y.4.6 第一版：`页$` 匹配页码 → 「第 5 页 / 共 5」漏网

`_PAGE_RE` 原本是 `页$`，实际页脚是 `第 5 页 / 共 5`（末尾还有空格），永远匹配不上，
每块正文的末尾都粘着一行页码。改成：

```python
r"^第\s*\d+\s*页\s*/\s*共\s*\d+\s*页?$"
```

### Y.4.7 验收脚本自己的三处误报（不是代码错）

| 断言 | 误报原因 | 改法 |
| --- | --- | --- |
| "正文里没有 PDF 页眉页脚" | 扫了 `.main-col` 全文，"第 2 页"来自**合法的出处标注** | 只扫 `.policy-text`，并查"共 N 页"与"/ 共" |
| "URL 带 document_id 且下拉框已选中" | `select` 的选项是 `loadDocuments()` 之后才填的，早读拿到 0 个 option | 先 `wait_for(options.length > 1)` 再读 `.value` |
| "卡片同时给出条件 / 材料 / 流程三行" | `.item-card` 先命中了「常用事项」区的 `.item-card.compact`（它没有三行摘要） | 选择器改 `.item-grid:not(.compact) .item-card` |

第三条尤其值得记：**同一个类名被用在两个展示密度不同的区块上**，选择器不写全就会
测到不该测的那个。这是 R11"选择器过期"的另一种形态——不是过期，是**过宽**。

## Y.7 已知不做 / 遗留

- **C-19（新增）**：编目是人工的。`GUIDE_ITEMS` 里的 32 条需要人工填写"哪份文件的哪一章"，
  新政策入库后**不会自动变成事项**。代价写明：入库到指南可见之间隔着一次编目提交。
  为什么不做自动：事项是业务单元（"国家励志奖学金申请"），规则是条款单元（"绩点 gte 3.5"），
  自动反推会把"申请条件"和"整件事"混为一谈。
- **`career` 分类只有升学方向**：知识库里收录的是推免、考研、出境交流；就业招聘与实习类
  政策尚未入库。后端在该分类上带 `note` 明说，前端分类卡显示"暂未收录相关政策"而不是空白。
- **`check_r12.py` 会写库**：它为了验证"草稿能确认、刷新还在"必须真的确认一条计划，
  因此每跑一次留一条数据。正确做法是跑完自清理，或指向一次性测试库——本轮没做，
  用"手工清理 + 登记"兜底。
- **搜索只做子串匹配**：`q` 在标题、简介、分类名、关键词、文件名上做 `lower()` 子串匹配，
  没有分词、没有同义词（"四六级"能命中"大学英语四六级考试"，"CET"不能）。

## Y.9 结论

**门禁通过**：后端 341 项全绿、前端类型检查 0 错误、构建通过、浏览器 42/42。

本链最重要的一条认知变化：

> **"新增一个模块"不等于"新增一张表"。**
> 用户要的是指南**这个界面**，不是指南**这份数据**。当"展示内容必须来自真实数据"
> 与"政策变化能及时反映"同时成立时，唯一解是让新模块**没有自己的数据**——
> 它只持有"指向"，内容永远跟着源走。这样"不重复建库"不是靠自律，
> 是结构上就没有第二份可以写歪的副本。

第二重要的一条：**同一字段上"不要"和"没指定"必须能区分**（`""` vs `None`）。
第一版把两者混为一谈，代价是推免卡片的材料区变成一串问句、请假卡片里多出成绩单。
一个 `continue` 的位置，决定的是学生会不会按错的清单去准备材料。
