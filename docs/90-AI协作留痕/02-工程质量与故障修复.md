## 链 D ｜ 2026-11-07 ｜ M1 ｜ 文档体系的三类质量缺陷与逐类修复

### D.1 目标

设计说明书与配套文档产出后，必须满足三条可机器校验的条件：

1. 全部 `json` 代码块能被 `json.loads` 解析（否则评审复制示例即报错）；
2. 全部 Mermaid 图能被渲染器解析（否则 GitHub 上显示为乱码）；
3. 文档内所有"数量类"结论必须与内容实算一致（接口数、表数、用例数）。

### D.2 我发给 AI 的完整 Prompt

> **[第 1 轮]**（任务提出）
> 请你先阅读我上传的四张图片，让你先对本次传智杯"AI创新应用挑战赛"的比赛有初步了解，再结合文件夹中的"01-项目介绍文档.md"与"02-项目实施整体框架步骤文档.md"，完成对我的"校园政策理解与智能事务规划系统"的初步认识并理解该项目的整体实施框架。最后输出系统设计说明书以及readme文件。

> **[第 2 轮]**（硬约束追加，因第一轮被打断）
> 请你严格按照我的要求完成任务，先不要进行代码的编写

> **[第 3 轮]**（验收要求）
> 请你根据你得出的结论，对文档进行修改……请您先对最基础的文件进行改版升级，得出最终的一系列系统设计规划实施所需要的文档，

### D.3 AI 的关键输出与自查动作

- 产出设计说明书 V1.0（22 章 + 3 附录）与 README，随后**主动编写校验脚本**而非肉眼检查：
  - 用正则抽取全部 ` ```json ` 块，逐个 `json.loads`；
  - 统计 ``` 围栏数量是否为偶数（防止代码块未闭合）；
  - 用正则扫描 Mermaid 中未加引号且含 `/ : ()` 的节点标签；
  - 用 `grep -c` 逐行统计接口清单行数。
- 自查结果：**一次就查出 3 类问题**，而非"生成后宣告完成"。

### D.4 我的判断与修改

| 处理 | 内容 | 理由 |
| --- | --- | --- |
| 采纳 | 用脚本校验而不是目视检查 | 目视会漏；脚本可复跑、可写进 CI |
| 要求 | 把校验脚本固化下来，每次改文档都跑 | 防止后续修订再次引入同类缺陷 |
| 纠正 | 接口数从"29 条"改为 **30 条** | AI 首版是估算值，逐行统计才能定论 |
| 否决 | 直接把 JSON 示例删掉以规避校验 | 示例是契约的一部分，删掉等于降低交付质量 |

### D.7 遇到的问题与修复过程（关键：一次改完仍失败）

> **现象**：第一次修完 D-1 后以为通过，重跑脚本仍报 `bad=1`。
> **定位**：脚本输出没有行号，改用"逐行 grep 关键词"策略——先列出所有含中文引号的可疑行，再逐条比对。发现是**两处**同类缺陷（`caveats` 与 `suggestions` 各一处），第一次只改了一处。
> **教训**：校验脚本必须报行号或上下文，否则"修一处漏一处"会反复发生。此后所有校验脚本都输出 `[序号] 失败原因`。
> **最终验证**（真实输出）：
> ```
> docs/系统设计说明书.md: json=8 bad=0 fences=48 lines=1551
> README.md: json=0 bad=0 fences=… lines=…
> ```

## 链 E ｜ 2026-11-07 ｜ M0 ｜ Git 推送静默失败：两个被证伪的假设

### E.1 目标

把本地 8 次提交推到 `https://github.com/liqing-258/campus-policy-planner`，并**证明远程内容与本地逐字节一致**——不是"命令没报错就算成功"。

### E.2 我发给 AI 的完整 Prompt

> **[第 1 轮]**
> 请你阅读一下"D:\私人\学习\大三上\物联网应用软件开发"这个路径下的文件夹的文件……请你根据"D:\私人\学习\大三上\物联网应用软件开发"这个路径下的文件，明确我们这个"校园政策理解与智能事务规划系统"的项目实施基本流程，再根据"03-WorkBuddy分阶段完整提示词文档.md"这个文件中描述的项目总控提示词，完成本次任务

> 我的GitHub仓库个人访问令牌是：（略，已作废）

> **[第 2 轮]**（仓库改名 + 新令牌）

### E.3 AI 的关键处理

按顺序做了 5 件事，其中 2 次是**先提出假设、再被自己的验证结果推翻**：

| 步骤 | 动作 | 结果 |
| --- | --- | --- |
| 1 | 首次直接 `git push` | **静默挂起**，无任何输出，最终被 SIGTERM 终止（`exit=1`） |
| 2 | 假设"网络或权限问题" | ❌ 被证伪：`git ls-remote` 同一地址可正常返回 |
| 3 | 判定为 Windows 凭据管理器弹窗吞掉进程 | ✅ 加载 `git-push-remote-sandbox` 技能，按其流程处理 |
| 4 | 改用 `GIT_TERMINAL_PROMPT=0` + `GCM_INTERACTIVE=never` + **空 credential.helper** + 一次性 URL 注入令牌 | ✅ 推送成功 |
| 5 | 校验远程 ref | ❌ 又出问题：`fetch` 打印 `[new branch]`，但 `git show-ref` / `git branch -r` 均为空，`status` 显示 `[gone]` |

### E.4 我的判断与修改

| 处理 | 内容 |
| --- | --- |
| 采纳 | 不把令牌写进 `.git/config`，改用一次性 URL；用完立即删临时凭据文件 |
| 采纳 | 用 `--force-with-lease=refs/heads/main:<期望sha>`，**指定期望值再覆盖**，而非 `-f` |
| 要求 | 必须做**逐 blob 哈希比对**，不接受"push 没报错"作为成功判据 |
| 保留 | 把两个失败假设都写进留痕，不删 |

### E.5 改动的文件

无业务文件改动；仅 `.git/` 内部引用（不入库）。

### E.6 问题定位与修复（第二处更隐蔽）

> **现象**：`git fetch` 输出 `* [new branch] main -> origin/main`，看起来成功了。
> **反证**：接着查 `git show-ref` → 空；`git branch -r` → 空；`ls .git/refs/remotes` → 空。
> **定位**：Windows 下 `refs/remotes/origin/main` 是 4 层深路径，Git 写入时**静默失败但返回 0**。fetch 打印的 `[new branch]` 来自 `FETCH_HEAD`，不代表远程跟踪引用已创建。
> **修复**：直接从 `.git/FETCH_HEAD` 读到提交 sha，手工写入 `.git/packed-refs`：
> ```
> # pack-refs with: peeled fully-peeled sorted
> <sha> refs/remotes/origin/main
> ```
> 之后 `git status -sb` 从 `[gone]` 恢复为 `main...origin/main`。
> **验证（这是关键一步）**：不用 Git 自证，改用 GitHub API 取远程树，与本地 `git ls-tree -r HEAD` **逐文件比对 blob sha**：
> ```
> 远程 blob 数=15  本地 blob 数=15
> 仅远程有: 无   仅本地有: 无   内容不一致: 无
> 结论: ✅ 完全一致
> ```
> **安全复验**：`grep -rl "ghp_" .git/` → 无命中；`git ls-files --error-unmatch .env` → 报错（未被跟踪）。

### E.7 被证伪的假设（保留，不删）

| 假设 | 为何看起来合理 | 被什么推翻 |
| --- | --- | --- |
| "push 失败是网络/权限问题" | 命令零输出、exit=1，很像连不上 | 同机 `ls-remote` 正常，说明连接没问题 |
| "fetch 打印 new branch 就算写入成功" | Git 自己说 `[new branch]` | `show-ref` / `refs/remotes` 目录均为空 |

> 这两个假设如果没被推翻，后果是：**你以为推上去了，评审 clone 下来发现 `origin/main` 不存在，或者你以为 8 次提交都在，实际只有 1 次。** 这也是为什么 §E.6 的逐 blob 比对不能省。
