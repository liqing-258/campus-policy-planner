| # | 产出 | 关键决策与理由 |
| --- | --- | --- |
| 1 | `app/parsing.py` | PDF 用 `import pymupdf`（不用已弃用的 `fitz`）；`doc.needs_pass` 显式判加密，报"需要密码"而不是"解析失败"。**扫描件判据用"页数 × 每页均字符 < 阈值"**，不用"是否含图片"——带一页插图的正常 PDF 不该被误判 |

## I.4 人工干预记录（AI 出错、被纠正的地方）

这一节是"如何引导 AI 修复 Bug"的直接证据。**每条都是真实发生过的**，保留错误现场。

### I.4.1 参数改名没改函数体，所有 PDF 解析全挂

`app/parsing.py` 里 `_Builder.add()` 的参数从 `page` 改名为 `page_number`（为了可读性），但函数体里还用着 `page`：

```python
def add(self, text, page_number, *, is_heading=False):   # ← 参数改名了
    ...
    if not text:
        return
    ...
    self.blocks.append(Block(
        text=text,
        page_number=page,        # ← 函数体里还是 page → NameError
        ...
    ))
```

结果：**所有 PDF 上传后 `parse_status=failed`**。表面症状是"解析器坏了"，实际是一个拼写问题。

修复后该行是 `page_number=page_number`。

### I.4.2 兜底异常把原因吞掉了，导致上面那个 bug 多花了一轮

第一版的兜底捕获是：

```python
except Exception as exc:
    return ParseOutcome(status=PARSE_FAILED, error=f"解析过程出现未预期错误：{type(exc).__name__}")
```

提示变成"解析过程出现未预期错误：NameError"——知道是 NameError，但**不知道是哪个名字**。所有 PDF 都是这一句，无从下手。

修复：`f"解析过程出现未预期错误（{type(exc).__name__}: {exc}）"`，立刻显示出 `name 'page' is not defined`，一轮定位。

**教训**：兜底处理的目标是"让人能修"，不是"让人知道出错了"。只报异常类型等于没报。这条已固化为项目惯例：**所有 except 分支必须带 `exc` 的字符串内容**。

### I.4.3 章节标题识别过宽，949 字的文件被切成 33 个碎片

第一版把「第X条」也当章节标题，于是每一条都成了独立章节：

```
原文 949 字 → 33 个片段，平均 28 字，最短 6 字
```

6 字的片段（比如"第四条 申请"）对检索毫无价值——它丢掉了上下文，还污染了 idf 统计。

修复：拆两级标题 + 两条硬约束（长度 ≤30、不以`。；：，`结尾）。修复后同一份文件：

```
949 字 → 4 个片段，长度 202 / 264 / 252 / 227 字，页码 1/2/3/4，章节名全部正确
```

### I.4.4 DOCX 把所有 Heading 级别都当章节边界

`python-docx` 的 `style.name` 里，`Heading 1`…`Heading 9` 都含 `Heading` 字样。第一版用 `"heading" in name.lower()` 判断，于是文档里任何一个小标题都切一刀，指南被切得七零八落。

修复：只认 `heading 1` / `标题 1` / `title` 三档。

### I.4.5 `min_section_chars=120` 把整篇指南合并成一个片段

为了防止 I.4.3 那种碎片，加了"短章节优先合并"策略，但阈值取 120，结果 484 字的指南**每个章节都低于阈值，全被合并**：

```
484 字指南 → 1 个片段，章节线索全部丢失
```

修复：阈值降到 40。修复后：

```
6 个片段，长度 41 / 52 / 108 / 78 / 62 / 137 字
章节为：文档标题（41字独立成段）、一、事项范围、二、办理流程、三、材料要求、四、时限与费用、五、办理时限一览
```

> 这两个方向相反的 bug（切太碎 / 合太狠）说明：切分参数没有"正确答案"，只有"在某类文档上合适"。
> 40 这个值是在 2 份演示文档上试出来的，**不是调优结果**，M4 建评测集时要一起复验。

### I.4.6 状态机白名单挡了自己的路

`shared/enums.py` 第一版：

```python
PARSE_PARSED:  (PARSE_CHUNKED,),
PARSE_CHUNKED: (PARSE_INDEXED,),
```

`reparse` 要从 `parsed` / `chunked` 回到 `parsing` 重建，被白名单拦下。当时的"解法"是把状态先复位成 `uploaded`——**这等于绕过状态机，把守卫变成了装饰**。

修复：白名单显式加上 `PARSED → PARSING`、`CHUNKED → PARSING`，并在注释里写明理由。原则：**遇到守卫拦路，先判断是守卫错了还是路径错了，不要绕过守卫**。

### I.4.7 演示扫描件 4.18 MB

第一版 `dpi=120` + PNG 产出 4.18 MB 的"一页扫描件"，提交进仓库纯属自伤。

修复：`dpi=72` + JPEG → 17.8 KB（18271 字节）。同一份文档，文件小 235 倍，仍然能验证"无文本层"这件事。

### I.4.8 验收脚本自己写错了字段名

`tools/e2e_gate.py` 第一版取登录令牌写的是 `data.access_token`，而真实响应是 `data.token`，于是脚本报"登录失败，先跑 seed_demo"——**而这个账号明明存在**。

同一次还暴露第二个问题：脚本在登录失败时 `raise SystemExit(1)` 直接退出，`finally` 里杀了服务，但**汇总表没打印**，什么都没看到。

修复：字段名改正；提前退出改用自定义 `_Abort` 异常，`finally` 之后统一打印汇总。同时给脚本加了"用一次性临时库"的隔离，否则第二次跑会撞 SHA-256 去重。

**教训**：验证脚本本身也会错，而且**它的错会被误读成"被测系统错了"**。所以脚本的失败信息必须足够具体（"HTTP 415，期望 400"），不能只说"失败"。

## I.5 一个推翻了原设计的实测发现：BM25 分数不能判断相关性

这是本里程碑最重要的一件事，也是**唯一一处 AI 的测试断言与算法真实行为不符、最终以算法行为为准并改了设计的地方**。

### I.5.1 事件经过

写 `tests/test_indexing.py` 时，我按设计说明书 §6 的意图写了一个用例：

```python
def test_search_returns_empty_for_unrelated_query():
    """无关问题必须返回空——M4 的拒答就建立在这个行为上。"""
    index = Bm25Index().build(_sample_rows())
    assert index.search("转专业学分认定流程") == []
```

跑出来红了：

```
AssertionError: assert [SearchHit(chunk_id='c1', ..., score=1.7997),
                        SearchHit(chunk_id='c2', ..., score=0.9253)] == []
```

### I.5.2 第一反应（错的）：加个阈值就行

`.env.example` 里本来就预留了 `RAG_MIN_SCORE=0.35`。最省事的做法是给 `search()` 加 `min_score=0.35`，红的立刻变绿。

**但先实测了分数分布，结果直接否掉了这个方案**：

| 查询 | 是否相关 | 最高分 | 命中词项 |
| --- | --- | --- | --- |
| 国家励志奖学金 申请条件 | ✅ 相关 | 3.4398 | 国家/励志/奖学金/申请/条件 |
| **转专业学分认定流程** | ❌ **无关** | **1.7997** | 专业/学分 |
| **保研推免条件** | ❌ **无关** | **1.4509** | 条件 |
| **申请要交哪些材料** | ✅ **相关** | **1.3687** | 申请/材料 |
| 成绩单 材料 | ✅ 相关 | 1.3687 | 成绩单/材料 |
| 宿舍水电费怎么交 | ❌ 无关 | 无命中 | — |

**无关查询的分数比相关查询还高。** 阈值 0.35 唯一能筛掉的是"零命中"那一行——它解决的问题，本来就不需要阈值。

### I.5.3 原因

BM25 的分数是"命中词项的 idf 加权和"。它奖励的是**命中了罕见词**，而不是**回答了问题**：

- 「转专业学分认定流程」命中了「专业」「学分」两个在奖学金文件里算罕见的词 → idf 高 → 分数冲上去；
- 「申请要交哪些材料」命中的「申请」「材料」在这份语料里到处都是 → idf 低 → 分数反而低。

换句话说：**BM25 衡量的是"字面重叠的稀有程度"，不是"语义相关性"。** 这是词袋模型的固有性质，调参调不掉。

### I.5.4 改成了什么

不再用绝对分数做闸门，改为输出**关键词覆盖率**（`coverage` = 命中的查询词项 / 查询词项总数），并把闸门做成显式参数：

```python
def search(self, query, *, top_k=6, document_ids=None,
           min_score=0.0, min_coverage=0.0) -> list[SearchHit]:
```

默认 0（不过滤），保持"检索永远给候选"的原始语义；要不要拒答由调用方决定。

同一批查询实测覆盖率：

| 查询 | 相关？ | coverage |
| --- | --- | --- |
| 国家励志奖学金 申请条件 | ✅ | 1.00 |
| 家庭经济困难认定需要什么材料 | ✅ | 0.83 |
| 成绩单 材料 | ✅ | 1.00 |
| 申请要交哪些材料 | ✅ | 0.67 |
| **转专业学分认定流程** | ❌ | **0.50** |
| **保研推免条件** | ❌ | **0.33** |

**这次分开了**：相关 ≥0.67，无关 ≤0.5。`RAG_MIN_COVERAGE=0.6` 取在中间。

同时把排序键从 `score` 改成 `(coverage, score)`。在真实的 10 片段演示库上立刻见效：

```
问题：家庭经济困难认定需要什么材料
1. score=6.0058  coverage=0.8333  第4页 / 第四章 申请材料与附则   ← 排第 1
2. score=6.8427  coverage=0.6667  第2页 / 第二章 申请条件         ← 分数更高但排第 2
```

第 2 名分数 6.8427 > 第 1 名 6.0058，但只覆盖 4/6 个查询词；第 1 名覆盖 5/6。**只看分数就会把"申请条件"排在"申请材料"前面**——而这正是用户问题问的东西。

### I.5.5 还没解决的部分（如实登记）

1. **单字查询挡不住**：查「转专业」只切出「专业」一个词，覆盖率必然是 1.0，会被判为相关。词袋模型对此无能为力，只能靠 M4 的模型判定兜底。
2. **0.6 没有校准**：这个数是在 3 片段 toy 语料上观察出来的分界，在 10 片段演示库上能正确拒绝「转专业流程」（覆盖率 0.5）。**没有评测集就不叫校准**，M4 必须用 24 条真实问答重新定标。这一点已写进 `.env.example` 的注释和 `app/config.py` 的注释里，避免后来人误以为它是调优结果。
3. **测试断言改了口径**：原用例 `assert search(...) == []` 保留不成立的部分是对的（零交集查询确实返回空），但"字面有交集即无关"这个假设被证伪。现在 `tests/test_indexing.py` 里有两个用例专门记录这件事：
   - `test_raw_score_alone_cannot_tell_relevant_from_irrelevant` —— 断言 `irrelevant.score > relevant.score`，**把这个反直觉事实钉在测试里**，一旦哪天打分逻辑变了（比如换了更好的算法），这条会立刻红，提醒重新评估；
   - `test_coverage_filters_topically_unrelated_query` —— 断言覆盖率闸门确实能筛掉无关查询。

> 这一节的处理原则，和 SOUL.md 里那条"数据里出现反直觉的结果，先回查原始数据；确认是数据本身的特性就照实写清楚它的机制"是同一条。
> 如果当时图省事加个 `min_score=0.35` 让测试变绿，M4 的拒答机制会在第一次实测时全线失效，而且**没人知道为什么**。

## I.7 已知不做的（明确登记，不假装完成）

| 项 | 为什么不做 | 什么时候做 |
| --- | --- | --- |
| OCR | 依赖 tesseract 或商业 API，体积与许可证都麻烦；赛事 11-18 截止，加进来风险大于收益 | 明确不做，文档与提示都写清"本系统不含 OCR" |
| 异步解析 | 单 worker 下异步只增加状态种类，不减少等待；且前端还没上传页 | M7 压测若暴露大文件阻塞再改 |
| `POST /retrieval/search` 接口 | 没有覆盖率闸门的检索接口会让人把"召回 3 条"误读成"有依据" | M4，与拒答机制一起上线 |
| 向量检索 / Embedding | 未配置模型，且 BM25 在 1 万片段量级够用；引入向量需要额外依赖与 API 成本 | M4 视评测结果决定是否加混合检索 |
| 前端上传页 | 单独为上传做一个半成品页面不划算 | M5 随政策知识库页面一起做 |
