# 链 Q ｜ 2026-11-13 ｜ 修复轮 R4 ｜ 点名了哪份文件，就答哪份文件

> 链编号与 `00-AI对话历史总档.md` §3 台账一致。前一条链是 P（追问与会话连续性，R3）。
> 这一轮的触发是一句很短的话——"**你先了解现有代码啥的然后再继续完成任务**"。
> 按要求先读代码，读完发现 **R3 的活确实做完了、262 项测试全绿、24 条评测 24/24**，
> 但"做完"不等于"做对"：在**降级路径**（无 API Key）上，点「继续追问」会拿到**另一个版本**的答案。
> 这一条链记的就是这个发现与修复，以及**顺手查出来的文档对不上账**。

---

## Q.1 目标（一句话）

让"用户点名了哪份文件"成为检索的**硬约束**，而不是一个会被年份稀释掉的查询词；
并且这条规则**不依赖模型**——因为降级模式正是它失效的地方。

拆成三条可断言的条件：

1. **点名即范围**：问句里出现《…》且能对上库内文件 → 候选**全部**来自该文件；
2. **版本要点准**：点名《…（2026年版）》时，2025 版不得出现在证据里；
3. **没点名就一点不变**：普通问句的 `anchor` 必须为 `null`，行为与 R3 逐位一致
   （这是回滚路径，也是"新功能不许改旧行为"的门禁）。

## Q.3 AI 输出摘要（做了什么，以及为什么这么做）

### Q.3.1 先读、再证伪：上一轮的结论只对了一半

读代码的顺序：`app/rewrite.py` → `app/retrieval.py` → `app/qa.py` → `stores/qa.ts` → `AskView.vue`，
再跑全量测试与真实链路。结果：

- R3 的两部分**都真的落地了**（改写、三路召回、三视图闸门、Pinia + sessionStorage、登出清理）；
- 262 项测试全绿、24 条评测 24/24、`origin/main..HEAD` **领先 16 个提交**（上一轮根本没推上去）；
- 但用**降级实例**（`LLM_API_KEY=`）跑前端第一条「继续追问」时，答案指向了**旧版本**。

这就是"读完代码不等于验证过"的现场：代码里每一步都对，**组合起来在降级路径上是错的**。

### Q.3.2 缺陷定位：年份是死词，却占着分母

前端 `followUps` 的第一条是：

```ts
out.push(`《${doc}》里还有哪些与这个问题相关的规定？`)
```

其中 `doc` 是真实文件名 `本科生奖学金评审办法（2026年版）`。检索把它分词后得到
`本科生 / 奖学金 / 评审 / 办法 / 2026 / 年版 / 还有 / 问题 / 规定`——
**"2026" 一次也命中不了**：2026 版的正文只写"本办法"，年份只印在文件名上。
反倒是 2025 版第一章正文里印着"（2025年版）"，于是它撞上了"年版"。

实测（`.workbuddy/probe_degraded.py`，改前）：

```
candidates: [('本科生奖学金评审办法（2025年版）', '第一章 总则', 0.769),
             ('本科生奖学金评审办法（2026年版）', '第一章 总则', 0.692)]
```

2026 版的第二/三/四章覆盖率 **0.308 < 0.35**，全部被闸门挡掉。
也就是说：**用户点名的那份文件，被自己的年份压出了证据窗口**。

### Q.3.3 为什么不在改写里修

改写能救（真实模型下引用全落在 2026 版），但改写**没有模型就不存在**，
而"无 API Key 时链路仍可用"是设计文档写死的降级策略（§7.7）。
在降级下这条缺陷的表现还是最糟的一种——**给出一个版本错误的答案**，而不是拒答。
所以这一层必须是**确定性规则**，放在检索里、与改写解耦：

| 步骤 | 做法 | 代码 |
| --- | --- | --- |
| 抽取 | 取问句里所有《…》 | `anchors.quotes_in()` |
| 匹配 | 全等 / 核心名相同 / 子串（≥6 字），**取最高一档，不并集** | `anchors.resolve()` |
| 改写检索文本 | 书名号换成**核心名**（只删年份/版本括号） | `anchors.residual_text()` |
| 收窄范围 | 只检索被点名的文件；核心名对应多版本时全保留 | `retrieval._fill_by_anchor()` |
| 闸门 | **不适用**，`anchor_gate = document_scoped` | 同上 |
| 留痕 | `anchor` / `anchor_gate` 进 retrieval 节点 detail | `qa._run_pipeline()` |

### Q.3.4 一个刻意的取舍：闸门在"点名"时不参与判断

闸门回答的是"用户问的这个主题，库里有没有"。写了《文件名》之后，这个问题已经被
"那份文件在库里"回答了；残余问法里的词只是在**文件内部指路**。三条前端模板按闸门判全是拒答：

| 模板 | 残余问法 | 被闸门判成 |
| --- | --- | --- |
| 《X》里还有哪些与这个问题相关的规定？ | 还有 / 问题 / 规定 | 0.33 → 拒答 |
| 《X》对办理流程和时间要求是怎么规定的？ | 办理 / 流程 / 时间 / 要求 | 0.20 → 拒答 |
| 不符合《X》规定的情况会怎么处理？ | 符合 / 情况 / 处理 | 拒答 |

三条都是"这份文件怎么规定"的正常问法，所以统一豁免，把"能不能答"交给**闸二（模型自评）**——
这正是 §7.2.1 定过的分工：覆盖率只做粗筛。代价如实写进 §7.2.5 与本文 Q.6。

## Q.4 人工干预记录（出错、被数据打回、测法错的现场）

### Q.4.1 正则写成"恰好 60 字"，锚定一次都没生效——而且**不报错**

```python
_QUOTE_RE = re.compile(r"《([^》]{%d})》" % QUOTE_MAX_CHARS)   # ← QUOTE_MAX_CHARS = 60
```

`{60}` 是"恰好 60 个字符"，正确写法是 `{1,60}`。于是 `quotes_in()` 恒为空，
`anchors.resolve()` 恒为 `None`，整条锚定**静默退化**成普通检索：

```
retrieval anchor: None            ← 看起来像"这个功能没写"，而不是"写错了"
```

现场是我先看探针输出的 `anchor` 字段，发现它一直是 `None`，才回去单测正则。
**这类"功能不生效但不报错"的缺陷，只能靠断言输出字段来抓**——所以最终用例里
第一条就是 `test_quote_is_extracted_with_length_limits`，并且在 docstring 里写明
"这条看着废话，但第一版正是错的"。

### Q.4.2 第一版把书名号整段删掉，把一个能答的问法改成了拒答（自己引入的反向退化）

第一版 `residual = strip_quotes(text)`，实测：

```
《图书馆借阅与自习空间管理办法》对办理流程和时间要求是怎么规定的？
    删干净 → 残余"办理流程和时间要求" → 0.20 → 4001（拒答）
```

书名号里**就带着主题**（"图书馆借阅"）。删干净等于把主语删了。
这和 R3 那次"加了改写、过闸 6→5"是同一类错误：**优化把原本能过的挡在了门外**。
改法是只删年份/版本括号（`residual_text`），核心名留下：

```
    留核心名 → 0.69 → 作答
```

### Q.4.3 `open_query` 判在错误的文本上

开放式问法（"还有哪些规定"）本该按文件顺序摆证据，但第一版把 `residual`（含核心名）
拿去分词，核心名当然"覆盖"得了这份文件自己，于是**永远判成"有主题"**，分支从不触发。

改成两份文本各有分工：`residual`（核心名，用于检索与排序）、`bare`（摘净，用于判断
"用户自己还说了什么"）。这一条也写进了 `with_residual_tokens()` 的 docstring：
**传错文本不会报错，只会让分支静默失效**。

### Q.4.4 一个被数据否掉的设计假设：用"摘净后的覆盖率"裁判相关性

我原本想让 `《X》里关于转专业的规定` 走闸门拒答（转专业不在 X 里），做法是覆盖率只用
`bare` 分词。实测把这个方案否掉了：

```
《X》对办理流程和时间要求是怎么规定的？
    bare 口径 → 0.20（这是系统自己生成的第一条追问模板，不能拒答）
```

同一把尺子，量"该拒的"和"该答的"得到同一个低分——说明**覆盖率在这类问法上就没有分辨力**，
不是阈值问题。于是放弃"用覆盖率裁判文件内相关度"，改为"点名文件即范围，能不能答交给闸二"。
这个假设的墓碑留在 §7.2.5 的"为什么闸门不适用"里。

### Q.4.5 上一轮 16 个提交根本没推上去

`git status -sb` 显示 `## main...origin/main [ahead 16]`。
上一轮结尾写了"已推送"，实际最后一次 `push` 没有成功（commit `a9b01e1` 的 message
甚至在解释"ahead 59 是假警报"）。这一轮把推送当成**收尾动作单独验证**：
`git ls-remote origin refs/heads/main` 与 `git rev-parse HEAD` 必须相等，否则不算完。

### Q.4.6 顺手查出的文档对不上账：README 说 26 条已知限制，正文说 27 条

```
README.md:20    ✅ V1.9（… 26 条已知限制）
README.md:90    **已知限制 27 条**（A 4 / B 12 / C 11）
已知限制.md 头部  共 **27** 条
```

按"先有条目再写数字"的规矩核对：文件里确实是 27 条（B-10、C-9 已关闭但编号保留）。
错的是 README 第 20 行那处，本轮一并改正为 27。**总数没变，所以不新增也不删除条目**，
避免造出"表里有、正文没有"的幽灵条目。

## Q.6 已知不做（明确登记，不假装完成）

1. **"点名文件里没有这个主题"仍不拒答**：问《图书馆办法》里关于转专业的规定，系统会把图书馆的
   片段摆出来，由模型说"证据不足"。理由见 Q.4.4——覆盖率没有分辨力，硬拦会把正常模板一起打死。
   实测代价是"答案里不含用户想要的那条"，不是"编了一条"。
2. **纯指代追问在降级下仍不还原**（B-11 的另一半）：没有模型就没有"它=上一轮那件事"的判断。
   按 R3 的结论不做"拼上一轮问题"的兜底（换话题会把无关片段带进来）。
3. **不改全局分词/停用词**：往 `tokenize` 里加"问题/还有"会改变所有查询的分母，
   等于把 0.35 这个用 24 条评测集扫出来的阈值换了含义。噪音词表只用于锚定层的"开放式问法"判断。
4. **不给锚定加开关**：它不改阈值、不改分词、未命中书名号时行为完全不变，
   回滚路径由"不写书名号"天然成立，再加一个环境变量只会多一个要被解释的状态。

## Q.8 结论

这一轮最值钱的一条不是"加了锚定"，而是**"全绿"≠"对"**：
上一轮 262 项测试全绿、24 条评测 24/24，问题却出在两者都没覆盖的**降级路径**上。
测试覆盖的是"有模型时的问答质量"和"代码对模型输出的处理"，而"没有模型时前端第一条按钮"，
两套验证都不管。

于是这轮的判据换了个方向：**先跑用户点得到的那条路径，再决定改哪里**。
报告里的 24/24 没有告诉我任何关于这个缺陷的信息——它是被"点一下按钮"找出来的。
