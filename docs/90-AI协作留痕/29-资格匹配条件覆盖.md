## AG.2 排查：先排除"最像的"那个，再找真因

用户列了四个怀疑方向（提取 / 审核 / 关联 / 算法）。**逐个排除**：

| 怀疑 | 怎么查 | 结论 |
| --- | --- | --- |
| 匹配算法错 | 读 `matching.run_match`：按 `document_id + review_status=approved + 规则类型` 取数 | 算法没问题，且**不会跨文件取数**（T4.4 验证：两次匹配的规则集合交集为 0） |
| 数据库关联错 | 查孤儿规则（`document_id` 指向不存在/已删文档） | 0 条 |
| 审核状态没更新 | 数 20 条规则的 `review_status` 分布 | 10 approved / 6 needs_review / 4 rejected —— 状态字段本身在正常工作 |
| 提取失败 | **按文档数规则** | **20 条规则全部属于同一份文件**；其余 17 份一条都没有，且没有任何"抽过"的痕迹 |

第四行是分水岭。接下来要分清"没抽过"还是"抽了失败"——**系统里没有这个信息**，
于是直接实测抽取接口。

## AG.3 三个独立的根因

### RC-1：抽取在片段多时必失败（这是"为什么没有规则"的直接答案）

```
《国家助学贷款与勤工助学管理办法》8 片段整篇抽取 → 29.3s → 4002
  "模型只输出了推理内容（reasoning_tokens=6000），正文为空"
同一文档只取前 2 片段                        → 24.9s → 成功 3 条
同一文档整篇 + max_tokens=12000              → 24.1s → reasoning 3213，出 20 条
```

**同一个提示词，只差预算。** 6000 预算下推理恰好把它吃满，`content` 为空。
4 片段的奖学金办法能过，8 片段就过不了——这解释了"为什么偏偏是那一份能匹配"。

### RC-2：上传不触发抽取，失败不留痕

`app/documents.py` 里**零处** `extract`——上传只做解析与索引，抽取是管理员的手动动作。
这本身是设计选择（抽取有成本、要人复核），但配合 RC-1 就致命：**管理员点过抽取也拿不到
东西，而失败在界面上和"从没点过"完全一样**——都是一个 `0`。

### RC-3：「0 条已复核条件」把四种处境压成一个数字

| 真实处境 | 之前显示 | 该谁做什么 |
| --- | --- | --- |
| 从没抽过 | 0 条 | 管理员点抽取 |
| 抽过但失败 | 0 条 | 管理员看原因、重试 |
| 抽到了没复核 | 0 条 | 管理员去复核 |
| 本来就没有申请资格条件 | 0 条 | 标记「不适用」，学生看到明确提示 |

前端还为此付出 18 次请求（逐份文件查规则数）的代价，只为得到那个分不清处境的 0。

## AG.4 修法：只落库两件事，其余全部推导

新表 `document_rule_states`（第 17 张，**零 ALTER**）只存：

1. **管理员「不适用」的判定 + 理由**（人的决定，推导不出来）；
2. **上一次抽取尝试的结果**（发生的事件，推导不出来）。

六种状态其余部分一律现算（`rule_states.derive_state`）：

```
ready > not_applicable > pending_review > extract_failed > no_conditions > pending_extract
```

**顺序不能换位**：

- `ready` 必须压过 `not_applicable`——匹配接口只按规则查，标了"不适用"也照样会跑，
  此时显示"不适用"就是骗人。矛盾以 `conflict=True` 暴露，并在写入时用 `1003` 拦下；
- `no_conditions`（抽了、成功、0 条）必须与 `pending_extract`（没抽过）分开——
  一个该做判断，一个该去点按钮。**实测《食堂与后勤生活服务指南》在新提示词下抽出 0 条
  只用 1.5 秒**（模型"拿不准就不抽"），正是这种状态；
- 不落库理由与收藏同源：状态随规则表变化，落库会在复核后静默过期，而它没有"过期"标记。

## AG.5 修法中撞到的三件事

### ① 抽取出的 `expected_value` 与画像枚举对不上（会把人判成"不符合"）

第一版抽取产出：`disciplinary_record equals "无纪律处分记录"`、`poverty_certified equals "true"`。
画像里存的是 `none` / `yes`。**字符串比较不相等 → 所有学生被判"不符合"**——比不判更糟。

修法不是"复核时手工改"（18 份政策 ×N 条改不完），而是**把取值域写进提示词**：
九个画像字段各自允许的取值 + 一句"塞不进去就填 `manual_review`，不要硬造一个对不上的值"。
重抽后推免的两条直接产出 `gpa gte 3.5` 与 `disciplinary_record equals none`，可直接判定。

实测效果：`manual_review` 的占比明显上升（贷款 5 条资格条件里 3 条），
这是**对的**——那些条款（"全日制本专科 + 家庭经济困难"两个事实塞一个字段）本来就判不了，
硬编码反而制造假结论。**如实登记 C-27。**

### ② 审计写在 `commit()` 之后 = 从未落库

`set_applicability` 第一版：

```python
db.session.commit()
_audit("document.rule-applicability", ...)   # ← 只 add 不 commit，之后再没人提交
```

`_audit` 的设计是"调用方负责提交"（`documents.py` 里都在 commit 前调）。这条路径照抄了
调用姿势却把顺序搞反，**审计行 100% 丢失**。是新增测试里"标记成功后查 `audit_logs` 应为 1"
这条断言（实际 0）抓到的——**如果只测接口返回 `code=0`，这个洞永远不会被发现**。

### ③ 提示词改了但服务没重启 → 两次抽取结果不可比

第二批抽取（含 4 份政策）在改提示词**之前**启动的进程里跑完，随后我改了 `SYSTEM_PROMPT`
又重抽了一遍。若两次结果混在一起，就变成"同一份数据来自两个不同的抽取器"。
处理：**清掉旧提示词产出的全部 `needs_review` 规则**（65 条），重抽，并在文档里记下
"演示库的规则来自 R20 这一次抽取"。

## AG.6 这一轮"能匹配"是怎么达成的（不是为了让测试通过而点通过）

用户要求"不要为了让测试通过而虚构政策条件或随意修改真实政策要求"。所以审核按明确规则做：

| 动作 | 判据 |
| --- | --- |
| 复核通过 | ① `original_quote` 逐字出现在所属片段（脚本先断言）② 能用画像字段判定，**或**明确是需要人工核实的表述（`manual_review` 通过后返回"无法判定/需人工核实"，不是"不符合"） |
| 规范化 1 条 | 贷款 R-3：原文"家庭经济困难学生可以申请校园地国家助学贷款" → `poverty_certified = yes`（**只改编码，不改政策要求**） |
| 保留待复核 | 其余 60+ 条：主观表述、非画像可判定、或与枚举无法对应 |
| 标记不适用 | 违纪处分办法（全文为处分程序与申诉时限）、食堂指南（全文为服务时间与收费标准），**理由写进库** |

**结果**：3 份可匹配（奖学金 5 条、贷款 2 条、推免 2 条已复核资格条件）、2 份标记不适用、
其余保持待提取/待审核——这正是演示数据应有的样子，而不是"全部调成能匹配"。

## AG.7 没做的事（写清楚，不假装）

1. **不自动审核**：抽取仍一律 `needs_review`。自动通过等于拿模型的一次猜测替人做资格判断。
2. **不做"语义匹配"来解决枚举映射**：引入相似度推断会让资格判断不可复现，与
   "匹配不调模型"的硬约束冲突（登记 C-27）。
3. **不自动标"不适用"**：抽取 0 条也可能是模型漏抽（`no_conditions` 只是**待确认**状态）。
4. **不给 `documents` 加列**：那样要 ALTER 既有表；新表零迁移（`create_all()` 只建缺失的表）。
5. **不重写匹配算法**：一行没改，它本来就是对的。
