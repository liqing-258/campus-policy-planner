# 链 S ｜ 2026-11-14 ｜ 修复轮 R6 ｜ 降级不是"没配密钥"，是两个缺陷叠在一起

> 一句话：用户看到"未配置模型密钥"时，密钥其实一直在项目根——**exe 在 `dist/` 里找 `.env`**；
> 而"同一问题两次结果不一样"根本不是两次检索，是**同一个降级结果被画成了两副面孔**。

## S.3 AI 输出摘要（做了什么，以及为什么这么做）

### S.3.1 先分层，不要一上来改代码

问题里其实叠着三个疑问，先分开：

1. **是不是真的降级了？** ——查 `/api/v1/health`：`llm_mode: "degraded"`、`llm_model: null`。是。
2. **密钥到底有没有？** ——直接读项目根 `.env`：`LLM_API_KEY` 35 字符、`LLM_MODEL` 14 字符、`LLM_BASE_URL` 27 字符，**都在**。
3. **那为什么读不到？** ——查进程从哪个目录找 `.env`。`app/paths.py` 里 `writable_root()` 在打包形态下返回 **exe 所在目录**，而 `config.Settings.__init__` 只 `load_dotenv(PROJECT_ROOT / ".env")`。用户跑的是 `dist\知校校园政策助手.exe` → 找的是 `dist\.env` → 不存在 → 降级。

**定案的证据不是猜的**，是两条文件系统痕迹：

```
-rw-r--r-- 1818624 2026-11-14 09:45:36  data/app.db      ← 源码实例写的
-rw-r--r-- 1818624 2026-11-14 09:57:55  dist/data/app.db ← exe 实例写的
dist/.env 不存在
```

`dist/data/app.db` 有新的写入时间，说明**跑的是 exe**；同目录没有 `.env`，说明它注定读不到密钥。
`tools/build_exe.py` 的收尾提示还写着"想用真实模型：`copy .env dist\.env`"——也就是说，**原设计要求用户手动复制一次密钥**。用户不会去做这件事，也不该期望他做。

### S.3.2 第二个问题不是检索问题，是渲染问题

两张截图的内容其实高度重合（都是同一批原文片段），差别在外壳：

| | 当前轮（图 #3） | 历史轮（图 #2） |
| --- | --- | --- |
| 标题 | `降级模式：未配置模型`（橙色 `warn`） | `原文片断`（灰色 `past`） |
| 错误码 | 有 `4006` 标签 | **无** |
| 说明文字 | 后端 `note`：`未配置大模型（LLM_API_KEY / LLM_MODEL）…` | 前端另拼的一段：`（1）…（2）…（降级模式共 8 条原文片段…）` |
| 原文呈现 | 平铺全部候选 | 折叠的引用卡片（160 字摘要） |

同一个 `4006` 走两条模板：一条看着像**报错**，一条看着像**答案**。用户连问几次、或刷新后回看，就会以为"同样的问法给出不同结果"。
后端其实一次都没变——两次都是 `_degraded_payload()` 的同一份内容。

### S.3.3 修法（四个动作，都不是"关掉降级"）

1. **`app/config.py`：`.env` 多候选 + 一条硬条件**
   `env_candidates()` 依次看：`exe 目录/.env` → **上一级/.env** → `_MEIPASS/.env`。
   上一级不是无条件信任：**必须存在 `server.py`**（本项目的开发根特征）。
   否则把 exe 拷到桌面就会去读 `C:\Users\xxx\.env`——那是别人的配置，读进来比读不到更危险。
2. **`/health`：把"为什么降级"回给界面**
   新增 `llm_config`：`configured` / `api_key: set|missing` / `model` / `base_url` / `missing: [变量名]` / `env_files: [{path, found}]`。
   **只回路径与 set/missing，永不回值**——长度也不给（长度能被用来验证猜测）。
3. **`_degraded_note()`：指名缺哪个变量**
   原来固定写"（LLM_API_KEY / LLM_MODEL）"，让"没配"与"配了没读到"看起来一模一样。改成按 `settings.llm_missing` 拼。
4. **前端：横幅带诊断，两张降级卡合并成一张脸**
   横幅第二行直接显示"缺 X；已查找 A（不存在）；B（已读到）"；
   历史轮也带 `4006`、标题改为 `降级模式：未配置模型`，正文**以后端 note 开头**（`commitTurn` 时写进消息正文，回放才看得到当时为什么降级）。

## S.4 人工干预记录（出错、被数据打回、测法错的现场）

### S.4.1 我加的安全字段，被自己两轮前写的测试拦住

`test_health_never_leaks_secrets` 原本断言 `/health` 的响应文本里不能出现 `api_key` 这个词。新增 `llm_config.api_key` 后它立刻变红：

```
AssertionError: /health 泄露了 api_key
```

**这次是测试对、我错**——但要修的不是代码，是**断言的粒度**：公开接口真正该禁的是**值**，而不是变量名。
诊断功能必须能让用户看到"缺 `LLM_API_KEY`"，否则等于没说。于是改成：

```python
for forbidden in ("jwt_secret", "password", "token", "bearer"):
    assert forbidden not in lowered
real_key = os.getenv("LLM_API_KEY", "")
if real_key:
    assert real_key not in raw          # 真正不允许的：回显密钥值
assert set(cfg) == {...}                 # 字段集一变就要重审
```

保留"字段集必须显式列出"这一条，是为了防止将来有人往这里加一个带值的字段而没人注意。

### S.4.2 两次 Edit 匹配失败，原因一个是行尾、一个是我多打了两个字

第一次想改 `_degraded_payload` 的 note，`old_string` 里写成了"以下为检索到的**政策**原文片段"——原文没有"政策"二字。
第二次把引号换成中文引号再试，仍然不命中：这些 `.md`/`.py` 在工作区是 **CRLF**，而我手写的多行串是 `\n`。
判据很简单，读一遍 repr 就现形：

```python
'        "note": "未配置大模型（LLM_API_KEY / LLM_MODEL），以下为检索到的原文片段，未经归纳",\r'
```

改成"先按子串定位行号、再整行替换"的脚本，一次就过。教训与技能里那条一致：**多行替换必须先归一化行尾，并逐次 `assert count == 1`**。

### S.4.3 `pytest` 又是"全绿但退出码非零"

第一次全量跑完：进度条 100%、`FAILED`/`ERROR` 各 0 个，但退出码 `1`，且**汇总行没打印**——末尾是：

```
[100%][safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":266,"threshold":50,...}
```

原因是 pytest 结束时清理 `%TEMP%` 被安全删除钩子拦下。以前的做法是"数进度点"或 `--collect-only` 反推，这次换了更直接的办法：

```bash
.venv/Scripts/python.exe -m pytest --basetemp=.build/pt_run
# 304 passed, 1 warning in 305.76s
```

把临时目录放进项目内，就不再碰 `%TEMP%`，退出码 0、汇总行完整。**这比"数点"可靠**，已写进项目记忆。

### S.4.4 验证 exe 时把交付库写脏了，自己收尾

为了确认真实 exe 能读到密钥，我让 `dist\知校校园政策助手.exe --port 5001` 起了实例，并用它问了两次真实问题。功能验证通过，但代价是 `dist/data/app.db` 多了 2 条会话（交付库是发出去给人看的那份）。

清掉并 `VACUUM`：会话 31 → 29，消息 114 → 112。**验证动作产生的数据要一并收回**，否则"交付库"会慢慢变成一个测试垃圾场。

### S.4.5 一个必须说清的"看起来没修好"

`verify_exe.py` 三个场景里，A/B/C 的日志都写着 `问答模式 degraded`。这**不是回归**：

它把 dist 复制到 `%TEMP%\zx_exe_verify_*` 的沙箱里跑，沙箱的上一级没有 `server.py`，`env_candidates()` 拒绝向上读取——于是降级。这正是设计想要的行为：**把 dist 单独发出去，里面没有密钥，也不该有**。
真实验证走的是另一条路：exe 留在项目 `dist/` 时，`llm_mode = llm`（见 §S.5.2）。

## S.6 已知不做（明确登记，不假装完成）

1. **不把 `.env` 复制进 `dist/`**：那等于把密钥塞进一个"准备发出去"的目录。`build_exe.py` 只在提示里说明"项目内会向上读取"，绝不落副本。
2. **不做密钥的其他托管方式**（系统凭据库、加密配置）：这轮的问题是"路径没对上"，不是"密钥没地方放"；换托管方式会把一个 5 行的修复扩成一套基础设施。
3. **历史轮降级卡片里的原文仍是 160 字摘要**，不是全文：会话消息存的是"回忆用的摘要"（`stores/qa.ts` 有裁剪），要看全文得回原问题重新检索。这一点卡片内已有提示，不做全文落库。
4. **沙箱里的 exe 仍会降级**（`verify_exe` 场景 A/B/C）：这是预期行为，不是缺陷——见 §S.4.5。
5. **降级横幅的路径列表可能很长**：目前直接平铺三条路径。形态固定、条数恒定，暂不做折叠。

## S.8 结论

**门禁通过**：304 项全绿、exe 在项目内读到密钥（`llm_mode=llm`）、三场景自检全过、交付目录未被污染。

这一轮最重要的认知变化：**"降级"是一个状态，不是一条故障文案**。

- 它必须**说得出原因**（缺哪个变量、找过哪些路径），否则用户唯一的结论就是"系统坏了"；
- 同一状态在**实时**与**回放**两条渲染路径上必须是同一张脸，否则用户会把它读成"两次结果不一样"；
- 而"同一问题两次答案不同"在降级模式下几乎总是**呈现**问题，不是检索问题——真去查检索链路会一无所获（这轮一开始我差点就去查了）。
