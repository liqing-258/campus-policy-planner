## Z.1 目标

用户的原话（节选）：

> 请在现有「知校」系统中新增「智能政策推荐」功能。系统应根据学生已填写的个人基本信息、
> 学籍情况及资格匹配记录，从现有政策知识库中筛选可能适合该学生的奖学金、助学金、评奖评优
> 及其他校园事务政策。……**必须沿用现有资格匹配模块的三态判断逻辑，不能简单地让大模型
> 直接判断学生是否符合申请资格。**……无合适政策时显示「暂未发现匹配度较高的政策」，
> 不生成虚假推荐。……不得用写死卡片冒充智能推荐。

| 需求 | 表面看 | 实际牵连 |
| --- | --- | --- |
| "根据学生已填写的信息推荐" | 读一张学生画像表 | **系统里没有画像表**。唯一持久化的是 `match_sessions.profile_json`（每次匹配一行）。推荐要么去读它，要么就得新建一张"学生画像"表——后者立刻产生第二份真值：用户改了匹配页的填写，画像表不会跟着变 |
| "沿用三态判断逻辑，不要让大模型判断" | 调 `POST /matches` 拿结论 | 一次推荐要出 7 张卡片，逐张调匹配接口是 7 次写库（`/matches` 会落 `match_sessions`），而且"刷新推荐"会变成"刷新就往库里塞 7 行" |
| "按相关程度和政策有效状态排序" | 一个 `ORDER BY` | "相关程度"没有存过，只能算；算完还得能解释——"为什么它排第一"不能是黑盒 |
| "每条结果可追溯到具体政策文件和原文片段" | 卡片上放个文件名 | 文件名是文件级的，条件溯源要细到"第二章 第 4 条 · 第 2 页"，也就是要落到 `document_chunks` 的某一行 |
| "信息不完整可推荐，但须说明缺什么" | 缺字段就不推 | "缺"与"不符合"是两件事。混在一起，学生会把"没填绩点"读成"绩点不够"——这正是三态存在的理由 |
| "未经审核的规则不得作为确定性依据" | 只查 `approved` | 更难的是**解释"为什么一条规则都用不上"**：是被退回、待复核、还是在别的奖项名下——三种情况的下一步动作完全不同 |

**这一轮的核心判断**：推荐必须是**纯函数**——同一个人、同一份规则、任意时刻重算，
必须得到逐字相同的结果，而且一次都不写库。

> 这不是为了"干净"。用户第 12 条约束要求"刷新后能恢复"，而第 6 条要求"AI 功能必须真调"。
> 如果推荐落表，规则一复核、政策一换版，表里的推荐就和真相脱节了——**过期的推荐比没有推荐更危险**：
> 学生按一份已经失效的推荐去准备材料，比看到"暂未发现匹配度较高的政策"损失大得多。

## Z.2 我发给 AI 的完整 Prompt

**用户原文**（六节结构 + 十二条长期约束，此处按原文顺序重排，条目文字照抄，长句用省略号断开）：

> 请在现有「知校」系统中新增「智能政策推荐」功能。
>
> 【一、功能定位】
> 根据学生已填写的个人基本信息、学籍情况及资格匹配记录，从现有政策知识库中筛选可能适合该学生的
> 奖学金、助学金、评奖评优及其他校园事务政策。
>
> 【二、具体功能】
> 1. 在系统工作台页面增加「为你推荐」区域。
> 2. 展示与当前学生相关的政策推荐卡片。
> 3. 推荐范围优先包括：国家奖学金、国家励志奖学金、校级奖学金、助学金、优秀学生评选，
>    以及其他符合学生画像的校园事务政策。
> 4. 每张推荐卡片应展示：政策名称、适用对象、推荐理由、主要申请条件、政策有效状态、
>    相关文件名称，以及「查看详情」「进行资格匹配」按钮。
>
> 【三、推荐结果设计】
> 1. 推荐结果应区分三种状态：可能符合 / 暂不符合 / 暂无法判断。
> 2. 「可能符合」表示根据学生已填写信息，其条件满足当前可核对的政策要求；
>    「暂不符合」表示至少存在一项有明确依据的不符合项；
>    「暂无法判断」表示信息不完整、条款较主观或需人工核实。
> 3. **必须沿用现有资格匹配模块的三态判断逻辑，不能简单地让大模型直接判断学生是否符合申请资格。**
>
> 【四、推荐逻辑】
> 1. 优先使用学生已填写的画像信息和系统中已确认的政策规则。
> 2. 未经管理员审核的规则不得作为确定性推荐依据。
> 3. 学生信息不完整时，可以推荐，但必须说明缺少哪些信息。
> 4. 推荐结果应可追溯到具体政策文件与原文片段。
> 5. 推荐结果应按相关程度和政策有效状态排序。
> 6. 无合适政策时显示「暂未发现匹配度较高的政策」，不生成虚假推荐。
>
> 【五、交互设计】
> 1. 「查看详情」→ 进入政策详情或校园事务指南。
> 2. 「进行资格匹配」→ 进入现有资格匹配模块。
> 3. 「生成办理计划」→ 调用现有事务计划生成能力。
> 4. 支持刷新推荐结果。
>
> 【六、开发要求】
> 1. 复用现有学生画像、政策规则抽取、资格匹配、政策检索能力，不重复实现资格判断。
> 2. 必须基于真实数据，不能写死推荐卡片。
> 3. 完成后验证不同学生画像下的推荐结果是否存在合理差异。
>
> 【长期约束，十二条】
> 1. 这是一个已经相对成熟的项目，不是空项目，不要重写整个系统。
> 2. 不要为了完成任务而更换技术栈（Vue3 + Vite + TypeScript + Flask + SQLite 保持不变）。
> 3. 不要删除、清空、覆盖现有数据。
> 4. 优先复用已有组件、接口、数据模型，新增功能要与现有代码风格一致。
> 5. 不要为了"看起来丰富"而写死假数据、假接口、假页面。所有展示内容必须来自真实数据和真实逻辑。
> 6. AI 功能必须真实调用模型或真实规则，不能只做静态演示界面。
> 7. 不要破坏已实现的核心能力：政策引用溯源、资格匹配三态判断、计划草稿与确认、任务状态管理、工作流执行记录。
> 8. 修改前先说明计划与影响范围。
> 9. 每完成一个模块要跑测试。
> 10. 如果发现需求与现有设计冲突，优先保留已有可靠实现，并说明原因。
> 11. 每次完成后给我：修改总结、测试结果、未完成事项。
> 12. 新增功能必须能真实运行、能保存数据、刷新后能恢复。
>
> 最后：完成任务后请你更新需要迭代的文档，更新 GitHub 仓库，请你严格按照我的要求执行任务，
> 不要做任何与本次任务无关的操作。

### 我对 Prompt 的理解

四条约束一交叉，可选形状就只剩一个：

1. 第 6 条（AI 功能必须真调）+ 三-3（不能大模型判断）→ **判定必须走 `matching.evaluate()`**，
   它是全系统唯一一处三态实现，纯函数、不调模型；
2. 第 5 条（不许写死）+ 六-2（必须真实数据）→ 卡片内容必须由 `policy_rules` / `document_chunks` 现算，
   代码里只能有"哪些政策算得上一个可推荐事项"的**编目**；
3. 第 12 条（刷新后能恢复）+ 第 7 条（不破坏溯源）→ 不能为了"记得快点"把推荐缓存进库；
4. 三-1 的三态 + 六-3（不同画像结果要有差异）→ 同一份编目在不同画像下必须**分叉**，
   这是"没写死"唯一可验证的证据。

所以推荐不是"再写一个匹配接口"，而是**把已有的匹配结论按政策聚合、排序、配上理由与出处**。
一句话：**推荐层不产生新事实，只整理既有事实。**

## Z.3 AI 的关键输出与我的取舍

| 方案 | 取舍 | 理由 |
| --- | --- | --- |
| 新建 `recommendations` 表，定时/触发式预生成 | ❌ 否 | 违反第 12 条的可解释性：规则一复核、政策一换版，表内推荐立刻与真相脱节。要保证不过期就得加"规则变更 → 全量重算"的联动，那是把简单问题做成一个后台任务系统 |
| 让大模型读画像 + 读政策，直接给"你适合申请哪几项" | ❌ 否 | 与三-3 正面冲突。而且模型的输出无法逐条落到 `document_chunks` 的某一行，四-4 的溯源要求会退化成"贴一个文件名" |
| 逐张卡调 `POST /matches` 拿三态 | ❌ 否 | `/matches` 是**写接口**（落 `match_sessions`）。点一次"刷新推荐"写 7 行历史，还会覆盖画像的唯一来源——下次推荐读到的就是这次刷新产生的匹配 |
| 前端按关键词把卡片"过滤"出来 | ❌ 否 | 那是把判断挪到前端，等于第二套实现；而且 `unknown` 与 `not_met` 的区分会丢 |
| **只读接口 + 复用 `matching.evaluate()` + 聚合排序（`GET /recommendations`）** | ✅ | 一次请求算完 7 张卡；不写库；结论来自同一处三态实现；刷新 = 重新算一遍，天然一致 |
| 画像另起一张 `student_profiles` 表 | ❌ 否 | 第二份真值。用户第 3 条不许覆盖数据、第 4 条要求复用——`match_sessions.profile_json` 已经是画像的唯一持久化，`analytics.py` 的管理看板也在读它，两处口径天然一致 |
| **画像取"最近一次匹配"（`ORDER BY created_at DESC, id DESC LIMIT 1`）** | ✅ | 无画像时给"目录态"（全部 `unknown` + `no_profile` 提示），而不是空列表——第 6 条不许虚假推荐，但也不该让新用户看到一片空白 |
| 卡片按分类硬排序（奖学金在前、事务在后） | ❌ 否 | 需求四-5 要求"按相关程度和政策有效状态排序"，硬编码分类序等于把"相关程度"换成了"政策类型" |
| **打分排序：三态权重 + 命中条件数 + 适用对象确认 + 现行有效 + 分类权重 − 未判定惩罚**，并回传 `sort_basis` | ✅ | 分数可复算、依据逐条写进响应，前端直接展示"为什么它排第一" |
| 一个 `kind` 打天下（所有政策都按规则判定） | ❌ 否 | 资助/服务类文件在库里**一条规则都没有**。硬判会全部落到 `unknown` 却说不清原因 |
| **`kind` 分两类：`award` 按规则判定 / `support` 恒 `unknown` 但解释"为什么推荐给你"** | ✅ | 需求三-2 的 `unknown` 本来就包含"条款较主观或需人工核实"这一支；分类后卡片能把原文写明的对象、前置条件、办理时间摆出来 |

## Z.4 我的判断与修改

这一节记**第一版里哪些是错的**。R13 的失败不在"接口通不通"，而在**卡片上写出来的那句话对不对**——
十三处里有十一处，接口都是 200。

### Z.4.1 第一版：全局字典按 `id(spec)` 存"别的奖项的规则" → 跨请求残留

第一版为了解释"这个奖项的规则全在别人名下"，在模块级放了一个 `_ALL_APPROVED: dict[int, list]`，
键是 `id(spec)`：

```python
_ALL_APPROVED: dict[int, list] = {}   # ❌ 跨请求共享，id() 会被复用
```

`id()` 只在对象存活期间唯一，模块级字典等于把它们永久钉住；更糟的是它让推荐变成**有状态**的——
同一份画像在两次请求之间可能拿到不同的解释文案，直接违背这一轮的"纯函数"前提。

**改法**：把"别的奖项的已复核规则"算进 `_Context`（每次请求新建），在 `_build_card` 里就地算
`other_approved`。现在的推荐函数签名里没有任何 `global`，`test_repeated_calls_are_identical`
就是在钉这一条。

### Z.4.2 第一版：`target_group == 目标` 一个条件筛规则 → 把励志的五个条件当成国家奖学金的

第一版只按 `rule.target_group == spec["target_group"]` 取条件，国家奖学金的 `target_group` 是
`国家奖学金申请人`，库里没有一条规则属于它。于是 `specific` 为空，代码退回到"整条第四条"当条件摘要——
第四条里写着励志奖学金的五条条件（绩点、排名、困难认定……），**国家奖学金卡片上出现了别家的条件**。

更隐蔽的是理由文案：它说"该奖项的 1 条条件规则未通过复核"，而那 1 条其实是通用的「交换生不适用」。

**改法**：拆成两组，各有各的用途。

```python
specific = [r for r in rules if r.rule_type in CONDITION_RULE_TYPES
            and (r.target_group or "").strip() == target]        # 本奖项
generic  = [r for r in rules if r.rule_type in CONDITION_RULE_TYPES
            and not (r.target_group or "").strip()]              # 通用（未标注奖项）
```

- 判定只用 `specific + generic` 里 `approved` 的；
- 计数 `pending` / `rejected` **只数 `specific`**，通用规则另算——否则就是上面那句半真半假的话；
- 国家奖学金改 `conditions_from_quote=False` + `condition_quote` 带 `lines="国家奖学金"`，
  只取溯源那一行（第四条（二）的"同一学年内未获得国家奖学金"兼得限制）。

`test_unreviewed_rules_never_produce_a_verdict` 断言 `condition_counts["rejected"] == 3`
（校级优秀的三条），**不是 4**——那一条通用限制不该算进任何奖项的账上。

### Z.4.3 第一版：困难认定的"条件摘要"取到第十一条 → 把"挂钩关系"当成认定标准

困难认定卡片的第一版条件摘要是：

> 认定结果与奖学金评定、助学贷款办理、勤工助学岗位分配挂钩。

这句话是**关系**，不是**条件**。学生照它准备，会以为自己要先申请奖学金才能被认定。
第十一条的正确用途是"为什么这张卡值得看"（它是另外三件事的前置条件），而认定标准在第九条
（三档 / 每学年 9 月 / 有效期一年）。

**改法**：把"理由引用的条文"和"条件摘要引用的条文"分开，新增 `evidence_quote` 字段：

```python
condition_quote={"section": "第五章 家庭经济困难学生认定", "article": "第九条"},
evidence_quote={"section": "第五章 家庭经济困难学生认定", "article": "第十一条"},
```

这是本轮唯一一处**新增数据结构**，加它的理由很具体：一张卡片上会引两段不同的原文，
只有一段能当"主要申请条件"，另一段是"推荐理由的依据"。

### Z.4.4 第一版：未推荐原因是算子表达式 → 「家庭经济困难认定为「no」，要求等于「yes」」

`matching.evaluate()` 的 `rationale` 是给"逐条判定"用的，它长这样：

```
家庭经济困难认定为「no」，要求等于「yes」，不符合。
```

放在匹配页没问题（上面就是画像表单，用户看得见 `no` 对应哪个选项）。放到工作台的"未推荐 N 条"
折叠区就变成了黑话——那里的读者只想知道"为什么没推给我"。

**改法**：加 `VALUE_LABEL`（`yes → 已认定`、`no → 未认定`、`none → 无`、`enrolled → 在籍在读`…）
与 `_value_label()`，把 excluded 的理由重写成：

> 你的「家庭经济困难认定」是「未认定」，不满足该政策的适用对象要求（家庭经济困难认定等于已认定）。

判定行的 `rationale` **保持原样**——它是既有三态实现的输出，改它就等于改匹配页的文案，
而第 7 条约束要求不破坏既有能力。

### Z.4.5 适用对象与主要申请条件指向同一条 → 卡片在自我复读

三张卡（生源地助学贷款、勤工助学、推免）的 `audience_quote` 与 `condition_quote` 一开始指向同一条，
渲染出来是同一段原文印两遍。对"资助类"文件尤其常见：原件本来就不分"管谁"和"要什么"。

**改法**两层：

1. **按原文重新指**：贷款 → 适用对象第一条（对象与额度）、条件第三条（7–9 月办理期与凭证）；
   勤工助学 → 适用对象第七条（优先安排困难学生）、条件第十五条（上岗培训与工时表）；
   推免 → 适用对象只取第三条（一）（`lines="（一）"`）、条件取第三条整条。
2. **加兜底**：两段正文完全相同时，条件摘要留空，卡片退回"原文未单列申请条件"。
   编目是人工的，这类错误早晚还会出现；兜底让它表现为"少一行"，而不是"同一句话两遍"。

`test_audience_and_conditions_are_not_the_same_sentence` 钉住三张卡的取文位置。

### Z.4.6 支持类理由引错了段落 → 「你的画像与文件…第三条写明的适用对象一致」

改完 Z.4.5 之后出现了一个**新**错误（这类"修一处带出一处"在本项目已经出现过多次）：
贷款的适用对象挪到第一条、条件挪到第三条，而 `_support_verdict()` 拿的是 `condition_block`，
于是理由变成"你的画像与文件第一章 生源地信用助学贷款 **第三条** 写明的适用对象一致"——
引用的段落里根本没有"适用对象"这几个字。

**改法**：调用处改传 `audience_block`，并在函数 docstring 里写明"`quote` 必须是适用对象那段原文"。
测试加两条断言：`"第一条" in reason.text` 且 `"第三条" not in reason.text`。

### Z.4.7 前端：筛选到 0 条时显示「暂未发现匹配度较高的政策」

需求四-6 的这句文案是"一条都没算出来"时说的。但筛选条上有「可能符合 0」，学生一点就看到了
同一句话——听起来像系统什么都没给他找，实际上只是这个筛选下没有。

**改法**：两种"空"分开说。总数 > 0 时给「当前筛选下没有政策，切回「全部」可以看到其余 N 条。」

### Z.4.8 验收脚本自己的三处误报（不是代码错）

| 现象 | 真相 |
| --- | --- |
| "推荐区不在列表卡之前" FAIL | `document.querySelector('.grid')` 先命中的是统计行的 `.grid.grid-4`。选择器**过宽**，不是布局错 |
| "每张卡都标了政策有效状态" FAIL | 允许值是 `['现行有效','已失效','待生效','未知']`，而 `EFFECTIVE_LABEL.unknown` 实际是「**未标注**」——照着自己记忆里的词写断言 |
| "换画像前：困难认定卡在提示卡在这一项" FAIL | 上一段结束时页面停在 `/ask`，`card_info()` 在工作台上找不到 `.rec-grid`，返回 `None`。**采样时机错**，不是文案错 |

这三条与 R12 的三条误报（扫了整栏把合法出处当页脚 / `select` 选项异步填充 / `.item-card` 先命中
常用事项区）是同一类：**验收脚本最容易错的地方是"我以为页面现在长这样"**。

### Z.4.9 后端没热重载 → 改完 `recommend.py` 接口还是旧文案

改完 Z.4.5 后直接复测，接口返回的两行**仍然完全相同**。第一反应是"改错了位置"，
实际是 `server.py --no-browser` 起的是无热重载进程，跑的仍是旧代码。

处理方式沿用本项目的既有规矩：**先取一个"只有新代码才有的字段"证明连的是新进程**，再谈结论。
这里的判据是贷款的条件摘要应该出现"集中办理期"——旧代码不可能有这句话。
确认仍无 → `Stop-Process` 停旧进程 → 重启 → 同一段脚本复测，两行终于分开。

> "我刚重启过"不是证据。只有"新代码独有的输出出现了"才是。

### Z.4.10 测试夹具的三处环境坑

| 报错 | 真正原因 | 改法 |
| --- | --- | --- |
| `IntegrityError: FOREIGN KEY constraint failed` | `uploader_id="test"` 这个用户不存在 | 夹具里先查 `admin` 再传 `admin.id` |
| `DetachedInstanceError` | `commit()` 之后出了 `app_context`，读 `old.id` 时对象已脱离会话 | 提交前先取 `ids = {...}`，返回 id 而不是 ORM 对象 |
| `assert '3.0' in '…不低于 3，不符合。'` | `matching._trim()` 对整数值不补小数（`3.0 → "3"`） | 断言改成 `"不低于 3"`，并在注释里写"跟着既有口径断言，不为这一条去改三态文案" |

## Z.9 结论

需求里最容易被做歪的一句是"根据学生已填写的信息智能推荐"。省事的做法是让模型读一遍画像与政策、
输出一个排序列表——看起来最"智能"，却同时违反三-3（不能大模型判断）、四-4（可追溯到原文片段）
与四-2（未审核规则不得作依据）。

这一轮的实际做法是相反的：**把"智能"从"模型判断"挪到"整理既有事实"**——
三态来自 `matching.evaluate()`，条件来自 `policy_rules`（只认 `approved`），
原文来自 `document_chunks`，排序是一条可复算的加法。推荐层唯一自己的东西是两张**编目表**
（`SUBJECTS` 与 `PRIORITY`）和一段排序规则。

代价是清楚的：新增政策文件不会自动进推荐（C-20），画像只有最近一次（C-21）。
收益也是清楚的：同一个学生任意时刻刷新，看到的是同一份结果；每一条理由都能落到
"第几章、第几条、第几页、哪条规则编号"；规则复核状态一变，推荐下次请求就跟上，
不需要任何回填或迁移。
