# 链 R ｜ 2026-11-13 ｜ 修复轮 R5 ｜ 继续追问：从"标签造句"改成"从证据里长出来"

> 链编号与 `00-AI对话历史总档.md` §3 台账一致。前一条链是 Q（点名文件与版本锚定，R4）。
> 这一条的用户反馈只有一句："**提问后继续追问的问题仍有无法继续回答的情况**"，
> 外加一个顺序要求：**先完善政策知识库，再解决这个问题**。
> 顺序很关键——它把"语料缺口"和"代码缺陷"分开摆，而这两件事的修法完全不同。

---

## R.1 目标（一句话）

让界面上那三条「继续追问」**点下去一定有内容**，而不是"点下去先撞一次拒答再看运气"。

可断言的三条：

1. 18 份文件 × 每条建议，端到端都返回答案（不是"检索到候选"，是 `code=0`）；
2. 建议里必须带《文件名》——否则 R4 的锚定用不上，问句就没有确定的检索范围；
3. 建议的根据必须是**库里真实存在的东西**（文件、章节），不能是分类器给的标签。

## R.3 AI 输出摘要（做了什么，以及为什么这么做）

### R.3.1 先量化：不是"偶尔答不出"，是 54 条里 9 条必错

前端的追问是这么拼的（`AskView.vue::followUps`）：

```ts
out.push(`${label}需要准备哪些材料？`)
out.push(`${label}的申请截止时间和办理流程是什么？`)
out.push(`《${doc}》里还有哪些与${label}相关的规定？`)
```

`label` 是 `app/intent.py` 的意图分类结果，`doc` 是引用到的文件名。
我照这段逻辑造了 54 条（18 份文件 × 3），用真实模型逐条发出去：

```
合计 54，答出 45，失败 9
  [4001] 学籍管理规定 | 转专业需要准备哪些材料？
  [4001] 学籍管理规定 | 转专业的申请截止时间和办理流程是什么？
  [4001] 学生宿舍管理规定 | 住宿管理需要准备哪些材料？
  [4001] 学生宿舍管理规定 | 住宿管理的申请截止时间和办理流程是什么？
  [4001] 图书馆借阅与自习空间管理办法 | 《图书馆…办法》对办理流程和时间要求是怎么规定的？
  [4001] 学生事务办理指南 | 不符合《学生事务办理指南》规定的情况会怎么处理？
  [4001] 学科竞赛与创新创业项目管理规定 | 不符合《…规定》规定的情况会怎么处理？
  [4001] 校医院就诊与心理健康服务指南 | 不符合《…指南》规定的情况会怎么处理？
  [4001] 食堂与后勤生活服务指南 | 不符合《…指南》规定的情况会怎么处理？
```

### R.3.2 两个根因，必须分开修

| 根因 | 例 | 修法 |
| --- | --- | --- |
| **语料缺口**：文件里确实没写"材料/流程时限/违规处理" | 学籍规定没有转专业材料与时限；图书馆没有办理流程 | 补语料（用户要求的第一步） |
| **模板缺陷**：句子用分类标签当主语，库里不可能有对应内容 | `学分与成绩的申请截止时间和办理流程是什么？` | 改由后端按文件与章节派生 |

只修第一类不够——补完语料后重跑，失败从 9 降到 2，但**又一次跑成了另外 2 条**（见 §R.4.2），
说明"用标签造句"这件事本身没有下限保证。

### R.3.3 语料补全（第一步）

9 份文件各补 1 页，都是围着"三类追问"写的，条文里带具体数字（时限、份数、比例），
不是空话，便于模型直接引用：

| 文件 | 补的章节 | 落的缺口 |
| --- | --- | --- |
| 学籍管理规定 | 第十章 学籍事务办理流程与时限 | 转专业的材料、流程、截止时间、材料不齐的处理 |
| 学生宿舍管理规定 | 第八章 调宿、退宿与住宿事务办理 | 调宿材料与时限、退宿流程 |
| 学生事务办理指南 | 九、材料不齐与不符合规定的处理 | 材料不齐/虚假材料/不予受理的处理 |
| 图书馆借阅办法 | 第八章 办理流程与时限 | 借阅、续借、文献传递、预约的流程与时限 |
| 学科竞赛规定 | 第七章 违规处理与申诉 | 虚报、造假、指导教师失职的处理 |
| 校医院指南 | 第八章 不按规定就医的处理 | 冒用卡、未转诊、伪造证明的处理 |
| 食堂指南 | 第八章 违规处理与投诉办结时限 | 投诉响应与办结时限、属实的处理 |
| 考研与出国办法 | 第八章 不实申报与违约的处理 | 材料造假、放弃资格、逾期不归 |
| 助学贷款办法 | 第八章 贷款申请流程与时间要求 | 生源地/校园地贷款流程、受理与截止时间 |

顺带修掉一个真缺陷：《学生社团与校园文化活动管理办法》里有**两个「第四章」**
（「第四章 附则」夹在「第三章 场地与经费」和「第四章 组织与换届」之间），
条号也从第八条直接跳回第十条。现在附则挪到第八章，条号连续。

片段数 122 → **131**，18 份文件不变。

### R.3.4 追问改由证据派生（第二步）

`app/qa.py::build_next_questions`：拿**刚答出来的证据**（`outcome.candidates`）反推建议。

| 建议 | 依据 | 为什么一定答得出 |
| --- | --- | --- |
| 《X》里还有哪些与{label}相关的规定？ | 刚引用的文件 | R4 锚定：范围就是 X，覆盖率闸门不适用 |
| 不符合《X》规定的情况会怎么处理？ | X 有违规/处理类章节 **且** X 是办法/规定类 | 章节真实存在 |
| 《X》的「第 N 章 …」是怎么规定的？ | X 里**这轮没引用到**的章节 | 该章节正文确实在库里 |

三条边界是被数据逼出来的，不是设计时想到的：

1. **指南类文件不给"不符合规定会怎么处理"**。校医院、食堂的读者与文件之间不是"遵守/违反"关系，
   这句话在两次批次里一次答出、一次拒答（§R.4.4）。改成问该文件里真实存在的
   「第八章 不按规定就医的处理」——同样的信息，问法不预设义务。
2. **处分类文件不给"不符合它自己"**。问《违纪处分与申诉管理办法》"不符合规定会怎么处理"
   是套娃，模型稳定判证据不足（§R.4.3）。
3. **章节题只挑这轮没引用过的**。用户刚看完第二章，接着问第三章才有意义；
   全都引用过就少给一条，不凑数。

### R.3.5 拒答时也给一条"点了就有原文"的建议

`_refusal_payload` 原先只有三句通用建议（"换一种说法""确认文件已上传"）。
R4 之后手里有更好的东西：被闸门拦下的候选（`rejected`）——把它变成
`《X》里还有哪些与这个问题相关的规定？`，R4 的锚定会跳过闸门，**点进去必然出原文**。
这条放在建议列表第一位，因为它是唯一"确定有结果"的路径。

## R.4 人工干预记录（出错、被数据打回、测法错的现场）

### R.4.1 我的第一版探针漏了 `vague` 分支，误报 24 条失败

前端在 `label` 以"其他"开头时会改用**文件名**造句（`vague` 分支），
而我的探针直接按 label 造了 54 条，于是把 14 份文件（label=其他事项）都算成失败：

```
合计 54 条追问，答出 30，失败 24      ← 假的
```

实际上那 14 份文件走的是 `《doc》里还有哪些与这个问题相关的规定？`，全部答得出。
**测法错比代码错更危险**：如果照这个数字去修，会去补一堆根本不缺的语料。

### R.4.2 补完语料仍剩 2 条，而且两次跑的不是同 2 条

```
第一次（补语料后）：失败 2 —— 考研与出国办法「不符合…」、助学贷款「申请截止时间和流程」
补这两章后再跑：    失败 3 —— 课程考核「学分与成绩的申请截止时间…」、推免同上、校园卡「不符合…」
```

失败项在**漂移**。逐条看，新冒出来的都不是"库里没写"，而是**问法本身没有答案**：
"学分与成绩的申请截止时间"——课程考核与推免这两种事项都没有"申请截止时间"这回事。
这一条实测把方向改掉了：**光补语料治不了"用标签造句"的毛病**，必须换建议的来源。

### R.4.3 处分类文件的"不符合它自己"是稳定失败

```
[4001] 学生违纪处分与申诉管理办法 | 不符合《学生违纪处分与申诉管理办法》规定的情况会怎么处理？
```

这部办法本身就是"违规会怎么处理"，再问"不符合它会怎么处理"是套娃。
模型的判定是稳定的（多次都拒答），所以按标题关键词排除（违纪/处分/申诉）。

### R.4.4 指南类的同一句话，两次跑出不同结果

```
第一次：[OK  ] 不符合《校医院就诊与心理健康服务指南》规定的情况会怎么处理？
第二次：[FAIL] 不符合《校医院就诊与心理健康服务指南》规定的情况会怎么处理？   ← 同一句话、同一份文件
```

这种"看起来能答、其实模型在摇摆"的最难处理：它不会暴露成固定失败。
判据改成**按文件类型分流**：办法/规定类才用"不符合…"，指南类改用章节标题提问
（章节标题是库里的原文，模型没有摇摆空间）。改后同一位置稳定 `[OK]`。

### R.4.5 语料重建把 `uploads/` 堆到 54 个文件

`refresh_demo_library.py` 每次重建都会写入新的物理文件，旧的不动。跑了几轮之后
`data/uploads` 从 20 涨到 54，`build_exe` 会把这些全打进交付目录（多 34 个没人引用的 PDF）。
脚本本身有 `--prune-uploads`，但**没人提醒你要跑它**：

```
[prune] 删除 68 个孤儿文件（956 KB），保留 20 份在用文件
```

清理后重新打包，交付目录里 `已复制上传件 20 个` 才是对的。

## R.6 已知不做（明确登记，不假装完成）

1. **用户自己敲的追问仍可能答不出**。R5 只保证"界面上那三条建议"可答，
   自由输入不受保证——登记为 `已知限制.md` **B-13**。
   要彻底解决只能要求每份上传件都写全四类内容，而用户可上传任意通知。
2. **不给建议做"答案质量"承诺**。47/47 是"能出答案（`code=0`）"，
   不是"答得对"；质量仍由 24 条评测集与人工抽检判断。
3. **没有把追问建议落库**。它是每轮临时算的，不进 `messages`；
   历史会话回看时不会复现当时的建议（反正点开历史也不会续问）。

## R.8 结论

这一轮的教训不是"要补语料"，而是**"补语料"和"修问题"是两件事**：

- 补语料解决的是"文件里没写"；
- 而用户点的那三条建议里，有一部分**问法本身就没有答案**（"学分与成绩的申请截止时间"）。
  这类问题无论补多少语料都答不出，唯一的修法是**换掉建议的来源**——从"分类器标签"
  换成"证据里真实存在的文件与章节"。

判断依据也随之换了：不再问"检索召回够不够"，而是问
**"这条建议所依赖的那段文字，在不在这份文件里"**。这个判据不需要模型，也不需要语料扩充，
写进单元测试就能守住。
