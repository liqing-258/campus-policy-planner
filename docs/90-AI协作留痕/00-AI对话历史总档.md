## 0. 先读这段：这份文档解决什么问题

赛事要求提交"AI 对话历史导出的 Prompt 历史快照"，难点有两层：

1. **导出**：要把散落在会话窗口里的交互，变成可提交、可检索、可核验的文件；
2. **证明**：要证明这些不是事后编的，而是**真实发生过的**，且能看出"你是如何驾驭 AI 的"，不只是"AI 帮你写了什么"。

本文件用**证据台账 + 三要素检查 + 追加机制**回应这两层。§5 会明确写出现在还缺什么——不遮掩。

## 2. 导出方案：为什么是"三重证据"而不是一个文件

### 2.1 三条证据链分工

不同形态的证据能证明的东西不同，不能互相替代，所以三条都要有：

| 形态 | 能证明什么 | **不能**证明什么 | 产生时机 | 落地位置 |
| --- | --- | --- | --- | --- |
| **Markdown 原文快照** | 提问原文、AI 输出要点、我的判断与否决、验证命令与结果 | 不能证明"对话真实发生过"（可以事后编） | 每完成一条链当场写 | `docs/90-AI协作留痕/0X-*.md` |
| **会话截图** | 对话真实存在、界面上有输入框与回复、时间可见 | 不能证明我的判断过程 | 每轮关键交互后立即截 | `docs/90-AI协作留痕/evidence/` |
| **录屏** | 连续交互过程，能看出"改一句 Prompt、看结果、再改"的迭代节奏 | 覆盖不全，体积大 | 核心 Bug 修复、核心模块生成时 | 剪辑进 5–8 分钟演示视频，另存原始文件 |

> **优先尝试直接导出**：若所用 AI 工具的新版本支持导出会话，应优先导出完整会话文件（JSON/Markdown）并归档到 `evidence/`，本方案作为兜底。赛事原文明确"如果 AI 工具不支持导出，可以截图或者录屏"，截图是被认可的形态。

### 2.2 截图规范（缺一条就失去证据效力）

| 项 | 要求 |
| --- | --- |
| 命名 | `AI-<链编号>-<序号>-<YYYYMMDD-HHMM>.png`，例：`AI-D-03-20261107-1742.png` |
| 内容 | 必须同时可见 ①我的输入框内容 ②AI 的回复 ③时间或会话标识 |
| 颗粒度 | 每条链 ≥ 3 张：提问、AI 给方案、修复后验证 |
| 隐私遮挡 | 截图前遮挡：API Key/PAT、手机号、真实姓名学号、他人隐私信息 |
| 禁止 | 只截 AI 输出的成品、截掉自己的提问、用 PS 修改内容 |

### 2.3 录屏规范

| 项 | 要求 |
| --- | --- |
| 用途 | 剪辑进演示视频的"≥2 分钟 AI 协同过程复现"片段 |
| 内容 | 必须拍到：输入 Prompt 的完整过程、AI 输出的滚动、我指出问题并追问、最终验证 |
| 分辨率 | 1920×1080，与视频一致 |
| 原始文件 | 保留未剪辑版本，作为原始证据备查 |

## 5. 核心功能迭代链的覆盖情况

### 5.1 赛事要求的字面含义

"至少 3 个**核心功能迭代**时与 AI 交互的完整 Prompt 链"——重点是"功能迭代"，即一个**可运行的功能点从提出到跑通**的过程，而不是纯文档设计。

### 5.2 当前覆盖：**尚未满足 P-2，这是必须承认的事实**

| # | 核心功能 | 计划里程碑 | 计划记录文件 | 追加截止 | 当前状态 |

| F-3 | 三态匹配（规则抽取→代码判定→unknown 归因） | M5（11-12） | `06-核心功能-三态匹配.md` | 11-13 | ⬜ 未开始 |

> 当前已落盘的 5 条链（A–E）属于**设计阶段与工程阶段**，不冒充"功能迭代"。M0/M1 阶段确实没有功能代码，此时若出现"某功能迭代的对话记录"，只能是编造。

### 5.3 为什么不现在把这三条写出来

因为这三条的内容取决于代码怎么写、遇到了什么 Bug，现在写必然是虚构的。而虚构 AI 对话正是合规清单 **X-04 红线**（"从根本上杜绝抄袭与伪造"）。**宁可现在如实显示"未开始"，也不提前写好等着填。**

### 5.4 补齐门禁（写进 M7 前置检查）

| 检查点 | 判定 |
| --- | --- |
| F-1～F-3 三条链全部落盘，每条含 3 要素 | 缺一条则 M7 不放行 |
| 每条链至少含 1 次真实的"失败 → 定位 → 修复" | 全是"一次成功"的链要复查是否漏记失败轮次 |

| 每条链能对上至少 1 个 `feat`/`fix` 提交 | 与 `Git提交日志.md` §6 矩阵交叉核对 |

## 6. 追加机制（防止事后编造的四条硬规则）

| # | 规则 | 理由 |
| --- | --- | --- |
| W-1 | **随做随记**：一条链结束当场追加，最迟 24 小时内 | 拖延就越写越像总结，细节会丢 |
| W-2 | **失败轮次不许删** | 被否决的方案和被证伪的假设，才是"驾驭 AI"的证据 |
| W-3 | **追加与提交同步**：每次追加单独 `docs(ai-log)` 提交 | 让"写留痕"这件事本身也进 Git 历史 |
| W-4 | **Prompt 原文照抄**：不润色、不补全、不合并多轮 | 润色后的 Prompt 会显得"一次就问对了"，反而失真 |
| W-5 | **写链与更新索引是同一步**：新建 `NN-xxx.md` 必须同时改 §3 台账与"修订记录" | 链 H 就是只写了正文、没更台账，到 M3 才发现（见修订记录 V1.2 下方的自查） |

## 6.5 每条链的固定 8 段结构

评审可以拿这张表逐条核对，缺一段即为不合格：

| # | 段落 | 内容要求 |
| --- | --- | --- |
| 1 | 目标 | 一句话说清这一轮要解决什么 |
| 2 | 原始 Prompt | 用户原话，不改写、不合并 |
| 3 | AI 输出摘要 | 做了什么 + **为什么这么做**（决策理由比产物清单重要） |
| 4 | 人工干预记录 | AI 出错、被纠正的具体现场，保留错误代码/输出 |
| 5 | 验证记录 | 实测输出，不是"应该会这样" |
| 6 | 已知不做 | 明确登记未实现项与理由，不假装完成 |
| 7 | 对应提交 | commit 短 sha 或指向 Git 提交日志的定位 |
| 8 | 结论 | 门禁通过与否，以及本链最重要的一个认知变化 |

链 I（`05-M3知识库可用.md`）的 §I.5 是本项目目前**最值得示范**的一段：
AI 提出的"加个阈值让测试变绿"被实测数据否掉，最终改了设计而不是改测试口径。

链 J（`06-M4问答可信.md`）的 §J.4.4 与 §J.5.3 补充了两类新证据：
§J.4.4 是"M3 埋下、M4 才被真实需求照出来"的分词缺陷（加词典治不好，改用字符 bigram）；
§J.5.3 是"扫描出最优点却主动不选"——0.15 与 0.35 都是 100%，但中间 0.25 只有 95.8%，
非单调说明差异落在模型抖动范围内，最终按可解释性选 0.35 而非最高分。
