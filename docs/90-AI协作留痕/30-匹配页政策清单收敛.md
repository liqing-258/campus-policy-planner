# 链 AH · 匹配页政策清单收敛（R21）

> 留痕编号：AH ｜ 对应轮次：R21 ｜ 日期：2026-11-16
> 一句话：**把"能不能匹配"的判据收到后端一处，页面只负责展示它给出的集合。**

---

## AH.1 原始 Prompt（摘录）

> 目前资格匹配页面中存在较多暂时无法进行资格匹配的政策文件，例如显示为「待提取」
> 「不适用于资格匹配」等状态的政策。这些文件会使学生在选择政策时产生困惑…
>
> 请采用动态筛选方式，而不是简单地将当前政策名称写死在前端。具体要求：只有当政策文件
> 至少拥有一条有效、已审核且已启用的资格匹配条件时，才允许其出现在资格匹配页面的
> 政策选择列表中。
>
> 特别注意：本次任务只是清理资格匹配页面中的政策选项，**不是删除政策知识库中的政策文件**。

---

## AH.2 判断：这不是"删数据"，是"换判据"

R20 已经把六种状态做出来了，但匹配页仍然是"18 份全列、逐份标注状态"。用户的诉求是
**只列能用的**——于是问题从"怎么展示状态"变成"谁来判断可用"。

三个可选位置：

| 方案 | 问题 |
| --- | --- |
| 前端按 `rule_summary.state === 'ready'` 过滤 | "能不能匹配"的判据（approved + 条件类）在后端，前端再写一遍就有**两份真相**；而且 `total` 与 `items` 会对不上（分页按未过滤集合算） |
| 前端把三个文件名写死 | 用户明确禁止；管理员复核新政策后也不会自动出现 |
| **后端加查询条件**（采用） | 判据只有一处；分页总数天然正确；新政策审核通过后下一次请求就在列表里 |

## AH.3 实现：一个查询参数，一条 EXISTS

```http
GET /api/v1/documents?page=1&page_size=50&parse_status=indexed&match_ready=1
```

- 判据：**存在**至少一条 `review_status='approved'` 且 `rule_type ∈ (eligibility, restriction)`
  的规则；
- 用 `EXISTS` 子查询而不是"先查 id 再 `in_`"：后者要为每个 id 拼参数，文件多了会撞
  SQLite 参数上限，且两次往返之间有窗口期；
- 参数值只接受 `1/0/true/false`，其他给 `1001`（与 `parse_status`/`effective_status`
  的校验风格一致）；
- **不是新接口**：`GET /documents` 本来就存在，所以接口总数仍是 57。

**"已启用"在本系统里就是"已复核通过"**：`policy_rules` 没有独立的 enabled 列，
`update_rule` 在 `review_status=approved` 时强制要求算子与预期值（否则这条规则判不了）。
所以本轮的判据只有 `approved + 条件类` 两个条件，没有引入第三种状态——如果需要
"审核通过但暂停使用"，那是另一个功能，本轮不做。

## AH.4 前端只改三件事

1. 请求带上 `match_ready=1`；
2. **选中的文件必须仍在列表里**：管理员撤掉复核后，本地存的 `documentId` 会指向一个
   已经不该出现的选项，直接拿来请求就是 2008。所以每次加载都校验一次，不在列表就回落到
   第一份（需求四.3「保留用户上次选择的有效政策」+ 四.4「新审核的自动进入」同时成立）；
3. 选项文案回到三要素（名称 / 已复核条件数 / 片段数）——能出现在这里本身就是
   "已具备匹配条件"，再挂一个状态标签是重复信息。

顺带补了**空列表的空状态**：不是留白，而是说清"为什么空"（还没有任何一份完成抽取与复核）
和三条下一步（看事务指南 / 查知识库原文 / 管理员去复核）。

## AH.5 动态性怎么证明（不是"现在刚好是 3 份"）

只在真实数据上看一眼"3 份"是不够的——那可能只是把名单写死了。所以分两层验：

**pytest（10 条，`tests/test_match_ready_filter.py`）**

| 验什么 | 为什么必须验 |
| --- | --- |
| 只有待复核规则 / 只有材料规则通过 → 都不出现 | 材料类复核通过 ≠ 可匹配 |
| `eligibility` 与 `restriction` 都算 | 漏了 restriction 会少列"处分期内不得参评"这类政策 |
| 新复核通过 → 自动出现 | 需求四.4 |
| 撤销复核 → 自动消失 | 需求四.5 |
| 多条规则只需一条通过 | 否则会变成"全部通过才可用"，与需求"至少一条"相反 |
| 不带参数 → 18 份一份不少 | 需求三：不删知识库数据 |
| `match_ready=0/false` → 不过滤 | 参数语义自洽 |
| 非法值 → 1001 | 与既有参数校验一致 |
| `total` 与过滤后集合一致（含翻页不重不漏） | 前端分页靠它 |
| 剩余政策的匹配结果不受影响、互不串用 | 需求四.3 |

**真实数据可逆验证（`.build/r21_live_check.py`，10 条）**

拿《国家助学贷款》（2 条已复核条件）做：

```
撤 1 条 → 仍有 1 条 → 仍列出（证明"至少一条"）
撤 2 条 → 归零     → 自动移出（total 3 → 2）
移出后匹配         → 2008，且文案是"待复核 20 条"而不是"不适用"
恢复 2 条          → 回到列表（total → 3）
结尾核对：规则状态与开始时逐条一致（可逆，无残留）
```

## AH.6 没做的事

1. **没删任何文件、片段、规则**：知识库仍是 18 份（`GET /documents` 不带参数逐条比对），
   问答检索、事务指南全部走原数据。
2. **没加"启用/停用"开关**：需求里的"已启用"按现有语义（已复核通过）解释，
   不引入新的规则状态机——那会让"复核"与"启用"两个状态互相打架。
3. **没动三份政策的规则与审核结果**：验证脚本只做了 `approved → needs_review → approved`
   的往返，结束逐条核对一致。
4. **没把规则管理页也筛掉**：管理员需要看到全部 18 份才能去补条件——清理只作用于
   资格匹配页（浏览器验收 D2 断言 `> 3` 项）。

## AH.7 验收

| 项 | 结果 |
| --- | --- |
| 后端全量 | **493 passed**（483 + 10） |
| 浏览器 | `.build/check_r21.py` **22 / 22** |
| 真实数据可逆验证 | `.build/r21_live_check.py` **10 / 10** |
| 空状态补验 | `.build/r21_empty_state.py` **13 / 13**（临时撤回 9 条 → 空状态 → 恢复并逐条核对） |
| 接口 | 仍 **57** 条（只给既有接口加查询参数） |
| 数据表 | 仍 **17** 张（零结构变更） |
| 数据基线 | 12 张业务表零净变化（`match_sessions` 49 / `items` 245 已复原） |

浏览器验收的**两条测试自身缺陷**值得记：

1. 第一次把 `wait_for` 写成"页面出现'符合/无法判定'"，而页头那句「结果只有三种：符合、不符合、
   无法判定」本来就含这几个字——第一次轮询立刻命中，读到的是"结果还没渲染"的空白，于是断言
   "三份都能跑出结果"实际什么都没验。改成等 `.counts .count` 才是真信号。
   **断言要等"被测动作的产物"，不要等"页面上本来就有的字"。**
2. `document.querySelectorAll('select.select option')` 把奖项下拉与九个画像字段下拉一起数进来
   （"3 份"变 24 个 option）。同一个陷阱在**空状态补验里又踩一次**——因为画像表单的
   `select.select` 还在，误判"政策下拉没被移除"。两次都改成贴着目标元素取。

**空列表分支本来永远走不到**（演示数据有 3 份），写了不验等于没写。所以用可逆方式真验了一次：
临时撤回 9 条已复核资格条件 → 页面出现空状态块、文案说清原因与三条下一步、不渲染空下拉、
按钮禁用、无异常；`try/finally` 恢复后逐条核对规则状态一致、匹配页回到 3 份。
