## AK.3 追问的真相：一个"过期的假设"

### 现象

`followup_click_check.py` 每一轮都等满 120 秒报"点下去没回应"，而同一句话走接口 6 秒就答完。
R23 把它记成"浏览器侧的追问提交或渲染路径"问题。**这个归因是错的。**

### 定位

```
chip 按钮 → useSuggestion(s)
              ├─ question.value = text      ← 只填入
              ├─ suggestClosed = true       ← 并且把建议栏收起
              └─ nextTick(聚焦输入框)
```

`useSuggestion` 里**没有任何发送动作**。再往上查，这是 R8 的明确要求（用户原话：
"点击继续追问按钮时将该问题放置于对话框中，用户按下发送或是 enter 键才会发送"），
代码注释里就写着"点建议只填入，不提交"。

**脚本写于 R8 之前**，它假设 `chip.click()` 会发出去，然后等 `.answer-text` 增加。
R8 改了交互，**脚本没跟着改**——于是它不是"发现了 bug"，而是"在等一件不会发生的事"。

### 修法（不是放宽超时）

1. 交互改成真实路径：点选 → **断言只填入且未发送** → 点「发送」→ 等新解答；
2. 把"只填入"做成断言：谁改回"直接发"，脚本立刻失败。**契约用断言咬住，不用注释咬住。**
3. 补 5 组边界：空白输入（按钮应禁用）、连点三次（只出一条）、整页刷新（对话仍在）、
   换角色（看不到上一个用户的对话）、管理员也能问。

结果 **1/3 → 22/22**。

### 排查中又踩的两个坑（都是**测试自身**的错）

| 坑 | 表现 | 原因 |
| --- | --- | --- |
| 同帧读 DOM | 三条都判"没填进去"，但 detail 里打印的输入框是**上一句** | `question` 是 ref，textarea 的 `v-model` 要到 `nextTick` 才写回 DOM |
| 复用了上一轮的会话 | "首问后有 0 条建议" | `launch()` 复用浏览器 profile，`sessionStorage` 把旧对话铺回来，"等到第一块解答"在页面刚打开时就成立 |

这两条与 R21 记过的"断言等到了页面上本来就有的东西"是同一类错误：
**判据必须只对"本次操作产生的结果"成立。**

## AK.4 退出码 1：环境行为，不是用例失败

R22 遗留的问题。做法是把变量逐个排除：

```
# 默认 basetemp（落在 %TEMP%）
→ 493 passed，但 EXIT=1，且汇总行时有时无

# 项目内 basetemp，每轮换新目录
.venv\Scripts\python.exe -m pytest --basetemp=.build/pt-r24a -p no:cacheprovider
→ 493 passed, 1 warning in 408.21s   EXIT=0
```

结论：pytest 收尾批量清理 `%TEMP%\pytest-*`，被本机安全钩子拦下 → 退出码非零。
**用例数是 493**，另用 `--collect-only -q` 独立核对（31 个文件、合计 493），不照抄历史文档。

唯一告警 `InsecureKeyLengthWarning` 来自**测试用例自己**造的 14 字节密钥（为验"换密钥应拒绝"），
不是产品问题——这条也写进报告，免得下次有人拿它当缺陷。

## AK.5 新增四支门禁：把"我看着没问题"换成"这条命令说没问题"

| 工具 | 为什么必须独立存在 |
| --- | --- |
| `match_audit.py` | pytest 用临时库、数据是构造的。这里走**真实库 + 真实接口**，断言"条目数 = 已复核条件数"——只有真数据能验这件事 |
| `data_consistency_check.py` | 数据中心 12 项指标：接口 JSON 与**独立写的 SQL** 逐项比对（不 import `analytics.py` 的函数，否则同一个 bug 会同时错在两条路上） |
| `permission_check.py` | 只验"学生打不开"不够——把接口全拦掉也能通过。必须同时验"管理员能打开" |
| `regression_check.py` | 浏览器脚本管渲染、pytest 管函数，中间"真实服务 + 真实库 + 真实角色能不能跑通"这层没人管 |

### 三个设计上的判断

1. **匹配验收的断言不许写死条数**。读库拿"已复核条件数"（当前 9 条）当预期，
   复核状态变了断言跟着变。写死 9 会变成"下一轮改了复核就莫名其妙失败"。
2. **写操作只删自己创建的 id**。匹配会话 / 计划 / 任务接口没有删除端点，就在 `finally` 里
   按 id 精确删，删完逐表核对零变化。
3. **有一条断言是"故意断言它为真"**：`permission_check` 最后一条断言"登出后旧令牌仍可用"为真。
   因为这是当前的真实语义（JWT 无状态、无吊销表），假装它通过才是错的；
   将来引入吊销表，这条会失败并提醒"该改判了"。

## AK.6 一个必须如实写的副作用：浏览器门禁会写库

接口级门禁清得干净（`match_sessions` 49→49、`action_plans` 9→9、`policy_rules` 63→63），
但**浏览器问答门禁无法只读**：它会真的提问。于是：

| 表 | 起始 | 结束 |
| --- | --- | --- |
| `messages` | 174 | 216（+42） |
| `conversations` | 40 | 46（+6） |

**没有删这 6 条会话。** 理由：它们与用户真实使用产生的数据不可区分，为了账面干净去删业务数据
是更糟的做法。如实登记在测试报告 §6.21.4 与本报告 §4.3。
交付包 `dist/data/app.db` 是独立快照（49 会话 / 174 消息），不受影响。

## AK.10 本轮学到的三条

1. **"测试失败"先分三种**：产品坏了 / 测试假设过期 / 环境干扰。这一轮的两个"遗留问题"
   分别是后两种——**都不是产品问题**，而当时都被记成了产品问题。
2. **结论要能被一条命令复现**。493 这个数用 `--collect-only -q` 数出来，不抄文档；
   退出码用"换 basetemp 重跑"证明是环境；匹配条数从库里读，不写死。
3. **写作时也要防转义**。这一轮在 README 里写 `tools\regression_check.py`，
   `\r` 被当成回车写进了文件——是我自己用一个 `chr(13)` 的检查抓回来的。
   凡是往文档里贴 Windows 路径，写完必须回读一遍。
