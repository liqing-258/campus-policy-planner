## 1. 这套系统现在能跑什么

必须先说清楚边界，避免复现者按"完整系统"的预期来验证：

| 能力 | 状态 | 验证方式 |
| --- | --- | --- |
| 后端启动、`/health` 返回真实状态 | ✅ 可用 | `curl /api/v1/health` |
| 登录、JWT、角色守卫 | ✅ 可用 | `curl -X POST /api/v1/auth/login` |
| 13 张表建表、SQLite 三 PRAGMA | ✅ 可用 | `tools/init_db.py` 输出 |
| 前端登录页、工作台、降级提示条 | ✅ 可用 | 打开 http://127.0.0.1:5173 |
| 政策上传（PDF/DOCX/TXT/MD） | ✅ 可用（M3） | `curl -F file=@...` 或 `tools/e2e_gate.py` |
| 解析：文本提取、魔数校验、扫描件识别 | ✅ 可用（M3） | 上传 5 份演示文件，看 `parse_status` |
| 结构化切分（章节 → 段落 → 句子） | ✅ 可用（M3） | `GET /documents/{id}/chunks` |
| BM25 建索引 + 检索 | ✅ 可用（M3，仅脚本侧） | `tools/rebuild_index.py --probe "..."` |
| **政策知识库前端页面（上传页）** | ⬜ **未实现** | 随 M5 界面一起做，M3 不占里程碑 |
| 问答 / 匹配 / 计划 / 任务 | ⬜ 未实现 | M4–M5 |

> **特别注意**：「BM25 建索引 + 检索」目前**只有脚本入口，没有 HTTP 接口**。这是刻意的——
> 没有覆盖率判断的检索接口会让人把"召回了 3 条"误读成"答案有依据"。详见 `接口清单.md` §6.4。

## 3. 三条启动路径

### 3.1 一键脚本（推荐评审）

```bash
git clone https://github.com/liqing-258/campus-policy-planner.git
cd campus-policy-planner
scripts\setup.bat          # macOS/Linux：bash scripts/setup.sh
```

脚本按序执行 5 步，任一步失败即中止：

| 步骤 | 动作 | 失败时的常见原因 |
| --- | --- | --- |
| 1/5 | 建 `.venv` | `python` 不在 PATH |
| 2/5 | 装 `requirements.txt` | 网络不通（可加国内镜像） |
| 3/5 | 复制 `.env.example` → `.env` | 目标文件已存在则跳过 |
| 4/5 | `tools/init_db.py` 建表 | 磁盘权限不足 |
| 5/5 | `tools/seed_demo.py` 写演示账号 | 用户名冲突（加 `--reset`） |

然后两个终端分别启动：

```bash
scripts\start-backend.bat     # 后端 :5000
scripts\start-frontend.bat    # 前端 :5173
```

### 3.2 手动逐步（需要逐条核对时）

```bash
# ① 虚拟环境与依赖
python -m venv .venv
.venv\Scripts\activate                 # macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt

# ② 环境变量
copy .env.example .env                 # macOS/Linux: cp .env.example .env
python -c "import secrets;print(secrets.token_hex(32))"
# 把输出填进 .env 的 JWT_SECRET

# ③ 建表与演示数据
.venv\Scripts\python.exe tools\init_db.py
.venv\Scripts\python.exe tools\seed_demo.py

# ④ 自检（20 项）
.venv\Scripts\python.exe tools\selfcheck.py

# ④.5 生成 5 份虚构演示文件（M3 起需要）
.venv\Scripts\python.exe tools\make_demo_docs.py

# ⑤ 启动
.venv\Scripts\python.exe server.py
```

另开终端：

```bash
cd frontend
npm install
npm run dev
```

### 3.3 分离端口（端口被占用时）

```bash
.venv\Scripts\python.exe server.py --port 5001
```

同时改 `frontend/vite.config.ts` 里 `proxy['/api'].target` 的端口，否则前端调不到后端。

```

[db] PRAGMA foreign_keys=1  journal_mode=wal
```

`foreign_keys=1` 必须为 1。SQLite 默认关闭外键，若此值为 0，删除文档不会级联删除片段——**静默的数据不一致**，因此脚本会显式断言。

### 4.7 文档入库（M3 核心链路）

用管理员令牌传 5 份演示文件，实测结果（`tools/e2e_gate.py` 的真实输出）：

| 文件 | HTTP | code | parse_status | 关键回执 |
| --- | --- | --- | --- | --- |
| 01 正常 PDF（4 页） | 201 | 0 | `indexed` | 切成 4 段，页码 1/2/3/4，202–264 字 |
| 02 正常 DOCX | 201 | 0 | `indexed` | 按 Heading 1 分节 |
| 03 扫描件 PDF | 201 | 0 | `empty` | `parse_hint`="共 1 页，仅提取到 0 个字符（平均每页 0.0 字），疑似扫描件。本系统不含 OCR，请上传带文本层的 PDF 或手工录入。" |
| 04 空文本 TXT | 201 | 0 | `empty` | `parse_hint`="仅提取到 0 个字符，低于有效阈值 50。" |
| 05 改名假文件 | 415 | 1005 | —（未落盘） | 扩展名 `.pdf` 但内容是 MZ 头，魔数校验在写盘前拦下 |

单条 `curl` 复现（第 1 条）：

```
$ curl -X POST http://127.0.0.1:5000/api/v1/documents \
    -H "Authorization: Bearer <TOKEN>" \
    -F "file=@demo/01-本科生奖学金评审办法（演示样例）.pdf" \
    -F "title=（演示样例）奖学金评审办法"
{"code":0,...,"data":{"id":"01M6X...","title":"（演示样例）奖学金评审办法",
 "parse_status":"indexed","chunk_count":4,"parse_error":null,"parse_hint":null,...}}
```

**为什么扫描件返回 201 而不是 4xx**：文件本身是合法的 PDF，系统也确实收下了（保留原件、可重新解析），
只是**没有可检索的文本**。这不是"请求错误"，是"内容不可用"，所以用 201 + `parse_status=empty` + 明确提示。
把这种情况报成 400 会让上传者以为文件坏了，而实际换一份带文本层的 PDF 就行——提示必须能指导行动。

### 4.8 索引与检索（M3 的"索引真的建成了"证据）

索引只在内存里，没有接口可看，所以必须用脚本证明它可用：

```
$ .venv\Scripts\python.exe tools\rebuild_index.py --probe "家庭经济困难认定需要什么材料"
[index] 片段数   10
[index] 词项数   255
[index] 平均词数 46.6
[index] 构建耗时 301.2 ms

[probe] 问题：家庭经济困难认定需要什么材料
  1. score=6.0058  coverage=0.8333 （演示样例）01-…pdf / 第4页 / 第四章 申请材料与附则
     命中词项：家庭、经济、困难、认定、材料
  2. score=6.8427  coverage=0.6667 （演示样例）01-…pdf / 第2页 / 第二章 申请条件
     命中词项：家庭、经济、困难、认定
  3. score=1.3542  coverage=0.1667 （演示样例）02-…docx / 无页码 / 三、材料要求
     命中词项：材料
```

**请重点看第 1、2 名的关系**：第 2 名分数更高（6.8427 > 6.0058），却排在第 1 名后面。
原因是它只覆盖了 4/6 个查询词，而第 1 名覆盖了 5/6——它撞上了更罕见的词（idf 高）所以分数虚高。
这就是排序用 `(coverage, score)` 而不是只看 `score` 的直接理由。

负向验证（知识库里没有的东西必须召不回来）：

```
$ .venv\Scripts\python.exe tools\rebuild_index.py --probe "食堂营业时间"
[probe] 问题：食堂营业时间
  （无命中——若知识库确实没有相关内容，这正是期望行为）

$ .venv\Scripts\python.exe tools\rebuild_index.py --probe "转专业流程"
1. score=2.396  coverage=0.5  …02-学生事务办理指南.docx / 无页码 / 二、办理流程
2. score=2.3005 coverage=0.5  …01-奖学金评审办法.pdf / 第2页 / 第二章 申请条件
3. score=1.2181 coverage=0.5  …01-奖学金评审办法.pdf / 第1页 / 第一章 总则
```

「转专业流程」召回 3 条全是 `coverage=0.5`——**低于 `RAG_MIN_COVERAGE=0.6`，M4 会在这里拒答**。
这正是 M4 拒答机制的落点：不是"分数小于多少"，而是"查询词覆盖不到一半"。

> `build_ms=301.2` 里约九成是 jieba 首次加载词典，第二次构建通常在 10 ms 量级。
> 索引不落盘是刻意取舍：落盘会引入"索引与正文不一致"的坑，而重建成本很低。

## 5. 故障排查（均来自本次实测踩到的真实问题）

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `127.0.0.1:5173` 打不开，`localhost:5173` 能开 | Vite 默认只绑 `localhost`，Windows 上解析为 `::1` | 已在 `vite.config.ts` 设 `host: true`，同时监听 IPv4/IPv6 |
| 前端页面打开是空白的，地址栏变成 `:5174` | 5173 被占用，Vite 默认静默换端口 | 已设 `strictPort: true`，端口占用会直接报错而不是换端口 |
| `curl /api/v1/health` 返回 5000 端口拒绝连接 | 后端未启动，或启动在别的端口 | 看 `server.py` 输出的实际端口；`netstat -ano \| findstr 5000` |
| `[fail] PRAGMA foreign_keys 未生效` | 使用了非 SQLite 驱动却期望该 PRAGMA | 检查 `DATABASE_URL` 是否被误改成 PostgreSQL |
| 登录一直 401 `用户名或密码错误` | 未执行 `tools/seed_demo.py`，或用了旧库 | 重跑 seed；或 `seed_demo.py --reset` |
| 重启后所有令牌失效 | 未设 `JWT_SECRET`，进程内用了开发临时值 | 在 `.env` 写死 `JWT_SECRET` |
| `pytest` 报 `no tests ran` | 在错误目录执行 | 必须在仓库根目录执行（`pytest.ini` 指定了 `testpaths`） |
| 前端 `npm install` 提示 `install-scripts` 未批准 | 新版 npm 的脚本执行策略 | 本项目 `vue-tsc + vite build` 已实测通过，可忽略该提示 |

### 5.1 M3 阶段新增（解析/切分/索引相关）

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 上传正常 PDF，`parse_status` 却是 `failed` | 极可能是解析器内部异常（M3 开发期真踩到过：参数改名后函数体没跟着改，抛 `NameError`，所有 PDF 全挂） | 先看 `parse_error`，M3 起错误信息已带异常类型与内容，如 `解析过程出现未预期错误（NameError: name 'page' is not defined）`。**不要只看"failed"就猜是文件问题** |
| 上传 `.pdf` 返回 415 / `code=1005` | 扩展名是 PDF 但文件头不是 `%PDF-`（改名的可执行文件等） | 这是设计行为。用 `head -c 4 文件 \| od -An -tx1` 确认真实格式 |
| `parse_status=empty`，但文件看起来有内容 | 无文本层的扫描件 PDF，或纯空白 TXT | 看 `parse_hint`，里面写了具体页数与字符数。本系统不含 OCR |
| PDF 切出来几十个 6 字碎片 | 章节标题识别过宽（M3 开发期第一版把「第X条」也当章节，949 字的文件切成 33 段） | 已修：只认章/编/部分/一、/附件级编号，且标题长度 ≤30、不以句末标点结尾。若仍异常，先 `GET /documents/{id}/chunks` 看 `section_title` 是否被误判 |
| DOCX 整篇只切出 1 个片段 | `min_section_chars` 太大，小章节被全并 | 已从 120 降到 40。若文档本身极短（<100 字），1 个片段是正确结果 |
| `tools/rebuild_index.py` 首次跑要 300 ms 以上 | jieba 首次加载词典（约 0.25 s），与索引规模无关 | 正常。第二次构建通常 <20 ms |
| `rebuild_index.py` 报 `no such table: document_chunks` | `DATABASE_URL` 指向的库没建表（常见于手动改了环境变量） | 对同一个库跑 `tools/init_db.py` |
| 用 `tools/e2e_gate.py` 反复跑，第二次开始报 `文档已存在` | 该脚本默认用一次性临时库并自动清理，若手动 `--keep-db` 后又对同一临时库跑，会撞 SHA-256 去重 | 删掉临时目录重跑；或直接不加 `--keep-db` |
| 检索召回一堆明显无关的片段 | BM25 只要有一个词命中就 >0 分，**这是已知行为不是 bug** | 用 `coverage` 判断：`coverage < 0.6` 视为不相关。M4 会把这道闸门做进接口 |

## 6. 重置与清理

| 目标 | 操作 |
| --- | --- |
| 清空所有数据，回到空库 | 删 `data/app.db*`，重跑 `tools/init_db.py` + `tools/seed_demo.py` |
| 重建表结构（会丢数据） | `tools/init_db.py --drop` |
| 重置演示账号 | `tools/seed_demo.py --reset` |
| 清空上传文件 | 删 `data/uploads/*`（不入库，可安全删除） |
| 重建检索索引 | 重启进程即可（索引在内存，随进程重建）；不重启则跑 `tools/rebuild_index.py` |
| 换数据库 | 改 `.env` 的 `DATABASE_URL`，重跑 `tools/init_db.py` |

> `data/` 已在 `.gitignore` 中，不会入库。**不要**把 `app.db` 提交到仓库——里面存的是运行期数据，提交后每次演示都会带上历史脏数据。

## 7. 日志

- 后端：输出到控制台，级别由 `.env` 的 `LOG_LEVEL` 控制（默认 `INFO`）。
- 每个响应带 `request_id`，同时回写 `X-Request-Id` 响应头；排查时用它在日志里串联同一次请求。
- 未预期异常只把堆栈写日志，**不进响应体**（安全红线：不泄露内部结构）。
